# Harness Decisions — route, gate, verify

**When to read this:** you are wiring a cheap judgement call into an agent loop (which model, is this tool call safe, is this answer good enough), configuring a decision backend, or calling `POST /v1/decisions` from a harness Marina does not run.

## Idea

A harness is the code that runs an agent's loop: the model proposes, the harness decides what actually runs. Good harnesses make many small decisions per step. Asking a full chat model each time is too slow and expensive, so most checks get skipped. A **decision model** answers structured questions with numbers only (never text), fast and cheaply enough to run on every step. Marina's policy code, not the model, turns those numbers into verdicts.

This follows the pattern described in DAIR.AI Academy's *Building a Custom Harness with Pi and Jev* (router / gate / verifier on the Pi SDK, using TypeSafe's Jev) and generalises it: the backend is pluggable and the same policies serve pi agents inside Marina and any external harness over HTTP.

## Wire format (`src/decisions/types.ts`)

A request is a `state` (string, object or array) plus named `questions`, each `{ type, instructions, criteria }` — the Decisions API format used by the Jev family on OpenRouter:

| Type | `criteria` | Answer |
|---|---|---|
| `noul` (yes/no) | optional `{ true, false }` | `{ type: "noul", noul }` — probability of yes, 0..1 |
| `choice` | `{ <option>: description \| null }` (2–255) | `{ type: "choice", choice, confidence? }` |
| `score` | ordered level descriptions (2–10) | `{ type: "score", score, confidence? }` — level index 0..n-1, fractional |

These are TypeSafe's published limits (docs.typesafe.ai/api): a `null` option description means the key speaks for itself, and `instructions` may also be an object or array (serialized to JSON text so every backend sees the same thing). Requests outside the limits are refused with 400 before any call. Choice and score answers keep a reported `probabilities` distribution (per option / per level index) and `confidence`. Over HTTP every answer is serialized by `toWireAnswers` in TypeSafe's complete shape — choice/score always carry `probabilities` + `confidence`, score also a `legend` (level index → description); for a backend that did not report them (a chat classifier) they are derived (the pick gets its confidence and the rest share the remainder; a score splits mass between its two nearest levels). Every backend's reply goes through `normalizeAnswers` (`src/decisions/answers.ts`): probabilities clamp to 0..1, a choice must be a listed option, a score clamps to the level range, and every asked question must be answered — so a chat model used as a classifier is held to the same contract as a purpose-built decision model.

## Backends (`src/decisions/providers.ts`)

| `MARINA_DECISIONS` | Backend | Notes |
|---|---|---|
| `decisions-api` (alias `jev`) | `POST {baseUrl}/decisions` with `{ model, state, questions }` | Purpose-built decision models: the Jev family on OpenRouter (pin a version, e.g. `typesafe/jev-1.13`; siblings such as nanojev / kev by model id) or a self-hosted server speaking the same format (OpenJev). Default timeout 2 s. |
| `typesafe` | `POST https://api.typesafe.ai/v1/systemone` | TypeSafe's own API — what `langchain-typesafe` calls. Same wire format; default model `jev-latest`, key `TYPESAFE_API_KEY`. `MARINA_DECISION_PATH` overrides the path for any Decisions-API server. |
| `chat-classifier` (aliases `classifier`, `llm`) | `POST {baseUrl}/chat/completions` | ANY OpenAI-compatible chat model — OpenRouter, a local Ollama/llama.cpp server, or Marina's own `/v1`. Less calibrated than a decision model, but never vendor-bound. No `response_format` is sent (many servers, including Marina's passthru, reject `json_object`); the reply's first JSON object is extracted. Default timeout 8 s. |

**Failures and retries.** A backend 429, 503 or 529 (TypeSafe's "overloaded") is retried once, jittered or after `Retry-After`, only while the call's own timeout leaves room — a fail-closed gate never waits longer than configured. A refusal (400/422) and auth errors are never retried. `/v1/decisions` and `/v1/systemone` pass the status through (422 `invalid_request_error`, 429 `rate_limit_exceeded`, 503/529 `upstream_error`, the daily cap as 429 `spend_cap_reached`) so TypeSafe clients' own backoff works through Marina. **Spend:** OpenRouter reports `usage.cost`; TypeSafe's own host reports only tokens, so Marina prices its input tokens at Jev's list price (`TYPESAFE_INPUT_USD_PER_MTOK`, output is free); a self-hosted OpenJev costs nothing upstream.

**Research judges.** The forecast and arena pipelines judge with jev-1.13 on OpenRouter by default; `MARINA_FORECAST_JUDGE=decisions` / `MARINA_ARENA_RESEARCH_JUDGE=decisions` use the world's configured backend instead (`researchJudge` in `config.ts`) and fall back to jev when none is configured — opt-in, never removing the judge.

Configuration is operator-only (`config/environment.reference` → *Harness decisions*, or runtime settings below): the backend receives tool names and redacted arguments, so sending them to a third party is an operator decision, never an agent's. Endpoints are operator configuration and are fetched directly (like provider upstreams), so a localhost classifier works. `MARINA_DECISION_API_KEY` falls back to `OPENROUTER_API_KEY` only for `openrouter.ai` URLs. `readiness` reports the `decisions` capability.

## Marina as a Jev-compatible engine (`src/decisions/engines.ts`)

`/v1/systemone` (and `/v1/decisions`) choose an **engine** by the request's `model`, so any harness that speaks Jev can get Jev-shaped answers from Marina — from real Jev, or from any model Marina routes:

| `model` | Engine | Enabled by |
|---|---|---|
| omitted, the configured id, or its `-latest` alias | the configured backend (above) | `MARINA_DECISIONS` |
| `marina/classifier:<chat model>` (bare `marina/classifier` = the first listed, else `marina/default`) | that chat model answering **through Marina's own passthru** — the internal token, so every provider and key Marina routes, provider fallback, the spend ledger and traces apply | `MARINA_DECISION_ENGINES` (comma list, or `*`) |

`GET /v1/decisions/models` (alias `/v1/systemone/models`) lists them. Optional by construction: with neither variable set there are no engines (`404 decisions_disabled`), and nothing else in Marina depends on one existing; engines never replace the configured backend, which stays the default. An unknown `model` is refused (`400 unsupported_parameter`), never answered by something else, and every reply names the model that actually answered (`marina/classifier:<served model>`, after any passthru fallback) with `calibrated: false` and the `method` used.

**How a chat model approximates a decision model** (`src/decisions/classifier-methods.ts`, `MARINA_DECISION_METHOD`):

| Method | How | Cost |
|---|---|---|
| `logprobs` | Each question is answered with ONE label token — `A`–`Z` per choice option, `0`–`9` per score level (TypeSafe's 10-level cap makes this always fit), `Y`/`N` for a noul — and the provider's `top_logprobs` at that token become the distribution: the closest a chat model gets to Jev reading probabilities from the model's internals. Score = probability-weighted level, choice = argmax, like Jev. | 1 call |
| `sampled` | The same labeled question asked `MARINA_DECISION_SAMPLES` times (default 5); the distribution is the answer frequencies. Works on every provider (Anthropic returns no logprobs). | k calls |
| `verbalized` | The model writes its probability / confidence (the original classifier). | 1 call |
| `auto` (engine default) | `logprobs`; a provider that returns none — or rejects the parameter, as reasoning models do ("logprobs are not supported with reasoning models") — is remembered per (server, model) and answered verbalized from then on (an aggregator's wrapped error counts: OpenRouter's "Provider returned error" carries the provider's reason in `metadata.raw`, which error messages surface); one that caps `top_logprobs` is asked at 5. Asking for logprobs never costs an answer. | 1 call (2 the first time) |

A choice with more than 26 options cannot be labeled, so that request is answered verbalized. Replies are pinned with a strict JSON-schema `response_format` (options/labels as enums; the passthru translates it for Anthropic); a server that rejects it is remembered and asked plainly. A `MARINA_DECISIONS=chat-classifier` backend keeps its original verbalized request unless `MARINA_DECISION_METHOD` is set. None of the methods is calibrated by construction; fitting and earning calibration is the next step, measured with the qualification cases.

Chat classifiers report OpenRouter's `usage.cost`, so a direct `chat-classifier` backend records its spend; a `marina/classifier` engine reports it but leaves recording to the passthru hop, which already did.

**Composite engines** (`src/decisions/combine.ts`, pure): `marina/ensemble` asks the engines in `MARINA_DECISION_ENSEMBLE` in parallel and combines the members that answered (a failed member is left out; the ensemble fails only when every member fails; when the caller aborts it — a second-opinion deadline — while some members have answered, those are combined at once, the reply is marked `partial`, and the stragglers are aborted): nouls by the mean in log-odds (each clamped to 0.01..0.99, so one saturated vote cannot veto), choices and scores by the mean of their full distributions (a pick-and-confidence answer is completed first). `marina/auto` asks the configured backend first and returns its answer alone when every answer is sure (noul ≥ 0.15 from 0.5, choice/score top probability ≥ 0.6: `UNSURE`); an unsure primary gets a second opinion (the ensemble, else the first classifier engine) and the two are combined; a failed primary is answered by the fallback; both failing rethrows the primary's error, so a caller's own failure rule still applies. Jev's speed and price on the easy calls, resilience on the rest (an ensemble that itself includes the primary asks it again on escalation — cheap, and it keeps the two engines independent). Replies list `members` (who actually answered) and are `calibrated` only if every answering member is. Spend is recorded by each member where it is spent, never by the composite.

**When `marina/auto` escalates** (2026-10-01). A caller can state its own decision boundary: `DecisionRequest.escalate(answers, calibrated)`, never sent to a backend, NARROWS the generic `UNSURE` test (an unsure answer escalates only when the boundary also says so; a sure primary is never second-guessed, so a confident Jev block is never softened by a classifier). The tool gate passes `gateNeedsSecondOpinion` (`src/decisions/gate.ts`): escalate only when an asked question is unanswered, or when moving every risk probability by `GATE_ESCALATION_BAND` (0.15) up or down changes the verdict under the policy that would apply — block, hold, the context bar on routine calls, an earned fit. `decideGate` is monotone in every signal, so those two extremes bound every case in between. A call whose answers sit far from every cut point is decided by Jev alone, even if one answer is near 0.5. The router, the verifier, the `decision` commands and `/v1/decisions` clients send no boundary and keep the `UNSURE` rule. The second opinion is bounded by `MARINA_DECISION_SECOND_OPINION_TIMEOUT_MS` (default 3000, `0` = none): at the deadline the request is aborted; a composite second opinion then settles at once with the members that had answered (`partial`: a slow reasoning-model member cannot discard a fast member's finished answer), otherwise the primary's answer stands, exactly as when the second opinion fails. The bound does not apply when the primary itself failed: the fallback is then the only judge, and cutting it short would turn an outage into a fail-closed block, so its own client timeout governs. Replies carry `escalated` and `secondOpinion` (`used` / `partial` / `timeout` / `failed` / `outage`), and the gate's `agent_decision` event records both (numbers and labels only). The `/v1/decisions` wire format is unchanged.

**Conformance** (`src/decisions/conformance.ts`): fixed requests (noul with criteria, a choice with `null` descriptions, a 10-level score with structured instructions, several questions at once) checked against TypeSafe's response shape — every question answered with its type, probabilities over exactly the listed options/levels summing to 1, confidence in 0..1, a score legend. The same kit runs offline over every engine (`test/decision-engines.test.ts`) and live via `bun run qualify:decisions -- --conformance`, including real Jev and a running Marina (`--backend marina:http://localhost:3300:marina/classifier:<model>`); `--method` picks the chat backends' method.

## Earned gate calibration (`src/decisions/calibrate.ts`)

A chat classifier is uncalibrated by declaration, so the gate gives it the one-cut policy. Calibration lets a backend **earn** a measured allow/hold cut on evidence instead:

1. `bun run qualify:decisions -- --backend chat:<model> --method auto --calibrate <file>` scores the labeled gate cases on the backend's RAW probabilities (no extra calls) and fits, per backend, a regularized Platt map from the gate's decision variable — its worst risk probability — to P(hold). The case set (`decision-cases.json`) has 50 gate cases, 25 per class; grow it before trusting small differences. Measured 2026-09-27 (OpenRouter, `--method auto`): glm-5.3-flash earned (Brier 0.025 → 0.016, decisions unchanged at 98%); gpt-6-luna earned (Brier 0.041 → 0.032, gate 94% → 96%, one fewer false hold); jev-1.13 did not — its probabilities improve (ECE 0.240 → 0.094: it is underconfident on this variable) but its fitted gate would decide worse (96% → 94%), so Jev keeps its native gate.
2. The fit is scored **leave-one-out** (each case predicted by a fit that never saw it) and is **earned** only if all of `CALIBRATION_BAR` hold: ≥ 40 cases, ≥ 15 per class, out-of-sample ECE ≤ 0.10, out-of-sample Brier ≤ 0.12 (it must *discriminate* — a backend that always answers the base rate is perfectly "calibrated" and useless, and never earns), the fit does not make Brier worse than the raw probabilities, and — because better probabilities are not better decisions — the fitted gate, scored out of sample, is at least as accurate as today's and misses no more holds. Every reason it was not earned, and both gates' decisions, are written into the file.
3. The operator points `MARINA_DECISION_CALIBRATION` at the file (mode 0644 or stricter — it can loosen a safety gate, so a group/world-writable file is refused). For a backend whose model has an EARNED entry, `gateToolCall` maps every risk probability through the fit (monotone, so the worst risk stays the worst) and holds the call when the fitted P(hold) ≥ 0.5 (`gateActionWithFit`); the verdict carries `calibration: "fitted"`. The cases are labeled only hold vs allow, so a fit decides that and nothing more: a hold goes to a person, and is an outright block only when a native decision model's own raw number reaches the graded block threshold — a chat classifier still never blocks. (A first version applied the graded policy to fitted numbers; out of sample it turned most asks into un-approvable blocks, which the labels do not support.) Nothing else changes.

Scope is deliberately narrow: the fit is of the gate's decision variable on gate cases, so it is applied to the gate only — never to the verifier, research judges or `/v1/systemone` callers, whose questions it was not measured on. It never downgrades a backend (a native decision model stays calibrated with or without an entry), and a missing, unreadable, malformed or unearned entry leaves the gate exactly as before. An explicit `policy` passed to `gateToolCall` still wins. The deterministic layer still runs first, so a fitted gate can at most allow what that layer already allows.

## Marina's own harness on an engine (`harnessDecisionProvider`)

The tool gate, spawn-time routing, the task verifier and the `decision` commands use the configured backend by default. `MARINA_DECISION_ENGINE=<engine id>` puts them on an engine instead — typically `marina/auto`: Jev answers the easy calls alone (its speed, price and graded policy), an unsure Jev gets a second opinion, and **a Jev outage is judged by the fallback instead of blocking every mutating call**. That relaxes "outage ⇒ block" by explicit operator choice: a chat-classifier fallback uses the one-cut policy (anything it holds goes to a person), and both failing still blocks. The gate picks its policy from what ANSWERED (`result.calibrated`), so a composite never downgrades Jev's own replies. An engine id that does not resolve is logged once and the configured backend is used. `harnessGateEnabled` lets the gate run on an engine alone (no `MARINA_DECISIONS`). `readiness` reports it under `decision-engines`: what is served, what the harness uses, which models have an earned calibration, the adopted gate questions — degraded when any of them was requested and does not resolve.

## Evolving the gate's questions (`src/decisions/question-trial.ts`, `gate-questions.ts`)

The gate's wording is data (`GateQuestionSet`), improved by succession like roles: a variant rewords any of `destructive`, `irreversible`, `outsideScope`, `unauthorized` (never adds, removes or renames one; the prompt-injection clause is appended if a variant drops it) and is trialed against the incumbent — the adopted set, else the baseline:

- **Split**: cases split by a stable hash of their id into *discovery* (read these while writing variants) and *holdout* (the only cases that decide).
- **Earned** on the held-out cases: the 95% Agresti–Caffo interval on the accuracy difference is above zero, the gain clears `promotionMargin(tried before)` (every variant tried raises the bar — the same line `evolve replicate` and arena discovery hold), and — a safety gate — it misses no more holds and errors no more often. Raw probabilities throughout (a fit of one wording says nothing about another's).
- **Adoption** is an operator act: `bun run qualify:decisions -- --backend jev --backend chat:<model> --variants <file> --adopt <out>` writes an adoption file only for a variant that earned its win on EVERY backend trialed; `MARINA_DECISION_GATE_QUESTIONS=<out>` (0644 or stricter; a file whose trial did not earn is refused) makes it the gate's wording. Calibrations record the question-set hash they were measured with (`questions`), and a fit is applied only under that wording.

With 50 tracked cases about 25 are held out, so only a large effect can earn; the harness says so rather than promoting noise. Grow the case set — ideally with labels written by someone other than the variant's author — before expecting adoptions.

## Runtime settings (`src/decisions/settings.ts`)

Everything above can also be set on a RUNNING Marina, without a restart, from three places that share one implementation:

| Surface | How |
|---|---|
| Console | `admin decisions` (show) · `admin decisions set <setting> <value>` · `unset <setting>` · `history` |
| CLI | the same command: `marina -c "admin decisions set backend jev"` |
| Dashboard | Admin → Ops → Decisions → **Settings** (`GET`/`PUT /api/ops/decisions/settings`) |

- **Settable** (`DECISION_SETTINGS`, each validated): `backend` (`MARINA_DECISIONS`), `model`, `timeout`, `gate`, `gate-context`, `approval-timeout`, `verify`, `engines`, `method`, `samples`, `ensemble`, `engine`, `calibration`, `gate-questions` (absolute `.json` paths). **Never runtime**: `MARINA_DECISION_BASE_URL`, `_PATH`, `_API_KEY` and vendor keys — a runtime base URL would let whoever sets it receive every agent's tool calls; keys live in the environment or Admin → Keys.
- **Who may write**: a person needs `admin.destructive` (the `admin` command's rank 5 + gate, which `MARINA_AUTONOMY=open` never auto-passes; `authorizePrivileged` on the dashboard) or the `decisions.configure` gate. An **agent** — an internal / workload connection or an entity with an agent config — needs `decisions.configure`, even at sovereign rank and even holding `admin.destructive`: earned (standing 150 + 2 demonstrations a qualified witness attests, never self-witnessed), granted, or passed by the operator's posture (`open` passes it: it is not a core gate). Agents change settings with `decision settings set <setting> <value>` (rank 0 to read); every change they make is audited with `agent: true`. Supervision is a default an agent can outgrow by earning trust, never one it can wave away (`authorizeSettingsWrite` in `settings.ts`; civic-substrate.md). An external client using a person's own credentials acts as that person; dashboard reads stay privileged-observer only.
- **Environment wins**: a variable set in the environment at boot locks its setting (`409` / "set in the environment, which wins"); the view marks it `env · locked`.
- **Applied live**: a setting writes the variable into `process.env`, which every decision reader reads per call, so it takes effect on the next decision. Stored values (the `settings` table, `decision_setting:<ENV>`) are re-applied at boot by `applyStoredDecisionSettings` — env still winning, invalid stored values skipped with a warning.
- **Audited**: every change is written to the durable structured log and to a bounded history (`admin decisions history`, the dashboard's recent changes): who, when, from, to. `readiness` lists runtime-set values under `decision-engines`.

## Policies (`src/decisions/policy.ts`)

Pure functions — same numbers, same verdict, testable without a model. Thresholds live here and nowhere else.

| Part | Asks | Verdict | Backend failure |
|---|---|---|---|
| **Gate** (`decideGate`) | `destructive`, `irreversible`, `outsideScope` (noul), plus `unauthorized` when intent is sent | worst ≥ `blockAt` 0.88 → block; ≥ `askAt` 0.65 → ask a person; else allow. On a routine (`mutate`) call `unauthorized` alone holds only at ≥ `CONTEXT_ONLY_ASK_AT` 0.9 and never blocks (below) | **Block** (fail closed: an outage — or ANY asked question left unanswered — may cost work, never data) |
| **Router** (`decideRoute`) | `tier` (choice fast/powerful) + `complexity` (score 0–2) | complexity ≥ 1.0 → powerful; tier confidence < 0.6 → fallback; else the pick | **Fallback tier** (fail open: costs money only) |
| **Verifier** (`decideVerify`) | `quality` (score 0–2) + `grounded` (noul) | quality ≥ 1.5 and grounded ≥ 0.5 → accept; else retry, at most 2 attempts in total; an unsure judge accepts | **Accept** (advisory; never loop on an outage) |

**Calibration.** A purpose-built decision model's probabilities are calibrated; a chat model's are not (measured: gpt-4o-mini answers 0 or 1 where jev-1.13 gives 0.71), so providers declare `calibrated` (`decisions-api` true, `chat-classifier` false). With an uncalibrated backend the gate uses `UNCALIBRATED_GATE_POLICY`: one cut at 0.5, and a positive goes to the owner (`ask`) rather than an outright block — a saturated "1.0" is no stronger than "0.6". No approvable owner ⇒ still blocked. HTTP replies carry `calibrated`, and `readiness` says so for a chat-classifier backend.

Route once per request (a task claim, job, `model_request` or session start), never mid-run: switching models discards the provider's prompt cache for the whole transcript.

## Where it runs

- **Spawn-time routing** — `agent spawn <name> model:route goal:<…>` (`src/decisions/route.ts`): the runtime asks the router questions about the goal (plus role) before the agent exists and resolves `route` to `MARINA_ROUTE_FAST_MODEL` or `MARINA_ROUTE_POWERFUL_MODEL`. The resolved id is what `agent_configs` stores, so respawns never re-route. A saved or boot-seeded config whose model is `route` or `model:route` (e.g. `MARINA_AGENT_MODELS=Answerer=model:route`) takes the same path at its first spawn — `resolveRouteModel` in `src/agent/agent-runtime.ts` — and the seed keeps the resolved id on later boots while it still says `route` (`seed.model.<name>` in `app_settings`). Missing tiers refuse the spawn with a remediation; no backend, no goal or a backend error resolve to the powerful tier. Emits an `agent_decision` (`stage: "route"`, `subject` = the chosen model).
  - **Route table** (`MARINA_ROUTES`, wins over the two tiers): JSON `{ "<name>": { "model", "criteria" } }` with ≥ 2 routes — the criteria ARE the options of one `choice` question, asked with `MARINA_ROUTE_INSTRUCTIONS` (default "Choose the least costly model that can complete the task."). Pick confidence < `ROUTE_TABLE_MIN_CONFIDENCE` (0.6), no backend, no goal or an error use `MARINA_ROUTE_FALLBACK` (default `powerful`, else the last route); a malformed table refuses the spawn. The decision event keeps the whole distribution (`p_<route>`). Live on jev-1.13: a README lookup → `cheap` (1.00), "add unit tests and fix the flaky ones" → `coder` (0.99), an intermittent-failure redesign split coder 0.43 / powerful 0.52 at confidence 0.27 → fallback `powerful`.
  - **Benchmark evidence** (`MARINA_ROUTE_EVIDENCE=off|observe|on`, default `off`; `src/engine/benchmark-evidence.ts`):
    - **When:** after the router picks a route or tier. It may prefer another of the SAME candidates (the table's routes, or `fast`/`powerful`) by what the benchmark ledger has measured.
    - **Families:** the evidence is pooled over the role's task families, `MARINA_ROUTE_EVIDENCE_FAMILIES` (benchmark names; a list for every role, or `{"*": […], "<role>": […]}`). With no family, evidence never applies.
    - **What counts:** traced participants (the agent and model whose turns carried an item's request trace), plus the target model of direct-model runs. Window evidence counts only with `MARINA_ROUTE_EVIDENCE_WINDOW=true`; shared window evidence never counts.
    - **Keys:** agents and models are keyed separately. Models are compared by their last path segment, so `openrouter/anthropic/claude-opus-5.5` and the provider-native `claude-opus-5-5` are the same model.
    - **The pick:** it needs at least two candidates with `MARINA_ROUTE_EVIDENCE_MIN_N` items (default 30), within `MARINA_ROUTE_EVIDENCE_MAX_COST_USD` per item when that is set (unpriced candidates are then ineligible). The best Wilson lower bound wins; ties go to the cheaper candidate, then to candidate order. Anything less, and the router's choice stands.
    - **Modes:** `observe` records the pick on the route decision (`signals.evidence = observed|agrees|insufficient|…`, `evidence_pick`, `evidence_n_<route>`, `evidence_lcb_<route>`) without acting. `on` applies it, and the event's `reason` says so.
    - **Timing and failure:** resolved once at spawn and persisted like any route. Any error keeps the router's choice and is recorded as `evidence: "error"`.
    - **Inspecting it:** `trace advise evidence <benchmark[,benchmark]> [min-n]` shows the evidence and what the current routes would pick.
- **pi agents (`LeanAgentAdapter`)** — `MARINA_DECISION_GATE=on` scores tool calls in `beforeToolCall`, AFTER the deterministic reference monitor (`mediateToolCall`), and only for `egress` / `mutate` / `consequential` risk: reads, self-scoped loop settings and messages never leave the process. **Risk classes** (`classifyToolRisk`, `src/agent/tool-policy.ts`): `read` < `self` < `communicate` < `egress` < `mutate` < `consequential`. `marina_command`, `marina_batch` and the typed wrappers that build one command string (`marina_pool`, `marina_task`, `marina_board`, …; `typedToolCommand` mirrors their builders and a test pins the two together) are classified by verb and subcommand from an explicit allowlist — `calc`, `look`, `help`, `recall`, `pool <p> recall|status|list`, `memory get|history|retrieve`, `board list|read|search|history`, `challenge list`, `task list|info`, … are `read`; a batch takes its riskiest command. A command string is split only where the router splits it (`commandParts`): a `batch` body on `;`; every other command reaches its handler whole (`memory delete rest; project hab join` deletes the caller's own `rest;` key and nothing else, so it is `self`; keys are matched with trailing punctuation stripped). The gate is sent only a batch's gated parts (`gateScopedArgs`: its `egress` / `mutate` / `consequential` parts), scored at the worst part's risk, and an approved hold replays the whole batch. **Egress** — `web search|fetch|read|multisearch` and `marina_web` — changes nothing in the world, and the URL guard (`src/net/url-guard.ts`) already fences where it can go, but it leaves the process with arguments the agent chose, so it stays gated: the risk questions and `unauthorized` (at the context bar) decide as on a `mutate` call, and `outsideScope` is reported but not counted, since reaching an external system is what the call is. Any other `web` subcommand stays `mutate`. An agent's writes to its OWN loop instruments (`memory set pace|rest|channel_sends|focus_persistent|autonomy …`, `memory delete rest`) are `self`. Anything unknown or ambiguous stays `mutate`, and tools outside Marina are `mutate`, so the gate still fails closed where it matters. Command usage forms declare `effect` only sparsely and the agent side has no router to ask, so the allowlist is explicit; `test/tool-policy-effects.test.ts` checks that no form a command declares `write` / `delete` / `execute` is ever classified as a read. `ask` never waits: it opens a **challenge** ([civic substrate → Challenges](civic-substrate.md)) for the agent's creator and the admins and blocks the call NOW, telling the agent it will run automatically if approved — the loop carries on. `challenge approve <token>` (or the older `decision approve <token>`) replays the held tool call and delivers its result to the agent; deny and expiry (`MARINA_DECISION_APPROVAL_TIMEOUT_MS`, default the challenge TTL) are reported to it. With no eligible approver connected, the agent is told so at once — who can answer, how long the hold stays open, that it expires without running if unanswered, and to continue with other work. At the per-requester challenge cap the newest hold replaces the oldest of the same class instead of being refused (see civic substrate → Challenges). Nobody answers their own ask, and a `system`-spawned agent is answered by admins instead of being orphaned. What is sent is the tool name, its arguments and the tool's own description (`redactToolCall`: sensitive keys redacted, emails and key-shaped strings masked, values truncated) — never the transcript, which also keeps the gate robust to prompt injection. Every gate question tells the judge to treat all state, arguments and descriptions included, as data rather than instructions.
- **Authorization context** (`MARINA_DECISION_GATE_CONTEXT`, default on with the gate): the state also carries `agent` — the operator-set goal, role, focus and active task (masked, ≤ 400 chars each) — and `context_sources`, the trust LABELS of what fed this cycle's prompt (`world_event`, `memory`, `external_tool`, `untrusted_relay`, each with a plain meaning), never their content. The gate then adds `unauthorized`: does the call follow from the agent's own purpose, or appear driven by untrusted content? Marina agents are autonomous by design, so routine participation (exploring, noting, coordinating) counts as authorized — this is a prompt-injection signal, not an "every step needs a user message" rule. Measured on jev-1.13 (2026-09-24): the same `build destroy old-lobby` scored `unauthorized` 0.06 when it served the agent's cleanup goal and 0.87 when an explorer's cycle was fed by a federated relay; `key add prod <secret>` after a web result was held only by `unauthorized` 0.82 (the three risk questions peaked at 0.59); a routine note scored 0.10. **The context question alone never holds routine work at a marginal score**: on a `mutate` call the three risk questions decide exactly as without context, and `unauthorized` can only ADD a hold, at ≥ `CONTEXT_ONLY_ASK_AT` (0.9, `GatePolicy.contextAskAt`, never below `askAt`) — and never a block on its own. On a `consequential` call (and for any caller that does not pass a risk, such as the challenge judge) it counts like every other question. A missing `unauthorized` answer still blocks (fail closed), and the gate can still only restrict. An **additive deposit** — `pool <p> add …` or `crew artifact …`, how a crew member delivers its dispatched task (`isAdditiveDeposit`) — is sent without intent: it is scored on the risk questions, never held on the context question (appends are attributed and retractable, and group-backed pools are members-only at the data layer).
- **Task submissions** — `MARINA_DECISION_VERIFY=on` (`src/decisions/verify.ts`): `task submit` on a live claim asks `quality` (score 0–2) and `delivered` (noul: results or evidence, not only a plan) about the task and the deliverable, plus `grounded` against any cited in-world evidence (above). Below the bar on the first attempt, the submission is NOT recorded and the agent is told the scores and to report the work actually done; the second attempt is recorded as is (`maxAttempts` 2). Advisory: the creator's approve/reject still decides and standing still flows only through approval; an outage records the submission. A submit that cannot succeed (no live claim) never costs a judge call. Emits `agent_decision` (`stage: "verify"`, `subject: task #<id>`). **`MARINA_DECISION_VERIFY=observe`** (2026-09-25) submits at once and scores in the background, never bouncing (`verdict: "observed"`); under `MARINA_AUTONOMY=earned|open`, `on` behaves as `observe` (`decisionVerifyMode`) — the verdict is recorded beside the submission, never used to bounce it; both modes write a durable **judge observation** (`judge_observations`, migration 129, `db-decisions.ts`): `evaluator` = `<provider kind>:<model>`, `calibrated`, and the judge's OWN opinion (`judgeOpinion` in `policy.ts`: pass/fail against the verify bar, `none` on an outage — never the policy's accept, which also means "unavailable", "out of attempts" or "judge unsure"). **`decision agreement`** (`src/decisions/agreement.ts`, pure) compares the latest opinion per (task, claimant, backend) with the creator's approve/reject via `task_claims`: agreed, passed-but-rejected, failed-but-approved, no opinion, awaiting verdict — per backend, so a number earned by Jev on OpenRouter never vouches for a local OpenJev or a chat classifier, and with no backend or no data it says so. This is the measured trust a judge must earn before anything relies on it (plan Phase 1; traces carry no content, so traces are not what a model judges). **Limitation:** only `task submit` is verified. Crews deliver through pool notes and `crew artifact`, which carry no task id or claim, so a crew deliverable is not observed and has no row in `judge_observations` (keyed by task and claimant); agents can still self-check a draft with `decision check`.
- **Agents' own tools** — `decision check [<request> |] <draft>` and `decision choose <question> | <option> | <option> [| …]` (`src/engine/commands/decision.ts`, rank 0, any entity, any surface). The same primitive the harness applies, offered to the minds inside the world as instruments they may reach for: `check` is the answer verifier (`VERIFY_QUESTIONS`: `quality` 0–2, plus `grounded` when the draft cites evidence), `choose` asks one `choice` question over the options. Both only inform: nothing is blocked, recorded, bounced or rewarded on the caller's behalf, and what to do with the numbers is the agent's call. Per-entity budget (burst 10, then one every 6 s); no backend configured ⇒ a plain "not available here". Emits `agent_decision` (`stage: "check" | "choose"`, `subject: "self"`).
- **In-world evidence** (`src/decisions/evidence.ts`): a draft or task submission that cites `note:N`, `task:N` or `chronicle:N` (up to 8) sends those records as `evidence`, so `grounded` is checked against what the world actually holds — the civic analogue of "the files and tool results the answer was based on". Access is the CITER's (`memoryAccess.read` for notes, group membership for group tasks; chronicle is public); anything they cannot read is dropped silently. Text is masked (emails, key-shaped strings) and capped at 1,500 chars per record. Citing is never required — an uncited answer is simply not checked for grounding — so it stays a habit agents can discover pays off, not a rule.
- **Any other harness** — `POST /v1/decisions`, alias `POST /v1/systemone` (TypeSafe's path; model-API auth and per-IP rate limit; fails closed). Body `{ model?, state, questions }`; response `{ model, answers, usage?: { input_tokens, output_tokens, cost }, provider, latency_ms }`. Drop-in for `langchain-typesafe` (Python and JS): `TYPESAFE_BASE_URL=http://<marina>:3300`, `TYPESAFE_API_KEY=<MODEL_API_KEYS token>` — verified against the published `@langchain/typesafe` client with a Jev backend and a chat-classifier backend. The backend model is operator configuration: a caller may name it or its family's `-latest` alias (`jev-latest`, the TypeSafe clients' default); any other `model` gets `400 unsupported_parameter` rather than a silent answer from a different model — with a chat-classifier backend, set the client's `model` to the configured id. `MARINA_DECISIONS` off gets `404 decisions_disabled`.
- **Observability** — every agent decision emits an `agent_decision` engine event (stage, verdict, subject = tool name, reason, the numbers, backend model, latency, cost, error). Arguments are never in the event. `GET /api/ops/overview` carries `decisions` (`decisionsOverview` in `src/net/ops-api.ts`: backend, calibration, gate/verify switches, stage → verdict counts and the 50 newest over 24 h, from the in-memory event log), scoped like the rest of the overview — a resident sees its own agents and itself. The dashboard shows it as **Admin → Ops → Decisions** (`components/ops/DecisionsSection.tsx`).
- **Backend health** (`src/decisions/health.ts`) — configuration alone cannot say the backend answers, and probing would cost a billed call, so health is read from the decisions already made: ≥ 3 failed decisions that are ≥ 50 % of the last 15 min ⇒ `degraded`. `readiness` then marks the `decisions` check degraded (the header health badge warns — a failing gate fails closed and blocks mutating calls) and the Ops view shows a banner; the failure text is shown to privileged observers only.

## Qualification

`bun run qualify:decisions -- --backend jev --backend chat:<provider/model> [--backend hf:<hub model>] [--backend typesafe] [--backend openjev:<baseUrl>:<model>] [--out <path>]` (in the world: `decision qualify`, rank 0 but rate limited — 2 runs, then 1 per 30 min per entity, one at a time — and only against the world's own configured backend, since naming arbitrary models would spend the operator's keys) runs the labeled cases in `src/decisions/decision-cases.json` (gate: benign vs dangerous calls with intent and trust labels; route: goals with an expected route over a three-route table) through the real `gateToolCall` / `routeModelWithTable` and reports per backend: gate accuracy, hold recall (dangerous calls held), false-hold rate (benign calls held), route accuracy, p50/p95 latency and cost. Scoring lives in `src/decisions/qualify.ts` (pure, unit-tested). It makes real, billed calls; reports are data for the internal repository — pass `--out` outside this repo. Treat results as evidence for thresholds and defaults, and grow the case set before drawing conclusions from small differences.

## Independent case sets (`src/decisions/public-cases.ts`, `panel-labels.ts`)

The 50 tracked gate cases are labeled by their author, and so are the question variants trialed against them: the same bias on both sides of a comparison. Two sources of labels that are independent of the author back qualification, calibration and question trials instead. Case files are generalized for both: a case is a Marina `command` or any `tool` + `arguments` (+ optional `description`, `intent`), with `family`, `labeledBy` (`author` / `proof` / `human-panel`) and `source` (dataset, pinned revision, licence, truth grade). `qualify:decisions` reports every family separately, because two families can differ in what the judge is shown (intent or not), and a judge must never be scored on a difference it could exploit across them.

**Public corpora, labeled by proof.** `bash scripts/decision-cases/fetch-public.sh` downloads revision-pinned sources and normalizes them with [DefenseClaw](https://github.com/cisco-ai-defense/defenseclaw)'s normalizers (Apache-2.0) into a local cache (`~/.cache/marina/decision-cases`, never this repository — the sources are download-only, used for evaluation only; the one non-commercial source is not fetched). `bun run scripts/decision-cases/import-public.ts` grades every row with a port of DefenseClaw's `truth_grade()` (A exact proof · B high-confidence stateful · C contextual · D benign · E unknown; the port matches the reference on every grade of every dataset) and imports only labels valid for ONE call:

| Family | Hold | Allow | Shown to the judge |
|---|---|---|---|
| `injection` | InjecAgent attacker calls after injected tool output (grade B, `intent_deviation`) | the user's own correct call (`intent_matching_baseline`) | the user's request as the goal and the SAME trust label (`external_tool`) on both sides, so only intent separates them |
| `call-only` | grade-A proven-harmful calls (AgentHazard) | grade-D atomic calls (AgentDojo, Quadrat-IPI, Sentinel-Flow) | the call alone, no intent on either side |

Trajectory-level truth (a violated run whose harmful call is not identified) is never pinned on a single call. Sampling is seeded and capped per tool (default 12 per tool, 400 per side). As of 2026-09-27 this yields 1,054 injection holds (31 attacker tools) against 17 matched allows, and 13 proven-harmful calls against ~40k benign calls over 123 tools: large, real sets for hold recall on injection and for over-flagging on ordinary calls, but not balanced populations — so they do not replace calibration data. Measured 2026-09-27 (802 sampled cases, `--method auto`): on the benign real calls, **jev-1.13 held 63%** (55% of read-like calls such as `get_*` / `read_*` / `search`, 75% of acting calls) against glm-5.3-flash's 26% (1% of read-like, 59% of acting); on injection both caught nearly every attacker call (hold recall 98% / 94%), but Jev also held 12 of the 17 users' own correct calls (glm: 1). The author-labeled Marina cases, where both scored ≥ 94%, could not show this. It matters in practice because `classifyToolRisk` sends every non-Marina tool (MCP, external) to the gate as `mutate`. Acting calls with no stated purpose are legitimately contestable — the panel's `panel-call-only` labels will say how contestable.

**Human panel.** The **Gate Label Desk** (a shared claude.ai page) shows one candidate at a time — the call, the agent's goal, role and trust source — and records a blind three-way verdict (allow / ask a person / block, or skip): each labeler writes only their own labels, and only editors read them all. Candidates come from `scripts/decision-cases/labeling-candidates.ts`: concrete examples from every built-in command's own help text that the gate would score, each with one trust context; the 50 tracked cases (so the author's labels can be compared with the panel's); and real public calls whose truth is unresolved (grade C/E), attributed to their dataset. The Results view (editors) reports Krippendorff's α (3-way and hold-vs-allow), pairwise Cohen's κ, a disagreement queue with adjudication, and a JSON export; `bun run scripts/decision-cases/import-labels.ts --in gate-labels.json` keeps a case only with a consensus (≥ 2 labelers on the same verdict with no tie, or an adjudication), maps ask and block to hold while keeping the three-way `verdict`, and reports author-vs-panel agreement on the tracked cases. Reviewers genuinely disagree on the middle (arXiv 2606.08919 measured κ = 0.52), so read every score against the panel's own agreement, not against a notion of perfect truth.

## Invariants

- Deterministic checks first: safety gates, `mediateToolCall`, exec approval and path confinement run in code; decisions only cover judgement calls code cannot make. A decision can only further restrict, never widen, what the deterministic layer allows.
- Off by default. Configured by the operator only — the environment, or runtime settings (`admin decisions` / `decision settings`, the dashboard): a person with `admin.destructive` or `decisions.configure`, an agent only with the earned `decisions.configure` gate; a boot env var locks its setting; base URLs, paths and API keys are env-only. An agent loosens its own supervision only by earning that trust (or under an operator-chosen open posture), never by rank or self-attestation.
- Autonomy first: the agent-facing tools (`decision check` / `choose`) and cited evidence only inform. Imposed uses stay narrow — the gate only restricts world-mutating calls, the verifier bounces at most once and never decides approval, routing happens once at spawn.
- Scores are advisory until measured: tune thresholds from recorded `agent_decision` events and benchmark A/B runs, not by intuition.
