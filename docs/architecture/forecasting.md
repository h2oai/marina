# Forecasting, Signal Discovery and the Social Simulation Arena

**When to read this:** you are changing the general forecaster (`src/forecast/`), the shared quantitative helpers (`src/quant/`), its lessons, its learned settings, a competition adapter, signal discovery (`src/arena/discovery/`) or the Social Simulation Arena entrant (`src/arena/`). `CLAUDE.md` states the invariants; this page holds the mechanics. User guides: [`docs/guides/forecasting.md`](../guides/forecasting.md), [`docs/guides/arena.md`](../guides/arena.md), [`docs/guides/futurex.md`](../guides/futurex.md).

## Signal discovery

`src/arena/discovery/`: signals are DATA in a fixed language (`signals.ts`: centre × spread, leakage-free primitives), never code. The loop (`loop.ts`) splits a family's clean resolved rounds BY TIME, shows the proposer only discovery scores (never holdout — `test/arena-discovery.test.ts` asserts it), promotes only on a holdout win over the incumbent by `promotionMargin(tried)` (grows with attempts) without losing on discovery, and records every scored attempt as an `arena-discovery` note. `discovered` forecaster = best promoted signal per family, else the nowcast.

## Forecasting any question

`src/forecast/` generalises the arena's research pipeline to any question: retrieve → mechanical citation check (`NO_FETCH_DOMAINS` honoured) → one analyst per vendor → Jev judge on verified lines → log-odds / weighted-mean aggregation; by default a plain probability or number question now runs through the typed pipeline below (a yes/no choice with probabilities, or a typed number; `plainForecastFor` in `src/forecast/surface.ts`) and keeps the plain answer shape with the typed answer attached as `typed` — `MARINA_FORECAST_PLAIN=legacy` keeps the single-round analyst path. Run verification is on by default (`MARINA_FORECAST_VERIFY=off` skips it), formation routing is on by default (it falls open to the default formation without paired evidence), a caller-chosen formation is validated (`verify` turns the checker on; an unknown name is an error), `board` / `MARINA_FORECAST_BOARD` reads that board's earned configuration first, and resolved history (`forecast/history.jsonl` next to an on-disk DB) records each answer's formation and score. Surfaces: `bun run forecast "<q>"`, the rank-0 `forecast` command (per-entity rate limit — every call costs money), `POST /v1/forecast` (model-API auth; error code `forecast_unavailable` only when no model is available — one model runs it degraded, see docs/guides/single-model.md). Typed answers (`src/forecast/typed.ts`, `answer-types.ts`: choice / multi / number / ranking / text) add plan → bounded research rounds → optional lookups → K runs combined by type (agreement = confidence; numbers read with scale and sign, power-of-ten outliers aligned to the median; opt-in `selection: confidence` / `MARINA_FORECAST_SELECTION` takes the most self-confident run — the default changes only by a held-out win, `benchmarks/futurex/rescore-selection.ts`) → a critique that replaces the answer only when its confidence exceeds the forecast's confidence (`critiqueApplies`); evidence is frozen at a cutoff (`asOf`, else min(now, `endTime`)) and recorded; models stay operator-set; saved via migration 151. General capability only — no benchmark-specific logic in `src/forecast/`; competitions get thin adapters (FutureX: `benchmarks/futurex/` + `bun run futurex`, files as agent `Marina` under org `h2o.ai`, never sends the submission, records it in append-only `external_submissions`, migration 152 → docs/guides/futurex.md). The answer object is the audit trail — keep every stage in it. Lessons are ONE system (`src/learning`, judged, retire/supersede): every forecasting surface recalls through `forecastLessonsFor` (`MARINA_LESSONS=observe` records `observedLessons`, injects nothing), and every caller states its measurement context (leakage rule 2: a `measure` run never recalls lessons learned from the board it measures — the held-out selection in `benchmarks/forecasting/cli.ts`, DeepResearch, `POST /v1/forecast` with `x-marina-eval` (Prophet replays send `measure`); live filing (FutureX `run`, Metaculus, ForecastBench rounds) passes `live`, which lifts the rule; the FutureX clean backtest recalls only its own in-run pool and the arena's `evaluate` a scratch store, so neither can reach the shared pool), the `forecast` command and `POST /v1/forecast` share one builder (`src/forecast/surface.ts`), an outcome is never visible before it was known (FutureX: end time + `SETTLEMENT_MARGIN_MS`), invalidating a ledger run retires the lessons citing `bench:<id>`, and backtests share one knowledge-bound rule (`benchmarks/forecasting/knowledge.ts`: one release table, one margin, floating aliases refused). Learned settings, all running by default and all earned (`src/forecast/adjust.ts`, `prior.ts`, `recalibration.ts`, `skeptic.ts`, `routing.ts`; the `skeptic` formation stays opt-in): prior shrink and recalibration default to `earned` (an earned prior shrink has no cold-start weight; `on` adds the operator's), routing to `on`; with no history no answer changes. Prior shrink, recalibration and formation routing learn ONLY from resolved history visible at the cutoff (`visibleRecords`: resolved ≤ cutoff, never the question itself; `MARINA_FORECAST_HISTORY` stores numbers and option-label hashes, never text), and a learned setting replaces its default only on a held-out win by the margin; shrinkage (prior and the `skeptic` formation) moves only toward an INFORMATIVE prior, never the uniform default. → docs/guides/forecasting.md

**Answer contract** (`src/forecast/answer-contract.ts`, `MARINA_FORECAST_CONTRACT=off|observe|on`, default off): the question's own answer-form instructions (format line, `\boxed{}` wrapper, date format, decimals, pick bounds, list size, word limit) parsed into a structured contract that refines the typed spec. `forecastFormed` resolves it once (a caller's `req.contract`, else parsed under observe/on); `on` carries it in the shared header (planner, runs, verifier, critic, gap and follow-up prompts), the Delphi/tournament prompts and the judge's question, then `applyContract` checks the finished answer: lossless normalisation, else ONE re-ask (critic → planner → first analyst), else the deterministic `fallbackFor`; the record (`contract`: status, before, rendered, violations, re-ask) stays on the answer, and the prediction changes only to a value that validates against the typed spec. `observe` records the check without carrying the contract or changing anything. Benchmark specifics stay in adapters (FutureX: `formatLine: keep|strip`, default strip).

**Opt-in crowd lookups** (`src/forecast/lookup-crowd.ts`): `OPT_IN_LOOKUP_NAMES` (today `manifold`) run only when named in `MARINA_FORECAST_LOOKUPS` / `MARINA_ARENA_RESEARCH_LOOKUPS` — never under `auto`, `all` or `markets`. Manifold reads a past cutoff from the bet history (`/v0/bets?contractId&beforeTime`: the probability after the last trade at or before it, within 30 days; yes/no markets only) and returns nothing when that history is missing; markets created after the cutoff or settled by it are skipped. Opting into several venues no longer forfeits the market-lookup prior: one market per venue on the same question (pairwise title overlap ≥ 2 words) is pooled by `poolVenuePrices` (log-odds mean, log(1+volume) weights only when every venue reports the same `volumeUnit`, spread noted); several markets on one venue stay rejected, and a single venue's output is byte-identical (`test/forecast-prior-venues.test.ts`). Good Judgment Open is deliberately absent (no public API, terms forbid automated collection, no as-of history); a new source implements `ForecastLookup` and adds one builder to `OPT_IN_LOOKUPS`.

### Method routing and the competence map

Formation routing is generalised to **method cards** (`src/forecast/method-cards.ts`): every runnable recipe — each formation, optionally `+verify` / `+noverify`, optionally `+closed-book` (no web research; lookups still run) — has one id that is also its `method:` evidence key, declared answer shapes, preconditions and a cost class; stages inside every recipe (web research, lookups, lessons, prior shrink, recalibration) are listed as components, never candidates. A card whose preconditions fail here (a panel with one run, no retriever, no checker) is never a candidate.

- **Features** (`src/forecast/featurise.ts`): mechanical first (answer type and group, category, board, horizon from the cutoff, supplied priors). `MARINA_FORECAST_FEATURES` (`auto` default) adds two fixed judgements from the configured decision backend through the bounded advisory path (`askAdvisory`, family `routing`): the domain from a fixed taxonomy and a scheduled-event probability. Only the masked question text, answer type and horizon are sent; no backend, a timeout or the spend cap falls open to mechanical features. The class chain is `board:` → `category:` → `domain:<d>/<group>` → `group:`.
- **Routing** (`src/forecast/card-routing.ts`): evidence is resolved, mechanically scored outcomes tagged `family:<class>` and `method:<card>` (live only — a measurement row counts only for its own board), plus the history file's formation records, all visible at the cutoff and never the question itself. The most specific class with `MARINA_FORECAST_ROUTE_MIN_N` records is the class; `earnedPick` (`routing.ts`) is the one promotion rule; sibling classes only order `explore`. No evidence ⇒ the default card (the operator's formation and options) answers exactly as before.
- **Tags**: the decision is the answer's `routing` record; `resolveForecast` copies its families, method and `q:<id>` onto the outcome (`src/forecast/routing-refs.ts`), so every resolved forecast — command, `/v1/forecast`, board adapters — accumulates evidence under the name routing chooses by.
- **Shadow challengers** (`src/forecast/shadow.ts`, `MARINA_FORECAST_SHADOW=off|<fraction>`, default off): a live answer runs one card, so live pairs never formed and routing (min 30 paired) was starved. On a sampled fraction of FILED live forecasts (never a measurement run), `typedForecastFor` leaves a plan beside the finished answer and the filing site (`forecast` command, `POST /v1/forecast` with `save`) starts ONE challenger in the background: the first `explore` card still short of `minN` pairs (the default card when routing answered with a challenger), same request, deps and cutoff. It is filed `eval_mode = live` under `marina:shadow` (source `shadow`; no standing) in the live answer's shape, tagged `shadow`, `method:`/`card:`, `model:`, the live `family:` classes and `q:<id>` or `pair:forecast:<live id>` (what `evidenceFromOutcomes` pairs on), and `resolveForecast` settles it with the live answer on the same value, so its outcome teaches lessons through the one outcome path; it never writes history (its question is already recorded by the live answer, so prior shrink and recalibration get no correlated extra record). FutureX (filed only at learn time) starts the shadow when an `earned` answer is adopted as a row's standing answer, under the same plan, gate and isolation: it is filed keyed by the row (`startBoardShadow`, map `shadows.json`), superseded if the standing answer is revised, and settled by `futurex learn` with the row's resolution (`benchmarks/futurex/shadow.ts`). Judged resolution never picks a shadow up on its own. Caps per UTC day: `_MAX_PER_DAY` (10) and `_CAP_USD` ($2), counting filed shadows and those in flight, plus the world cap. A cutoff more than an hour in the past gets backtest isolation (date-filtered engine as is, else the strict pre-cutoff filter). The live answer is never changed (`test/forecast-shadow.test.ts`). Card evidence now also skips a history record whose answer is already counted from its outcome (keyed by subject), and `|` is allowed in tags, so a yes/no question's `group:binary:no|yes` class is no longer dropped.
- **Route view** (`src/forecast/route-view.ts`, `forecast routes [family]`, read-only): per family and challenger, the paired n against the family's default, the win rate, the paired gain with its interval and whether the route is earned under `earnedPick`, for forecast evidence (outcome rows and the history file, per class) and arena evidence (`loadRouteEvidence`, when an entrant is configured).
- **Competence map** (`src/forecast/competence.ts`, `forecast competence [family]`, readiness line `competence`): per (family, method, metric) from every producer's tagged outcomes — live and measure counts, mean quality or loss with a 95 % interval, 80 %-band coverage for CRPS-scored numbers, last resolution. Read live; never a static claim.

### Forecasts by residents (2026-10-20)

Residents can be forecast analysts, opt-in with `MARINA_FORECAST_RESIDENTS=on` (default `off`: every path is byte-identical — `marina:` keeps its plain HTTP path, the `forecast` command parses no new modifiers, no fence is ever set).

- **`ResidentPart`** (`src/forecast/resident-part.ts`) is a `ModelPart` — the `(system, user) → string` seam every typed stage goes through — whose answer comes from a resident. `marina:<crew>` goes through `routeToChannel` (the crew's outward face, as `/v1`); `role:<r>` resolves to the live resident with that role and the highest standing (the `conduct resolve` rule) and is routed to it pinned (`RouteOptions.pinTarget`), on an endpoint channel it already serves or its own `model-resident-<name>`; parallel slots rotate over the role's residents by standing, and the forecast's asker is never asked (its own command slot is busy waiting). Inside the server the dispatcher is in-process (`src/net/model-api/resident-dispatch.ts`, attached in `main.ts`); a command-line process falls back to `marina:<crew>` over HTTP with `x-marina-asof` and `x-marina-deadline-ms` and reads the answering resident back from `x-marina-respondent` (`role:` needs the server). Each call passes the deadline (what is left of the forecast, capped per call — a crew answers with its best draft), joins the forecast's trace (`src/model` trace context, `routeKind: "agent"`), runs through the forecast's `WorkBudget` and `SpendGuard`, and records which resident answered (`calls`). `modelPart` returns one for `marina:`/`role:` specs when residents are on (a small hook in `service.ts`).
- **The fence.** When any part is a resident and the cutoff is in the past by the real clock (`residentFenceAt`), `forecastTyped` and `forecastFormed` run under `withEvidenceCutoff` (a small hook each, `fencedForResidents`); every resident request then carries the cutoff and the resident's whole turn is bound by the as-of fence (`src/engine/evidence-fence.ts`, [civic substrate](civic-substrate.md#the-as-of-fence--an-evidence-cutoff-over-a-residents-whole-turn)). A measured run requires it: a part made with `requireFence` refuses to call without it.
- **A forecast as a task, run as a Score** (`src/forecast/resident-forecast.ts`): `forecast <q> crew:<c>|role:<r> [pattern:ensemble|delphi] [residents:N] [asof:<date>] [measure:yes]` and `POST /v1/forecast` with `pattern`/`crew`/`role`/`residents` create a world task (value 0 — a forecast earns `forecast_resolved` when it resolves, never task credit; `eval_mode` recorded in its description when measuring) and run the formation through `executeScore`. Templates (`residentForecastScore`): ensemble = `research → f1…fK → combine`; delphi = `research → f1…fK → summary → v1…vK → combine`. Step 0 is the pipeline's own research round; combining stays pure code — the formation runs as usual over K slot parts, and each slot's run (and Delphi revision) is handed to the Score step that owns it, which asks the resident and hands the answer back; anything else (format repair, crux run, follow-up re-run) is asked of the resident directly under the same budget. Planner, critic and verifier stay the pipeline's own. Bounds: `MARINA_FORECAST_RESIDENT_CALLS` (default 24), `MARINA_FORECAST_RESIDENT_TIMEOUT_S` (default 900), `MARINA_FORECAST_RESIDENT_BUDGET_USD` (default none). A measured forecast is always fenced at its cutoff; a live one only when its cutoff is past. Other formations (tournament, skeptic) are not templated yet: Wave C converts formations to Score templates generally, and `residentForecastScore` is the seam.
- **Attribution.** The combined answer is filed as before under the asker (`external_id` `task:<id>`). Each resident's own run is filed as its own answer (`fileResidentRuns`: owner = the resident, `producers: [resident]`, source `forecast-resident`, linked by `parent` and `q:<id>`), its routing record tagged `method:residents-<pattern>`, `model:<its model>` and `resident:<name>` (`routing-refs.ts`), so `resolveForecast` credits the resident whose run scored under the usual cap and independence rule, and card routing gets resident evidence. A live run carries no eval mode (any eval mode never earns); a measured run files `measure`.

## Quantitative helpers (`src/quant/`)

Pure, dependency-free numeric helpers that any agent, the general forecaster and the arena share. There is no model call and no code sandbox. Agents reach them through the rank-0 `quant` command next to `calc`, and the `quantitative-estimates` skill (`seeds/skills/quantitative-estimates.md`) teaches when to use each one.

- **Normal primitives** (`normal.ts`): the Abramowitz–Stegun `erf` and Acklam `normalQuantile` that the arena's scores use (`src/arena/score.ts` and `score-shapes.ts` re-export them unchanged), plus `normalCdf` (Hart/West, absolute error ~1e-15, exactly symmetric) for bucket probabilities.
- **Series fit** (`series-fit.ts`, `fitSeries`): a plain or dated series plus `steps` (or a `target` date converted at the median spacing) gives a mean, an sd and normal quantiles. The methods are `persistence`, `ewma` (α 0.4, seeded at the first value), `blend` ((persistence + EWMA)/2), `trend` (least-squares line over the last 12 values), `damped` (that line with its slope damped 0.9 per step) and `combo` (mean of persistence, EWMA and damped). `auto` takes the lowest rolling-origin RMS only when it beats persistence by 5 %. The sd is `max(sdScale × the method's own steps-ahead rolling-origin RMS, minSd)`. With fewer than `minErrors` origins it falls back to √steps × the one-step change RMS (`sdBasis: "step-changes"`), and a single value gets `minSd`. Non-finite values are dropped and counted; an empty series returns `undefined`.
- **Arena reuse**: `forecastScalar`'s cadence, horizon and candidate spreads (`medianSpacingDays`, `stepsAhead`, `stepChanges`, `rms`, `robustSpread`) and the poll-level rule (`fitSeries` with `method: "blend"`, warm-up 8, `sdScale` 0.5, `minSd` 0.5) run on these primitives. `test/quant-arena-equivalence.test.ts` replays 462 generated series through the refactored arena code and through a frozen copy of the earlier code (`test/fixtures/arena-baseline-legacy.ts`), and requires bit-identical output. Change a primitive only with that test green.
- **Buckets** (`buckets.ts`, `bucketProbabilities`): a predictive normal (sd 0 is a point mass) or a set of quantiles (linear CDF between them, exponential tails matched to the nearest segment's density, tied values as an atom) gives P(each interval) and the most likely one, with ties and coverage reported. Buckets may be open-ended and choose per-end inclusion, which matters only at an atom. Gaps and overlaps are reported through `coverage` and a renormalised `share`. `parseBuckets` reads the text form (`<10, 10-20, [20, 30], A: >=30`), and `thresholdBuckets` builds a partition from cut points.
- **Typed-forecast stage** (`src/forecast/quant.ts`, `MARINA_FORECAST_QUANT=off|observe|on`, default `off`). `quantStage` runs after the lookups. `seriesBaseline` fits the freshest reading that has history, using `auto`, and projects it to the end time. `optionRanges` reads a choice whose every option is a numeric range with `parseBucket`; overlapping or non-range options switch it off. Displayed rounding gaps of at most half the narrowest width are joined at their midpoints, and an exact-value option makes it a count, where each integer covers ±0.5. `bucketProbabilities` turns the baseline, else a supplied numeric prior with value and sd, into option probabilities. Under `off` none of this runs, and the answer and every prompt are byte-identical to before (`test/forecast-quant.test.ts`). Under `observe`, only `answer.quant` is added; prompts and answer are otherwise identical, and `quant.blend` records the distribution the blend would give. Under `on`, the stage adds `QUANT BASELINE` / `QUANT RANGES` dossier lines and a `quant:1` judge-evidence chunk. For a choice asked with probabilities, it blends the buckets into the runs' distribution with `MARINA_FORECAST_QUANT_WEIGHT` (default 0.25) before the critique, and the critique's own blend then applies on top.
- **Intake triage** (`src/forecast/triage.ts`, `triage-calendar.ts`, `triage-route.ts`, `MARINA_FORECAST_TRIAGE=off|observe|on`, default `off`). `triageQuestion` is pure: facts from the text (`deterministicFacts`: publisher table, known statistics with their usual release lags and FRED ids, the reference period — month, quarter including UK financial quarters, ISO week, week ending, day range — a stated release day, the latest dated event, list cues and size from the spec or `parseAnswerContract`, numeric shape including `optionRanges`), optional model facts (`extractFacts`/`parseModelFacts`: validated field by field; a class or verdict in the reply is dropped) and calendar evidence decide `publicationStatus` in a fixed order — stated resolution, series probe, calendar, stated release, event, model date, known lag. A release on day D counts only from D + 36 h; a generic lag never says "published"; anything dated after NOW is ignored. The class follows: published → `lookup`, else list → `list`, else numeric series → `anchor`, else `forecast`; each carries a method (`triage:readoff`, `triage:quant-anchor`, `triage:board`, else the formation card) and a budget hint. `triageCalendar` probes FRED as published the day before NOW (`fredLookup`, ALFRED vintage with a key; a past NOW without a key is never probed) and reads the next release date only for a live NOW. `forecastFormed` calls `forecastTriaged` only when the deps carry triage settings (`typedForecastDeps` adds them only for observe/on), so `off` is byte-identical (`test/forecast-triage.test.ts`). The read-off brief carries `authority` (research authority mode) and the cutoff; the authority URL is read first only for a live cutoff; sources dated after the cutoff and their lines are dropped before `verifyDossier`; one model call must return a quote grounded in the verified evidence, a valid typed value stated in that quote, an as-of not after the cutoff and a cited URL among the sources — else the panel answers. The `triage` command is the same classifier at rank 0, deterministic only.
- **Built-in skills** (`src/agent/builtin-skills.ts`): `seeds/skills/quantitative-estimates.md` is bundled as text, so it ships with the server (`seeds/skills` is in the package files). `skill builtin [name]` shows it and `skill search` matches it. No note is written, so `MARINA_SEED_SKILLS` stays opt-in. The `quantitative-estimates` trait (seeded with the other traits, composed into `researcher` and `market-oracle`) points those roles to it; `seeds/skills/intake-triage.md` and the `intake-triage` trait do the same for `triage`.

## Social Simulation Arena

Marina can be a signed participant in the MIT Social Simulation Arena (`src/arena/`, docs/guides/arena.md). Env-only and OFF by default (`MARINA_ARENA_ENTRANT`, `MARINA_ARENA_KEY_FILE` mode 0600 or refused); filing is an operator act (`bun run arena`, hourly `arena-autopilot` tick job at phase 1500) — the in-world `arena` command is read-only. `protocol.ts` is a byte-exact port of the arena's `signed_forecasts.py` (golden vector in `test/arena.test.ts` — never change it without re-deriving it from the arena's code). The baseline keeps persistence's mean and picks sd per series (RMS or median-based) only when its own history beats the arena's fixed sd 1.5 by ≥ 5 % on the MEAN OF PER-ROUND SKILL — the leaderboard's metric, never total CRPS (a wide spread wins spiky totals and loses most weeks); otherwise exact persistence. `MARINA_ARENA_FORECASTER=model:<provider/model>` shrinks a model's answer toward the baseline; `crew:<m>[,<m>,<m>]` runs statistician/analyst/skeptic roles (one vendor each) with deterministic aggregation (the skeptic only shrinks); its roles read only the judged lesson pool at the round's lock (`forecast`, `arena`, `meta` through `forecastLessonsFor`) — the crew's former unjudged per-series `lesson` notes are no longer written or injected (2026-10-20), and a resolved round teaches once, on the outcome path. `bun run arena evaluate` scores forecasters on resolved rounds (lock order, no outcome before its release) before any switch. `nowcast` reads the arena's Civiqs daily snapshots — only those FETCHED at or before the lock (Civiqs revises nightly) — and Wikipedia daily lists PUBLISHED before it (≥ 2 days before the lock day; final once published, archive partly backfilled). Profile/ranking scoring (`score-shapes.ts`) is a byte-faithful port of the arena's energy score (sha256 point set, Acklam quantile) and RBO; keep it matching `test/arena-score-shapes.test.ts`. `research:` = brief → retrieve → mechanical citation verification → analysts (use other sources for CHANGES, never levels; the benchmark history is authoritative) → Jev judge on verified lines only; web research is evaluated prospectively in shadow (`arena_shadow`, migration 128), never backtested against already revealed outcomes. Every resolved accepted filing settles once on the outcome path (`src/arena/settle.ts`: numbers via `resolveFiled`, profiles/rankings as one mechanical outcome scored by `score-shapes.ts`, each tagged `family:<tracker>` and `method:<kind>`), from the autopilot and from every real operator `submit`. `arena_submissions` (migration 127) is append-only; the autopilot files each round once; an operator may replace it before lock with `--replace`; a transport failure re-sends the SAME signed request within 240 s.

Arena filing traces (migration 154) live in `arena_submissions.detail`, separate from the signed request; keep inputs, origin/projection decisions, strategy fingerprint, evidence and fallbacks. Sign at completion and recheck the lock margin after forecasting. Horizon policies may be scoped by `MARINA_ARENA_NOWCAST_SERIES`; `arena shadow horizons` compares all five policies on shared frozen inputs. Research may use `+research@closed-book` with explicitly enabled structured lookups; FRED changes are verified against the frozen vintage payload, never a later HTML revision.

Arena experiments: `shadow horizons --weekly-anchor` adds aged daily-slope projections from authoritative weekly levels, without enabling them in submissions. `shadow compare` records start / Delphi / FRED / calibrated scalar candidates with a shared input hash; use `shadow paired-score` for matched comparisons, retaining failed/incomplete batches. Frozen data views memoize failures and isolate mutations. Final-forecast uncertainty calibration is shadow-only, estimator/family/unit-bound, chronological and gated on later outcomes; never train model uncertainty on persistence errors. `arena audit` checks source identity, timing and history comparability. Trends archive fallback requires an exact basket and one eligible complete snapshot; never splice rescaled vintages or change its denominator.

`arena:portfolio` is an explicit shadow-only adapter over the existing Score executor: parallel formations, uncertainty-preserving aggregation and recursive refinement share one frozen input set and one `WorkBudget`. Preserve the original forecast anchor at every layer. Never silently turn budget exhaustion into a successful formation fallback. `task-routing.ts` accepts only time-safe paired evidence; keep native metrics/cohorts separate and cross-benchmark transfers labelled as hypotheses. Latest failed attempts remain in qualification. Plans and selector advice never promote themselves into live arena routes.

`research/measurement.ts` and `evidence-index.ts` add target identity and claim provenance
to captured snapshots, without a second truth store. Availability, unit/population matching,
exact source passages and numeric checks remain deterministic. Unknown metadata stays
unknown; configured JEV/classifier advice cannot upgrade it. Semantic deduplication is
limited to structured measurement identity; unstructured paraphrases remain separate.
`arena_attempts` (migration 164) records start/finish events even when a refresh fails before
signing. Accepted submissions remain in their existing ledger. Refresh reuse requires an
exact configuration/input scope and fresh checked evidence; the final lock window overrides
reuse. Challenger tools record every attempt in `arena_shadow`, preserving failures and
whole input batches. Survey-import, numeric, attention and population contracts are
documented in the [arena guide](../guides/arena.md).
