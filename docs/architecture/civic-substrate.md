# Civic Substrate — Standing, Rank, Safety Gates, Trust Profile, Exec Approval, Code Mode

**When to read this:** you are touching anything that decides *who may do what* — standing credits and decay, rank derivation, a safety gate or its enforcement site, the trust profile (`local|shared|public`), the autonomy posture and the gate ladder (approvals as proof), host code execution / the exec-approver chain, Code Mode dispatch, or the Flywheel sandbox boundary. The must-follow invariants are summarised in `CLAUDE.md` → "Civic Substrate"; this page is the full design and walkthrough that the summary points to.

## Standing — earned by verified work
- **One score, earned by verified work (2026-10-14)**: `standing` is the only contribution score (`src/agent/standing.ts`). A credit lands only when someone **independent** of the worker verified the work. Decay is exponential with a 60-day half-life; floor at 0 (no negative scores — exclusion is a separate civic procedure).
- **Independence** (`independentParties`, `recordVerified`): the verifier is not the worker's account and not in its spawn lineage, in either direction. A person and every agent in its lineage (children, grandchildren, siblings) are ONE party. Lineage is `agent_configs.spawned_by`, falling back to the agent principal's owner (`principals.owner_principal_id`) so it survives `agent delete` (`MarinaDB.spawnLineage`). Memory assistance applies the same rule to principals (`principalParty` in `db-principals.ts`).
- **What earns** (the live kinds in `STANDING_AMOUNTS`):

  | Kind | Verified by | Amount |
  | --- | --- | --- |
  | `task_complete` | the task's creator approving a claimant outside its party, in any validation mode (`creator`, `single`, `bounty`) | the task's value: `standing:N` with N from 0 to `TASK_STANDING_MAX` (10). The default is `TASK_STANDING_DEFAULT` (1). `task create` refuses a larger value; a legacy row over the cap pays the cap. |
  | `code_verified` | an independent reviewer approving a Code Mode task attempt whose recorded verification passed (`code review approve`, `creditVerifiedCode` in `src/outcomes/live.ts`) | 1, once per attempt (`code:<runId>`) |
  | `forecast_resolved` | an external resolution or judge, or a market resolver outside the worker's party (`resolveForecast` in `src/outcomes/forecast.ts`) | up to 0.5 by skill: Brier skill over a coin flip, a number inside its 80% band, or a correct typed answer's quality. Paid to the filer AND to every resident or agent the filing names as a producer (`producers`, 2026-10-20) — one party once per answer (a producer in the lineage of a worker already considered earns nothing, paid or refused). Once per answer per account; at most `FORECAST_DAILY_CAP` (1) per account per UTC day. A board or benchmark filing (`eval_mode` set) never earns. Residents' in-world calls (a market room's `predict`, `conduct track`) are filed on this path and earn it. |
  | `experiment_complete` | a recorder outside the completer's party who sampled the experiment, with samples on at least 2 arms | 3 |
  | `assistance_adopted` / `assistance_abstained_confirmed` | the requester adopting an independent helper's proposal, or confirming its abstention | 1 / 0.25, split across a delegated tree |
  | `quest_complete` | the engine's own quest check, once per quest | 3 |

  Penalties stay: `assistance_superseded` (−0.5) and `crew_member_stalled` (−3 after 3 stalls).
- **What no longer earns** (`RETIRED_STANDING_KINDS`; `record()` refuses them):
  - `chronicled`: being named by the Chronicler is recognition, and it stays in the chronicle;
  - `pool_note` and `reflection_recalled`: volume, and recall owners never resolved to accounts;
  - `crew_complete_member`, `crew_complete_lead`, `crew_stage_completed` and `crew_artifact_deposited`: a crew declares its own result, so crew work earns through the tasks an independent creator approves;
  - `helping_act`: completing a canvas intent is self-reported, and the intent's owner never accepts it.

  The ledger is append-only. Existing rows of these kinds stay readable as history, and nothing is deleted or reset. Since 2026-10-20 they count toward no standing by default (`MARINA_STANDING_RETIRED=exclude`): rank derivation, gate standing floors, low-standing review, shared-retrieval weighting, recruiting and the leaderboard all read only kinds that can still be earned. On the live world 97 of 106 ledger rows were `chronicled` or `pool_note`, so the old fade-out left the "verified work" number mostly recognition for two months. `standing` shows the retired value separately ("retired credit … history only") and marks retired rows in the ledger view. `MARINA_STANDING_RETIRED=decay` restores the old behaviour (they count and fade with the half-life). Residents above rank 4 keep their stored rank (progression never touches ranks 5+); a rank 0–4 account whose standing came from retired kinds is re-derived at the next hourly progression pass.
- **Presence-independent**: every credit resolves the worker's durable account by name (`accountKey`: `users.id`, else the live entity id). People, external agents and offline claimants earn equally; `task approve <id> <name>` finds a submitted claim by the claimant's name, so an offline claimant can be approved.
- **One readout** (`standingOf`, `namedLeaderboard`): `standing`, `standing show <name>` (offline included), `standing top`, `task standing`, `orient`, `brief` and `/who` (`src/net/api/entity-api.ts`) all show the same decayed number by account. `task info <id>` shows what independent approval would pay, and marks claims whose approval would pay nothing.
- **Storage**: `entity_standing` is a generic event ledger keyed `(entity_id, kind, ref)`; `entity_standing_cache` rolls up the decayed value. Permission checks read the cache (6h TTL); periodic `recomputeAll()` refreshes via the engine tick. **Durable key (migration 109)**: entity ids are transient (evicted after the 60s reconnect grace, re-minted on the next name-login), so the standing, competence, and witness ledgers are keyed by the durable world account `users.id`. Call sites keep passing entity ids; `MarinaDB.durableEntityKey()` resolves them at the delegate boundary (ids with no account pass through unchanged — tests can still use `"e_1"`). `standing show <name>` works for offline accounts.
- **Rank derivation (rank 0–4 only)**: thresholds 5 / 15 / 40 / 100 standing for ranks 1 / 2 / 3 / 4. Rank is *descriptive* — your standing crosses a threshold and the system observes "you're an organizer." Demotion is the natural consequence of decay.
- **Above the safety threshold (rank 4)**: standing keeps accruing but does NOT auto-promote. Engineers / stewards / guardians / sovereigns are honorifics, not progression states. Capability above the threshold is gated by per-operation **safety gates**, not tier numbers.
- **`standing` command**: agent-facing introspection — `standing` (own ledger), `standing show <name>`, `standing top [N]` (leaderboard).
- **Engine integration**: `applyRankProgression()` runs hourly for online entities; pure threshold lookup, no metric scoring.
- **Operator rank floor (migration 167, `users.rank_floor`)**: `rank <name> <level>` with level below 5 stores that level as a floor. Progression never lowers the account below it, and never lowers a session that holds it. Standing can still raise the rank above the floor. The floor never raises a session above what it was granted at login, so a passwordless remote login still starts at 0. Setting rank 0 clears the floor. Ranks 5 and up are not touched by progression.

## Safety gates and the trust profile
- **Safety gates** (`src/engine/safety-gates.ts`): 14 gated operations (`shell.exec`, `code.exec`, `agent.run`, `agent.spawn`, `role.edit`, `world.lineage`, `world.code`, `decisions.configure`, `adapter.enable`, `connect.manage`, `gateway.connect`, `key.manage`, `admin.destructive`, `code.exec.unrestricted`). Solo use needs an unsupervised competence row in `entity_competence`; an **earnable** gate also needs standing at its floor. How each gate is earned is in the gate ladder table below. Operators bootstrap via `safetyGates.grant(db, entityId, gateId)` from world seeds — no rank shortcut. **Standing is the live prerequisite, competence the durable proof (2026-09-22)**: a demonstrated (flipped) holder is re-checked against the gate's `minStanding` on every `checkGate` / `checkGateForExecution` call using the same cached standing read (6 h TTL). Below the bar — decay (60-day half-life) or a penalty — `checkGate` returns `{ ok: true, supervisedOnly: true, standingDecayed: true, reason: "standing decayed below <min> …" }`, `checkUnattendedGate` / `checkGateForExecution` refuse with the same `standingDecayed` flag, and `getGateProgress` reports `status: "locked", decayed: true`; the competence row is **never** flipped back, so once standing recovers the gate passes again with no re-demonstration. Operator grants are distinguishable — `grantCompetence` writes the `GRANTED_DEMONSTRATIONS` (999) sentinel, `isGrantedCompetence(row)` in `db-competence.ts` — and are **exempt from the re-check in every profile**: the bootstrap paths that make an instance operable (`grantSovereign` for MARINA_ADMINS / verified admin emails / loopback logins, world-seed operator grants, `grantGatesForRank`) produce zero-standing holders by design, so re-checking them on a shared or public instance would lock the operator out of `shell.exec` / `key.manage` / `admin.destructive`; `revoke()` is a grant's revocation path. `RANK_GATES` is unchanged. Decision table (unsupervised row × standing vs `minStanding`): granted → pass (any standing, any profile); demonstrated + standing ≥ min → pass (`unattended`); demonstrated + standing < min → `checkGate` supervised-only/decayed; `checkGateForExecution` then falls through to the ordinary ladder — `profile-local` under `isLocalUngated()`, `posture-open` for non-core gates under `open`, otherwise refused naming the decay (the refusal raises a challenge like any other).
- **Trust profile** (`src/engine/trust-profile.ts`, `MARINA_PROFILE=local|shared|public`, derived by `main.ts` from the bind + auth situation: loopback-only and no `MARINA_AUTH` ⇒ `local`). Friction is a deployment posture, not an architecture. `local` (one operator, their own machine) is **ungated**: `checkGateForExecution` returns `mode: "profile-local"` for every gate including `OPEN_POSTURE_CORE`; the router skips `minRank`; `applyAdminBootstrap` makes every loopback login sovereign; `selectExecApprover` defaults to `auto`; `RateLimiter.bypass` is set; `memoryLimitsFromEnv` is unlimited unless set; `MARINA_DB_DURABILITY` defaults to `normal`; a failed durable archive falls back to a `[compaction]` note; `skill import` is unconfined; passthru injection is on for identified clients. Never off in any profile: exec-decision audit, cognitive ledger, memory receipts, trusted/unverified labels, untrusted framing, the loopback-vs-public fatal check (`assertTrustProfileSafe`: `local` on any non-loopback bind is fatal unless `MARINA_ALLOW_INSECURE_PUBLIC=true` — `MARINA_AUTH` alone does not suffice, since `local` ungates every signed-in user). In-process default before `main.ts` resolves is `shared` (legacy enforcement), so tests keep exercising gates; tests opt in with `setTrustProfile("local")` + `resetTrustProfileForTests()`. Two predicates: `isLocalProfile()` drives performance defaults (limits, budgets, durability, archive fallback, passthru); `isLocalUngated()` = (local **and** `MARINA_AUTONOMY` not explicitly `guarded`) **or** `MARINA_AUTONOMY=sovereign`, and drives permissions (gates, rank floors, sovereign bootstrap, exec `auto`, skill-import confinement). So an admin re-enforces every permission check on a personal instance with one line, `MARINA_AUTONOMY=guarded`, while keeping local speed; `MARINA_PROFILE=shared` restores everything.

## The gate ladder — approvals are the proof (2026-10-14)

Gates are optional tools, never unliftable walls, and nothing blocks a loop. A gated action an entity does not hold yet is **held** as a challenge (below) and runs once a person approves it. That approval is the proof:

- **An approved run is a demonstration.** A person's `challenge approve <token>` (`once`) of an earnable gate's held run records one demonstration toward that gate (`recordGateExecution`, mode `approved`, `GatePass.demonstrates`); `demoThreshold` of them flip the gate to solo use, which then holds while standing stays at the floor. The judge's approvals never count.
- **One party, one rule.** The requester's own lineage — its owner and anyone up its spawn chain — may approve the run (it runs) but never builds the agent's gate (`approvalDemonstrates`, `src/engine/challenges.ts`, reusing verified-work standing's `independentParties`). That is the rule `gate grant` already applied (a non-sovereign never grants to an agent it spawned) and the one verified-work standing applies, so nobody launders trust into their own agents through approvals. Since only the owner and operators may answer a hold, the approvals that count are an operator's (a person at sovereign rank outside the lineage).
- **`always` is a grant and takes an operator.** An owner's `always` is one approval of this run; an operator's `always` writes the grant.
- **Operator-grant gates** (`GateDef.operatorGrant`, exactly `OPEN_POSTURE_CORE`: `key.manage`, `admin.destructive`, `shell.exec`, `code.exec.unrestricted`, `world.code`) have no standing floor and no demonstrations. Their refusal says "Operator grant"; an operator may approve a single held run, which builds nothing; `open` never lifts them; only a grant (`gate grant`, `challenge approve … always`, a seed, `grantGatesForRank`) makes them solo.

**Floors.** Standing is verified work (an independently approved task pays its value, default 1, at most 10; a verified Code Mode attempt 1; an experiment 3) with a 60-day half-life, so an entity that earns *r* points a day settles near *r* × 60 / ln 2 ≈ 86.6 *r*. The earnable floors sit on that curve. A floor only admits the attempt — approvals do the rest — and an operator can still approve a held run below it.

| Gate | Floor | Approved runs | Why this floor |
| --- | --- | --- | --- |
| `code.exec` | 3 | 3 | Three approved tasks: a first week of real work. Allowlisted, workspace-pinned execution. |
| `agent.spawn` | 10 | 3 | One verified task every ~9 days, sustained, or one top-value task. |
| `role.edit` | 10 | 3 | Same class as `agent.spawn`: changes the agents running on an existing role. |
| `world.lineage` | 10 | 3 | Same class: every child world has its own process and spend cap. |
| `agent.run` | 20 | 3 | Acting as another entity: one verified task every ~4 days. |
| `decisions.configure` | 30 | 2 | Changes what supervises agents: about two verified tasks a week. |
| `adapter.enable` | 30 | 2 | Reaches outside the world (Discord, Telegram). |
| `connect.manage` | 30 | 2 | Registers external MCP/HTTP connectors. |
| `gateway.connect` | 30 | 2 | Federates with peer Marinas. |
| `shell.exec` | — | — | Operator grant. Raw shell. |
| `world.code` | — | — | Operator grant. Room code runs inside the engine. |
| `key.manage` | — | — | Operator grant. Credentials. |
| `admin.destructive` | — | — | Operator grant. World erasure. |
| `code.exec.unrestricted` | — | — | Operator grant, never in `RANK_GATES`. Arbitrary host commands, also fenced by the exec approver. |

Before 2026-10-14 the floors were 5 / 40 / 100 / 150 / 200 / 250 / 251: only `code.exec` was reachable and the refusals told newcomers to grow standing to 250. **Living worlds:** nothing is reset — stored ranks, grants (`GRANTED_DEMONSTRATIONS`) and demonstrated rows are untouched; a demonstrated holder simply faces the lower floor.

## Autonomy posture and the retired witness ladder
- **Self-improvement by succession, not self-modification (`role.edit`, `src/engine/role-guard.ts`, 2026-09-25)**: an agent never changes the role it runs on — `role edit|delete|reload <own role>`, `trait delete` of a trait its role is built from, and `agent config <self> role …` are refused outright, in every profile and posture, with the successor path in the refusal. It improves by spawning an improved iteration: `role create <role>-v2 …` is ungated beyond rank 3 (a definition nothing runs on), and binding an agent to it is `agent spawn`, which the `agent.spawn` gate already fences. Changing an EXISTING role or trait — which changes every agent running on it — takes `role.edit` (floor 10, 3 approved runs, in `RANK_GATES` at rank 5); the gate is recorded only when the change actually happens (a `role reload` that reached no agent consumes nothing). `tool-policy.ts` classifies `role edit|delete|reload`, `trait delete` and `agent config` as `consequential`, so the decision gate scores them when on.
- **Supervision is a default an agent can outgrow (`decisions.configure`, `src/decisions/settings.ts`, 2026-09-27)**: the runtime decision settings — the backend, the tool gate, the verifier, engines, calibration and gate-question files — are the judgement layer that supervises every agent. A person changes them with `admin.destructive` (or this gate); an AGENT only through `decisions.configure` (floor 30, 2 approved runs, in `RANK_GATES` at rank 9): earned (standing + approved runs, never self-approved), granted, or passed by the operator's posture — it is not an `OPEN_POSTURE_CORE` gate, so `open` passes it, and the `local` profile ungates it like every gate. `admin.destructive` alone never lets an agent through. Agents use `decision settings set …` (the `decision` command, rank 0; reading is open to all); people also use `admin decisions` and the dashboard. What stays fixed is the operator's own bound: environment-locked settings and env-only base URLs / keys. Every change is audited with `agent: true` when an agent made it. This replaced an absolute "agents never change decision settings" rule: Marina's end state is an open, autonomous, evolving system, so a restriction here is earned away, not permanent.
- **Autonomy posture** (`src/engine/autonomy.ts`, `MARINA_AUTONOMY=guarded|earned|open|sovereign`, env-only by design — never settable in-world). All enforcement sites call `checkGateForExecution` + `recordGateExecution` (never bare `checkGate` — the site lint test enforces this). `guarded` (default): a supervised attempt is held as a challenge and runs once a person approves it; approved runs are the demonstrations. `earned`: `guarded` plus optimistic supervision for **earnable** gates — an entity whose standing clears the floor runs the operation at once, and the run lands as a `pending` row in `witness_attestations` that counts only when an operator (a person outside the requester's lineage) attests it with `witness attest <id>`; operator-grant gates get no optimistic mode. `open` ("YOLO"): every earnable gate auto-passes and the operator-grant core never does — so `open` DOES pass `code.exec` (allowlisted, workspace-pinned host execution) by design; `open`+public+passwordless is a fatal boot error. **The gate is the authority in every posture (2026-09-27)**: a gate-carrying command defers its `minRank` to the gate — the router skips the rank floor whenever `def.gate` is set (and a db is wired) and `checkGateForExecution` decides. Self-approval is always refused. `code.exec` gates the `code` command's host-execution / workspace-mutation subcommands (run/verify/test/lint/typecheck/recipe/apply/revert) so a rank-0 agent can't reach arbitrary host code execution via `code apply` + `code run`; read/inspect/propose stay rank 0. `code.exec.unrestricted` governs running **arbitrary (non-allowlisted)** host commands: operator grant only and NEVER in `RANK_GATES` — not even a sovereign gets it from rank. No approval mints competence toward it (an interactive `code exec-approve` is audited, nothing more), and the headless approver's refusal says it is operator-grant.
- **The witness ladder is folded into challenges (2026-10-14).** Supervision windows and witness requests went unused in practice. `witness` stays as a compatibility command so scripts never break: `witness` shows the ladder; `witness request <gate>` explains the path (run the action; the hold is the request) and opens nothing; `witness grant <entity> <gate>` opens no window — it lists that entity's held runs of the gate you can approve; `witness queue|attest|reject` review the `earned` posture's pending runs under the challenge rule (an operator, outside the lineage, never self). A legacy window row no longer authorizes anything; the table stays readable and is pruned like any audit table.

- **Child worlds are lineage, not destruction (`world.lineage`, 2026-09-27)**: `world` (list/create/start/stop/run/seed-role/adopt) and `marina-descend` moved off `admin.destructive` onto `world.lineage` (floor 10, 3 approved runs — the `agent.spawn` bar; in `RANK_GATES` at rank 5). Creating, running and adopting from child worlds is the self-improvement loop; adoption still needs someone else's approval and `role.edit` for `into:`, and every child keeps its own `MARINA_CHILD_DAILY_SPEND_CAP_USD`. Non-core, so `open` passes it.
- **World code (`world.code`, 2026-09-27)**: the seven `build` code paths (`build code|reload|revert|destroy` and `build command code|reload|destroy`) replaced their inline `rank < 5` checks with the `world.code` gate (operator grant; `RANK_GATES` rank 5) via `checkGateForExecution` + `recordGateExecution`. Room/command code runs inside the engine behind the static sandbox validator (`src/engine/sandbox.ts`); because that is a static check, not a process boundary, `world.code` is in `OPEN_POSTURE_CORE` — operator grant only: `open` never passes it, `earned` gives it no optimistic run, approvals never build it, and only a sovereign grants it. **Migration 140** carries capability across the upgrade: every unsupervised `admin.destructive` row is copied to `world.lineage`, and every account at rank ≥ 5 is granted `world.code` (existing rows untouched).
- **One rank-floor rule (`src/engine/rank-floor.ts`, 2026-09-27; router 2026-10-14)**: the router's `minRank` for an ungated command, and every subcommand floor stricter than its command's `minRank` with no gate of its own, go through `rankFloorRefusal(entity, min, message)` — undefined (proceed) under `isLocalUngated()`, under `open`, or when the running command carries an approved rank challenge covering that floor (`GatePass.waivedRank` ≥ min, so an approval never waives more than the approver vouched for); otherwise the refusal text plus a raised rank challenge. Converted: the router's own floor (`build` 4, `position`/`bankroll` 2, extension commands), `recruit` (rank 2 or the recruit standing), `role create|import` / `trait create` (3), `agent stop|restart|failover|attention*|disable|enable|focus|config` (4), `evolve trial|replicate` (4), `inheritance import` (2), `observe stats` (2) / `observe <entity>` (3), `experiment create` (2), `canvas delete` (1). Where a gate already governs the capability the rank floor is removed and the gate decides: `role edit|delete|reload` and `trait delete` (`role.edit`). Deliberately left as fixed checks: `shell allow|deny|log` (7) and `run raw` (9) — shell/unrestricted execution; `connect` stdio (9) and owner-or-9 checks on `connect`/`gateway`; `position`/`bankroll` writes (5, trading); `rank set` (9); `source connector` and `observe log` (7, others' raw input and connector config); `skill import` (3, host file read); `readiness providers` (spends tokens, already local-aware); crew owner-or-rank-4 recruitment; per-board ranks; the Code Mode interactive-exec sovereign check.
- **Read-only forms are not gated (2026-10-14).** `CommandDef.readOnlyForm(input)` lets a ranked or gated command declare its read forms; for them the router applies neither `minRank` nor `gate`, while the write forms stay behind both: `world list` (`world.lineage`), `position list` (rank 2), `admin decisions` / `admin decisions history` (`admin.destructive`; `decision settings` was already open).
- **Ownership** (`src/engine/ownership.ts`): an object's owner (or the creator of the agent that owns it) acts on it; on a shared/public instance anyone else is refused through `rankFloorRefusal` at rank 9, a challenge an operator can approve. On the local operator's instance and under `open`, ownership is not enforced — deliberately the same posture rule as every non-core floor; it guards no path into the core.
- **The all-gates-off switch (yolo).** `MARINA_AUTONOMY=sovereign` (`isSovereign()`) lifts every gate — the core included — every rank floor and every hold, for a sovereign, self-hosted Marina with no guests, in any trust profile; the profile still chooses the performance defaults. The `local` profile with autonomy not `guarded` does the same implicitly. Both feed `isLocalUngated()`, the one permission predicate. On a non-loopback bind either needs `MARINA_ALLOW_INSECURE_PUBLIC=true` (`assertTrustProfileSafe` refuses otherwise; sign-in is not enough). `MARINA_AUTONOMY=open` is not this switch: it never lifts the core. A guard test (`test/gates-authority.test.ts`) keeps every permission change from narrowing it.
- **`gate` command (`src/engine/commands/gate.ts`, Civic, 2026-09-27)**: `gate list [entity]` (every gate's status and next step), `gate grant <entity> <gate>`, `gate revoke <entity> <gate>`. Granting never escalates and is a PERSON's act (2026-10-14, the same rule holds use): agents grant nothing, whatever their rank; the actor is an operator (a person at rank 9) or a person who holds that gate solo (`checkUnattendedGate`); operator-grant gates (`OPEN_POSTURE_CORE`) are operator-only; self-grant is refused; a non-sovereign never grants to an agent it spawned (no laundering trust into a sockpuppet). Revoke is operator-only. A grant writes the same `GRANTED_DEMONSTRATIONS` row an operator seed does. Every grant and revoke is also an immutable chronicle `event` (`source: gate`, `refs: gate:<id>`; no standing flows from it).
- **`gate audit` / `gate reset` (2026-10-20, `src/engine/gate-audit.ts`)**: before #439 the `local` profile made every loopback login sovereign, the agents it ran included, and until 2026-10-20 a loopback MCP or declared-agent login still was. `grantSovereign` writes all 13 gates at the `GRANTED_DEMONSTRATIONS` sentinel (999), so the live world held 13 gates × 10 accounts at 999 (every resident and helper) and no gate could bite once the profile changed. New logins no longer seed this: under `local`, only a loopback **person** is made sovereign (not an internal or MCP connection, a client that declared `principal: "agent"`, or an account with an agent config or agent principal). Existing databases are **not** changed on boot, because that would change live autonomy on the next restart. Instead the operator has two commands. `gate audit` (read-only) lists every sentinel row by holder and flags agent accounts. `gate reset <entity|agents> [gate|all]` is a dry run by default. Adding `apply` (operator only) revokes sentinel rows only (demonstrated competence is never touched) and writes one chronicle `event` per holder, so `gate grant` restores any row. A revoked gate starts from the baseline a new account has. Under the `local` profile gates are lifted anyway, so a reset matters once the profile or `MARINA_AUTONOMY` changes.
- **Lineage growth limits are operator knobs**: `MARINA_MAX_SPAWN_DEPTH` (3), `MARINA_STANDING_PER_SPAWNED_CHILD` (25), `MARINA_MAX_REPLICAS_PER_RUN` (5), `MARINA_MAX_RELAY_HOPS` (3) — read once in `src/engine/constants.ts` via `positiveNumberFromEnv`; env only, never settable in-world.

## Challenges — a refusal asks instead of walling off
- **Challenges** (`src/engine/challenges.ts`, `src/engine/gate-context.ts`, `challenge` command, 2026-09-27): when a command meets a rank floor or a safety gate the caller can't pass — at the router or at an imperative site (`agent.spawn`, `code.exec`) — or the decision gate answers `ask` for an agent's tool call, Marina raises a challenge the way a coding agent asks before a risky step. The requester's owner (the first person up its `agent_configs.spawned_by` chain) and the connected operators get a token; the refusal returns **at once** and tells the requester it will run automatically if approved — **nothing ever waits on a person** (no tool call, command or tick blocks; the Code Mode exec approver holds in-command requests the same way). `challenge approve <token> [once|always]` leaves a single-use pass for the exact held input and re-dispatches it as the requester (the router claims the pass, arms the approved gate ids for that one run, and `checkGateForExecution` returns `mode: "approved"`); `always` also `grant`s the gate. `challenge deny <token> [why]` and expiry (`MARINA_CHALLENGE_TTL_MS`, default 1 h) are told to the requester. `MARINA_CHALLENGES=off` restores plain refusals. A requester has at most five open challenges of one class and twenty in all, so a newcomer probing different commands is not walled off: the same held input coalesces onto its open challenge; past the class cap the newest hold replaces the requester's oldest challenge of the same class (closed as expired — the requester and the approvers are told it did not run), and only past the overall cap is nothing opened, with a refusal that names the open tokens. A hold raised while no eligible approver is connected tells the requester who can answer, how long it stays open, and to carry on — never a silent wall.
- **Authority never escalates.** An approver must be able to do the thing themselves: an admin, or the creator holding the rank floor and the gate unsupervised (a creator always answers its own agent's tool-call asks). The requester, and any agent it spawned, can never answer (self-attestation). `always` is a grant and needs an operator — anyone else's `always` is approved once. A `once` approval by a person outside the requester's lineage is a **demonstration** toward an earnable gate (`recordApprovedDemonstration`); the owner's, the judge's and any approval of an operator-grant gate are not (see the gate ladder above).
- **People approve (2026-10-14).** Who may answer is decided by principal KIND, not rank: an agent never answers another participant's hold — not even a resident whose stored rank is 9 (residents are not demoted; they simply cannot approve). A participant is an **agent** when its connection is internal (room/crew/runtime agents), arrives over MCP, or declared itself one (`principal: "agent"` on the WebSocket `login`/`auth` message — the default for the SDK's `MarinaClient`; the `marina` CLI and Marina Code REPLs send `person` only on an interactive TTY, so one-shot/pipe use is an agent), or when its account has an agent config or an agent principal. Everyone else is a **person**; an external client using a person's own credentials acts as that person (the same rule as decision settings — a declaration can only remove authority, never add it). An **operator** is a person at sovereign rank, which only operator configuration confers (`MARINA_ADMINS` on loopback, `MARINA_AUTH_ADMIN_EMAILS`, the local profile's loopback operator, an operator's `rank set`). The **owner** of an agent is the first person up its spawn chain, so an agent spawned by an agent is answered for by the person who started the chain. Only eligible people are notified; `challenge approve|deny` from an agent is refused with a pointer to carry on. Answering is never held by the decision gate: `challenge|decision approve|deny` classify as `communicate` (the command checks authority itself), and `challenge`/`decision list` are reads.
- **Durable holds (migration 166, `challenge_holds`).** Every hold is persisted and restored on boot, so a held action survives a restart and still runs in the requester's own slot on approval (resolved by name — entity ids are transient; an absent requester keeps the hold open). The summary is masked; the held input is the requester's own command text and is stored only when `maskSensitiveText` leaves it unchanged — a secret-shaped input is closed at restore with a notice to re-issue it. A decision-gate tool hold survives when its call is a world command (`typedToolCommand`); other tool calls can only be replayed by the process that made them. Expiry is a timer sweep (every 15 s, `CHALLENGE_SWEEP_INTERVAL_MS`), not lazy. Notices the requester could not receive (restored, expired, denied) wait in `requester_notice` and are delivered when it next connects. Offline approvers have a durable inbox: one content-free `ops inbox` item per hold (`challenge:<token>`, category `challenge`, assigned to the owner, resolved on answer or expiry), `challenge` lists answerable holds, and the sweep tells an eligible approver about each hold once when they connect. Settled rows are pruned after 30 days (`RETENTION_POLICIES`); the verdicts live on append-only in `challenge_outcomes`.
- **Unanswered holds reach the operator (2026-10-20).** On the live world all 21 holds expired with nobody answering: they had no owner (operator-only), no operator was connected, and each per-hold inbox item closed on expiry, so nothing visible remained. Now:
  - when holds expire unanswered, one rolling `ops inbox` item, `challenge:unanswered` (warning, category `challenge-digest`, attention kind `approval`), states how many of the last 7 days' holds expired, by class and how many had no owner. It stays open until an operator resolves it, and reopens on the next unanswered expiry;
  - `challenge summary [days]` reports the same: held, approved, denied, expired unanswered and open, by class and by requester (content-free);
  - `MARINA_OPS_NOTIFY` (`src/engine/ops-notify.ts`, default off) pushes a notice out of the world when a hold opens (`challenge.opened`) and when holds expire unanswered (`challenge.unanswered`). An http(s) URL gets a JSON POST; `cmd:<program> [args]` runs a program without a shell, with the title and detail as its last two arguments (for example `cmd:notify-send -a Marina`). A notice carries the class, requester, reason, token and deadline, never the held input. Delivery is fire-and-forget and a failure is only logged;
  - the dashboard's attention drawer raises its desktop notification (when enabled) for an `approval` item as well as for a critical alert.
- **Dashboard REST has no rank shortcut.** `authorizePrivileged` (`src/net/dashboard-api/shared.ts`) lets the gate decide, exactly as the command router does — a sovereign operator holds its gates by grant (`grantGatesForRank` on promotion), so a resident with stored rank 9 does not pass a core gate on rank alone — and a 403 carries the gate's own path-forward `reason`. Cross-entity private-memory reads likewise need `admin.destructive` held unsupervised.
- **Every answer is a label, and the judge earns its shortcut.** Answers land append-only in `challenge_outcomes` (migration 139; summaries masked) with the judge's shadow opinion. `MARINA_CHALLENGE_JUDGE=observe` scores held commands and decision-gate tool holds (the redacted call) through the decision backend without acting; `on` also auto-approves `once` for a class (gate id, `rank:<n>` or `tool:<name>`) only after the judge has EARNED it — ≥ 25 people-answered cases it called allow, approved with a Wilson 95 % lower bound ≥ 0.85 (`earnedJudge` in `src/decisions/earned-judge.ts`, the one rule the outcome judges and `decision agreement` use too) — and still routes every 10th earned case to people. Never a core gate, never `always`, never a deny. `challenge stats` shows the record; `scripts/challenge-labels.ts` exports the labels as a `challenge-live` family (NOT blind — never pooled with the independent case sets) or, with `--blind`, the held actions without answers for the Gate Label Desk.

## Arbitrary code execution — the exec-approver core
- **Arbitrary code exec (exec-approver core)** (`src/coding/exec-approver.ts`): the `code`-command allowlist is the default; a non-allowlisted command runs only when an optional `ExecApprover` (attached per-call to `LocalWorkspace.run`, never global) approves it — still under the residual guards (scrubbed env with no secrets, cwd pinned to root, 300s cap, 64KB output cap, per-root lock). LAYER 0 (highest precedence, in `code.ts` before the `code.exec` `checkGateForExecution` check): host exec is refused entirely over **telnet** (plaintext/unauthenticated) — allowlisted runs included — while websocket/mcp/internal pass. `InteractiveApprover` prompts the loopback sovereign session creator via a perception (`data.execApproval = { token, argv, cwd, rendered }`; resolve with `code exec-approve/deny <token>`), honored only when the server independently verifies loopback+sovereign; `code exec-mode prompt|auto` opts in; `auto` runs without a prompt but still audits; a session-scope allow-set skips re-prompts for identical argv. `HeadlessGateApprover` approves non-interactively iff `MARINA_CODE_EXEC_UNRESTRICTED` lists the entity AND `code.exec.unrestricted` is unsupervised AND identity is trustworthy (`MARINA_AUTH` or loopback-only bind). Every attempt (approve/deny) writes an `exec_decision` coding artifact + event.

## Declarative vs. imperative gate wiring
- **`CommandDef.gate`** field: when set, the command phase (`CommandPhaseCoordinator`) calls `checkGateForExecution` INSTEAD of `minRank` (the gate is the authority) and `recordGateExecution` on a pass; a room command that shadows a builtin runs under its own empty definition, never the builtin's gate. Migrated commands use `{ minRank: 5, gate: "<id>" }` (`adapter` is rank 7, `key` rank 8). Seven gates wire this way (`shell.exec`, `agent.run`, `adapter.enable`, `connect.manage`, `gateway.connect`, `key.manage`, `admin.destructive` — the last on `admin`, `world` and `marina-descend`). The other four are enforced **imperatively**: `agent.spawn` gates a *subcommand* (`agent spawn`, while `agent list/status/diagnose` stay rank 0 and the lifecycle subcommands `stop/restart/config/…` check builder rank 4) and is also checked by every other spawn path (`code` crew/driver/spawn, `evolve`, `demo`, `usecase`); `code.exec` is checked in `code.ts` (and the code driver/workspace paths) before the exec/mutate subcommands (the `code` command itself is rank 0 so read/inspect stay open); `role.edit` is checked by `checkRoleEdit` (`src/engine/role-guard.ts`) inside `role edit|delete|reload`, `trait delete`, `benchmark promote`, `benchmark invalidate|revalidate` (an earned default changes every agent that runs on it; the challenger's own author is always refused, as is the account that invalidated the incumbent — as promoter or as the challenger's author) and `lessons retire|supersede` (a shared outcome lesson steers every agent it is recalled for; retirement closes validity and erases nothing); `shell.exec` is additionally checked imperatively by `run raw` and `connect add … stdio` (`shellExecRefusal`, `src/engine/commands/run.ts`); `code.exec.unrestricted` is checked by `HeadlessGateApprover` (`src/coding/exec-approver.ts`), the one allowlisted bare-`checkGate` site, which refuses anything short of unsupervised competence (`test/spawn-gate-sites.test.ts`).

## Code Mode
- **Code Mode is agentic by default** (`src/engine/commands/code.ts`): entering `code` evaluates the cwd (top-level listing) and a natural-language line is a *task*, not an error — the switch `default` case routes non-subcommand input through `doCode`. `code do <task>` (or any plain line in the modal) dispatches via the session's **driver** (migration 51: `coding_sessions.agent` + `driver`). `single` (default) binds one coding agent to the session (`ensureSessionAgent` recruits-or-spawns a coder, grants it `code.exec`, persists `session.agent`) and hands it the task via `CodeSessionDriver.assignAgent` → the agent loops autonomously with the `marina_code` tool. `crew` (`code driver crew` / `code crew <goal>`) fans out implementer/reviewer/tester. The driver is the extensibility seam for future multi-agent / multi-backend dispatch — strategies slot into `doCode` without touching callers. Explicit `code read/patch/apply/run/...` subcommands remain for manual control.

## Flywheel sandbox direction
- **Flywheel sandbox direction**: the accepted Phase-6 boundary is one durable Flywheel sandbox per Marina entity. Marina owns identity, policy, approvals, Code Mode, artifacts, and audit; Flywheel owns isolated execution, persistent guest disk, hibernate/resume, and publish. M1–M4 functional slices have landed: durable reconciliation, explicit session routing without host fallback, sandbox projects with bounded patch/archive transfer, and managed services with probe/screenshot/publish. M5 production gates cover transfer integrity, network/credential brokering, durable process identity, quotas/operations, and a live cross-product matrix. Never silently fall back from requested sandbox execution to host execution or imply host/guest file coherence.
