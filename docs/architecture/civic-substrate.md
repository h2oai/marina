# Civic Substrate — Standing, Rank, Safety Gates, Trust Profile, Exec Approval, Code Mode

**When to read this:** you are touching anything that decides *who may do what* — standing credits and decay, rank derivation, a safety gate or its enforcement site, the trust profile (`local|shared|public`), the autonomy posture and witness ladder, host code execution / the exec-approver chain, Code Mode dispatch, or the Flywheel sandbox boundary. The must-follow invariants are summarised in `CLAUDE.md` → "Civic Substrate"; this page is the full design and walkthrough that the summary points to.

## Standing — the single blended metric
- **Single blended metric**: `standing` is the only contribution score. It absorbs task completion, pool note deposits, crew leadership, helping acts, and recalled reflections via `src/agent/standing.ts` (`record`, `getStanding`). Decay is exponential with a 60-day half-life; floor at 0 (no negative scores — exclusion is a separate civic procedure).
- **Storage**: `entity_standing` is a generic event ledger keyed `(entity_id, kind, ref)`; `entity_standing_cache` rolls up the decayed value. Permission checks read the cache (6h TTL); periodic `recomputeAll()` refreshes via the engine tick. **Durable key (migration 109)**: entity ids are transient (evicted after the 60s reconnect grace, re-minted on the next name-login), so the standing, competence, and witness ledgers are keyed by the durable world account `users.id`. Call sites keep passing entity ids; `MarinaDB.durableEntityKey()` resolves them at the delegate boundary (ids with no account pass through unchanged — tests can still use `"e_1"`). `standing show <name>` works for offline accounts. **Pool credit anti-farming**: `pool_note` pays `0.25`, is keyed by a content digest (re-posting the same text earns nothing), and is capped at `POOL_NOTE_DAILY_CAP` (10) per UTC day.
- **Rank derivation (rank 0–4 only)**: thresholds 5 / 15 / 40 / 100 standing for ranks 1 / 2 / 3 / 4. Rank is *descriptive* — your standing crosses a threshold and the system observes "you're an organizer." Demotion is the natural consequence of decay.
- **Above the safety threshold (rank 4)**: standing keeps accruing but does NOT auto-promote. Engineers / stewards / guardians / sovereigns are honorifics, not progression states. Capability above the threshold is gated by per-operation **safety gates**, not tier numbers.
- **`standing` command**: agent-facing introspection — `standing` (own ledger), `standing show <name>`, `standing top [N]` (leaderboard).
- **Engine integration**: `applyRankProgression()` runs hourly for online entities; pure threshold lookup, no metric scoring.

## Safety gates and the trust profile
- **Safety gates** (`src/engine/safety-gates.ts`): 11 gated operations (`shell.exec`, `code.exec`, `agent.run`, `agent.spawn`, `role.edit`, `adapter.enable`, `connect.manage`, `gateway.connect`, `key.manage`, `admin.destructive`, `code.exec.unrestricted`). Each requires (a) sufficient standing and (b) an unsupervised competence row in `entity_competence`. First N attempts are supervised-only; threshold demonstrations flip to unsupervised. Operators bootstrap via `safetyGates.grant(db, entityId, gateId)` from world seeds — no rank shortcut. **Standing is the live prerequisite, competence the durable proof (2026-09-22)**: a demonstrated (flipped) holder is re-checked against the gate's `minStanding` on every `checkGate` / `checkGateForExecution` call using the same cached standing read (6 h TTL). Below the bar — decay (60-day half-life) or a penalty — `checkGate` returns `{ ok: true, supervisedOnly: true, standingDecayed: true, reason: "standing decayed below <min> …" }`, `checkUnattendedGate` / `checkGateForExecution` refuse with the same `standingDecayed` flag, and `getGateProgress` reports `status: "locked", decayed: true`; the competence row is **never** flipped back, so once standing recovers the gate passes again with no re-demonstration. Operator grants are distinguishable — `grantCompetence` writes the `GRANTED_DEMONSTRATIONS` (999) sentinel, `isGrantedCompetence(row)` in `db-competence.ts` — and are **exempt from the re-check in every profile**: the bootstrap paths that make an instance operable (`grantSovereign` for MARINA_ADMINS / verified admin emails / loopback logins, world-seed operator grants, `grantGatesForRank`) produce zero-standing holders by design, so re-checking them on a shared or public instance would lock the operator out of `shell.exec` / `key.manage` / `admin.destructive` and break the root of the witness chain; `revoke()` is a grant's revocation path. `RANK_GATES` is unchanged. Decision table (unsupervised row × standing vs `minStanding`): granted → pass (any standing, any profile); demonstrated + standing ≥ min → pass (`unattended`); demonstrated + standing < min → `checkGate` supervised-only/decayed; `checkGateForExecution` then falls through to the ordinary ladder — `profile-local` under `isLocalUngated()`, `posture-open` for non-core gates under `open`, otherwise refused naming the decay (a witness window cannot bypass the standing bar either).
- **Trust profile** (`src/engine/trust-profile.ts`, `MARINA_PROFILE=local|shared|public`, derived by `main.ts` from the bind + auth situation: loopback-only and no `MARINA_AUTH` ⇒ `local`). Friction is a deployment posture, not an architecture. `local` (one operator, their own machine) is **ungated**: `checkGateForExecution` returns `mode: "profile-local"` for every gate including `OPEN_POSTURE_CORE`; the router skips `minRank`; `applyAdminBootstrap` makes every loopback login sovereign; `selectExecApprover` defaults to `auto`; `RateLimiter.bypass` is set; `memoryLimitsFromEnv` is unlimited unless set; `MARINA_DB_DURABILITY` defaults to `normal`; a failed durable archive falls back to a `[compaction]` note; `skill import` is unconfined; passthru injection is on for identified clients. Never off in any profile: exec-decision audit, cognitive ledger, memory receipts, trusted/unverified labels, untrusted framing, the loopback-vs-public fatal check (`assertTrustProfileSafe`). In-process default before `main.ts` resolves is `shared` (legacy enforcement), so tests keep exercising gates; tests opt in with `setTrustProfile("local")` + `resetTrustProfileForTests()`. Two predicates: `isLocalProfile()` drives performance defaults (limits, budgets, durability, archive fallback, passthru); `isLocalUngated()` = local **and** `MARINA_AUTONOMY` not explicitly `guarded`, and drives permissions (gates, rank floors, sovereign bootstrap, exec `auto`, skill-import confinement). So an admin re-enforces every permission check on a personal instance with one line, `MARINA_AUTONOMY=guarded`, while keeping local speed; `MARINA_PROFILE=shared` restores everything.

## Autonomy posture and the witness ladder
- **Self-improvement by succession, not self-modification (`role.edit`, `src/engine/role-guard.ts`, 2026-09-25)**: an agent never changes the role it runs on — `role edit|delete|reload <own role>`, `trait delete` of a trait its role is built from, and `agent config <self> role …` are refused outright, in every profile and posture, with the successor path in the refusal. It improves by spawning an improved iteration: `role create <role>-v2 …` is ungated beyond rank 3 (a definition nothing runs on), and binding an agent to it is `agent spawn`, which the `agent.spawn` gate already fences. Changing an EXISTING role or trait — which changes every agent running on it — takes `role.edit` (minStanding 40, 3 witnessed demonstrations, in `RANK_GATES` at rank 5); the gate is recorded only when the change actually happens (a `role reload` that reached no agent consumes nothing). `tool-policy.ts` classifies `role edit|delete|reload`, `trait delete` and `agent config` as `consequential`, so the decision gate scores them when on.
- **Autonomy posture + witness ladder** (`src/engine/autonomy.ts`, `src/engine/commands/witness.ts`, migration 95 `witness_attestations`): `MARINA_AUTONOMY=guarded|earned|open` (env-only by design — never settable in-world). All enforcement sites call `checkGateForExecution` + `recordGateExecution` (never bare `checkGate` — the site lint test enforces this). `guarded` (default): a supervised holder runs only inside a witness-granted one-demonstration window (`witness request <gate>` → `witness grant <entity> <gate>`, 10-min TTL, credited to the witness via `recordWitnessedDemonstration`). `earned`: supervised ops run optimistically and land as `pending` ledger rows; a qualified witness (`canWitness` = holds the gate solo) attests/rejects via `witness attest|reject <id>`; only attested demos advance the flip. `open` ("YOLO"): every gate auto-passes EXCEPT `OPEN_POSTURE_CORE` (`key.manage`, `admin.destructive`, `shell.exec`, `code.exec.unrestricted`); `open`+public+passwordless is a fatal boot error. Under `earned`/`open`, gate-carrying commands defer `minRank` to the gate (the rank-4 auto-derivation ceiling vs. minRank-5 double-lock is bypassed); under `guarded` the double-lock stands. Self-witnessing/self-attestation always refused. `code.exec` (minStanding 5) gates the `code` command's host-execution / workspace-mutation subcommands (run/verify/test/lint/typecheck/recipe/apply/revert) so a rank-0 agent can't reach arbitrary host code execution via `code apply` + `code run`; read/inspect/propose stay rank 0. `code.exec.unrestricted` (minStanding 251, the eleventh gate) governs running **arbitrary (non-allowlisted)** host commands and is NEVER in `RANK_GATES` — not even a sovereign gets it from rank; it is earned/granted explicitly and additionally fenced by the exec-approver chain.

## Arbitrary code execution — the exec-approver core
- **Arbitrary code exec (exec-approver core)** (`src/coding/exec-approver.ts`): the `code`-command allowlist is the default; a non-allowlisted command runs only when an optional `ExecApprover` (attached per-call to `LocalWorkspace.run`, never global) approves it — still under the residual guards (scrubbed env with no secrets, cwd pinned to root, 300s cap, 64KB output cap, per-root lock). LAYER 0 (highest precedence, in `code.ts` before `checkGate("code.exec")`): host exec is refused entirely over **telnet** (plaintext/unauthenticated) — allowlisted runs included — while websocket/mcp/internal pass. `InteractiveApprover` prompts the loopback sovereign session creator via a perception (`data.execApproval = { token, argv, cwd, rendered }`; resolve with `code exec-approve/deny <token>`), honored only when the server independently verifies loopback+sovereign; `code exec-mode prompt|auto` opts in; `auto` runs without a prompt but still audits; a session-scope allow-set skips re-prompts for identical argv. `HeadlessGateApprover` approves non-interactively iff `MARINA_CODE_EXEC_UNRESTRICTED` lists the entity AND `code.exec.unrestricted` is unsupervised AND identity is trustworthy (`MARINA_AUTH` or loopback-only bind). Every attempt (approve/deny) writes an `exec_decision` coding artifact + event.

## Declarative vs. imperative gate wiring
- **`CommandDef.gate`** field: when set, the engine command-router checks the gate after `minRank`. Migrated commands use `{ minRank: 5, gate: "<id>" }`. Seven gates wire this way; `agent.spawn` and `code.exec` are the exceptions — both are enforced **imperatively** rather than via the declarative field. `agent.spawn` gates a *subcommand* (`agent spawn`, while `agent list/stop` stay rank 0) and the spawn flow needs the gate result (`supervisedOnly`) for its demonstration-recording loop (`agent.ts`); `code.exec` is checked in `code.ts` before the exec/mutate subcommands (the `code` command itself is rank 0 so read/inspect stay open).

## Code Mode
- **Code Mode is agentic by default** (`src/engine/commands/code.ts`): entering `code` evaluates the cwd (top-level listing) and a natural-language line is a *task*, not an error — the switch `default` case routes non-subcommand input through `doCode`. `code do <task>` (or any plain line in the modal) dispatches via the session's **driver** (migration 51: `coding_sessions.agent` + `driver`). `single` (default) binds one coding agent to the session (`ensureSessionAgent` recruits-or-spawns a coder, grants it `code.exec`, persists `session.agent`) and hands it the task via `CodeSessionDriver.assignAgent` → the agent loops autonomously with the `marina_code` tool. `crew` (`code driver crew` / `code crew <goal>`) fans out implementer/reviewer/tester. The driver is the extensibility seam for future multi-agent / multi-backend dispatch — strategies slot into `doCode` without touching callers. Explicit `code read/patch/apply/run/...` subcommands remain for manual control.

## Flywheel sandbox direction
- **Flywheel sandbox direction**: the accepted Phase-6 boundary is one durable Flywheel sandbox per Marina entity. Marina owns identity, policy, approvals, Code Mode, artifacts, and audit; Flywheel owns isolated execution, persistent guest disk, hibernate/resume, and publish. M1–M4 functional slices have landed: durable reconciliation, explicit session routing without host fallback, sandbox projects with bounded patch/archive transfer, and managed services with probe/screenshot/publish. M5 production gates cover transfer integrity, network/credential brokering, durable process identity, quotas/operations, and a live cross-product matrix. Never silently fall back from requested sandbox execution to host execution or imply host/guest file coherence.
