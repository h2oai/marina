# Civic Substrate — Standing, Rank, Safety Gates, Trust Profile, Exec Approval, Code Mode

**When to read this:** you are touching anything that decides *who may do what* — standing credits and decay, rank derivation, a safety gate or its enforcement site, the trust profile (`local|shared|public`), the autonomy posture and witness ladder, host code execution / the exec-approver chain, Code Mode dispatch, or the Flywheel sandbox boundary. The must-follow invariants are summarised in `CLAUDE.md` → "Civic Substrate"; this page is the full design and walkthrough that the summary points to.

## Standing — the single blended metric
- **Single blended metric**: `standing` is the only contribution score. It absorbs task completion, pool note deposits, crew leadership, helping acts, and recalled reflections via `src/agent/standing.ts` (`record`, `getStanding`). Decay is exponential with a 60-day half-life; floor at 0 (no negative scores — exclusion is a separate civic procedure).
- **Storage**: `entity_standing` is a generic event ledger keyed `(entity_id, kind, ref)`; `entity_standing_cache` rolls up the decayed value. Permission checks read the cache (6h TTL); periodic `recomputeAll()` refreshes via the engine tick. **Durable key (migration 109)**: entity ids are transient (evicted after the 60s reconnect grace, re-minted on the next name-login), so the standing, competence, and witness ledgers are keyed by the durable world account `users.id`. Call sites keep passing entity ids; `MarinaDB.durableEntityKey()` resolves them at the delegate boundary (ids with no account pass through unchanged — tests can still use `"e_1"`). `standing show <name>` works for offline accounts. **Pool credit anti-farming**: `pool_note` pays `0.25`, is keyed by a content digest (re-posting the same text earns nothing), and is capped at `POOL_NOTE_DAILY_CAP` (10) per UTC day.
- **Rank derivation (rank 0–4 only)**: thresholds 5 / 15 / 40 / 100 standing for ranks 1 / 2 / 3 / 4. Rank is *descriptive* — your standing crosses a threshold and the system observes "you're an organizer." Demotion is the natural consequence of decay.
- **Above the safety threshold (rank 4)**: standing keeps accruing but does NOT auto-promote. Engineers / stewards / guardians / sovereigns are honorifics, not progression states. Capability above the threshold is gated by per-operation **safety gates**, not tier numbers.
- **`standing` command**: agent-facing introspection — `standing` (own ledger), `standing show <name>`, `standing top [N]` (leaderboard).
- **Engine integration**: `applyRankProgression()` runs hourly for online entities; pure threshold lookup, no metric scoring.

## Safety gates and the trust profile
- **Safety gates** (`src/engine/safety-gates.ts`): 14 gated operations (`shell.exec`, `code.exec`, `agent.run`, `agent.spawn`, `role.edit`, `world.lineage`, `world.code`, `decisions.configure`, `adapter.enable`, `connect.manage`, `gateway.connect`, `key.manage`, `admin.destructive`, `code.exec.unrestricted`). Each requires (a) sufficient standing and (b) an unsupervised competence row in `entity_competence`. First N attempts are supervised-only; threshold demonstrations flip to unsupervised. Operators bootstrap via `safetyGates.grant(db, entityId, gateId)` from world seeds — no rank shortcut. **Standing is the live prerequisite, competence the durable proof (2026-09-22)**: a demonstrated (flipped) holder is re-checked against the gate's `minStanding` on every `checkGate` / `checkGateForExecution` call using the same cached standing read (6 h TTL). Below the bar — decay (60-day half-life) or a penalty — `checkGate` returns `{ ok: true, supervisedOnly: true, standingDecayed: true, reason: "standing decayed below <min> …" }`, `checkUnattendedGate` / `checkGateForExecution` refuse with the same `standingDecayed` flag, and `getGateProgress` reports `status: "locked", decayed: true`; the competence row is **never** flipped back, so once standing recovers the gate passes again with no re-demonstration. Operator grants are distinguishable — `grantCompetence` writes the `GRANTED_DEMONSTRATIONS` (999) sentinel, `isGrantedCompetence(row)` in `db-competence.ts` — and are **exempt from the re-check in every profile**: the bootstrap paths that make an instance operable (`grantSovereign` for MARINA_ADMINS / verified admin emails / loopback logins, world-seed operator grants, `grantGatesForRank`) produce zero-standing holders by design, so re-checking them on a shared or public instance would lock the operator out of `shell.exec` / `key.manage` / `admin.destructive` and break the root of the witness chain; `revoke()` is a grant's revocation path. `RANK_GATES` is unchanged. Decision table (unsupervised row × standing vs `minStanding`): granted → pass (any standing, any profile); demonstrated + standing ≥ min → pass (`unattended`); demonstrated + standing < min → `checkGate` supervised-only/decayed; `checkGateForExecution` then falls through to the ordinary ladder — `profile-local` under `isLocalUngated()`, `posture-open` for non-core gates under `open`, otherwise refused naming the decay (a witness window cannot bypass the standing bar either).
- **Trust profile** (`src/engine/trust-profile.ts`, `MARINA_PROFILE=local|shared|public`, derived by `main.ts` from the bind + auth situation: loopback-only and no `MARINA_AUTH` ⇒ `local`). Friction is a deployment posture, not an architecture. `local` (one operator, their own machine) is **ungated**: `checkGateForExecution` returns `mode: "profile-local"` for every gate including `OPEN_POSTURE_CORE`; the router skips `minRank`; `applyAdminBootstrap` makes every loopback login sovereign; `selectExecApprover` defaults to `auto`; `RateLimiter.bypass` is set; `memoryLimitsFromEnv` is unlimited unless set; `MARINA_DB_DURABILITY` defaults to `normal`; a failed durable archive falls back to a `[compaction]` note; `skill import` is unconfined; passthru injection is on for identified clients. Never off in any profile: exec-decision audit, cognitive ledger, memory receipts, trusted/unverified labels, untrusted framing, the loopback-vs-public fatal check (`assertTrustProfileSafe`: `local` on any non-loopback bind is fatal unless `MARINA_ALLOW_INSECURE_PUBLIC=true` — `MARINA_AUTH` alone does not suffice, since `local` ungates every signed-in user). In-process default before `main.ts` resolves is `shared` (legacy enforcement), so tests keep exercising gates; tests opt in with `setTrustProfile("local")` + `resetTrustProfileForTests()`. Two predicates: `isLocalProfile()` drives performance defaults (limits, budgets, durability, archive fallback, passthru); `isLocalUngated()` = local **and** `MARINA_AUTONOMY` not explicitly `guarded`, and drives permissions (gates, rank floors, sovereign bootstrap, exec `auto`, skill-import confinement). So an admin re-enforces every permission check on a personal instance with one line, `MARINA_AUTONOMY=guarded`, while keeping local speed; `MARINA_PROFILE=shared` restores everything.

## Autonomy posture and the witness ladder
- **Self-improvement by succession, not self-modification (`role.edit`, `src/engine/role-guard.ts`, 2026-09-25)**: an agent never changes the role it runs on — `role edit|delete|reload <own role>`, `trait delete` of a trait its role is built from, and `agent config <self> role …` are refused outright, in every profile and posture, with the successor path in the refusal. It improves by spawning an improved iteration: `role create <role>-v2 …` is ungated beyond rank 3 (a definition nothing runs on), and binding an agent to it is `agent spawn`, which the `agent.spawn` gate already fences. Changing an EXISTING role or trait — which changes every agent running on it — takes `role.edit` (minStanding 40, 3 witnessed demonstrations, in `RANK_GATES` at rank 5); the gate is recorded only when the change actually happens (a `role reload` that reached no agent consumes nothing). `tool-policy.ts` classifies `role edit|delete|reload`, `trait delete` and `agent config` as `consequential`, so the decision gate scores them when on.
- **Supervision is a default an agent can outgrow (`decisions.configure`, `src/decisions/settings.ts`, 2026-09-27)**: the runtime decision settings — the backend, the tool gate, the verifier, engines, calibration and gate-question files — are the judgement layer that supervises every agent. A person changes them with `admin.destructive` (or this gate); an AGENT only through `decisions.configure` (minStanding 150, 2 witnessed demonstrations, in `RANK_GATES` at rank 9): earned (standing + demonstrations a qualified witness attests, never self-witnessed), granted, or passed by the operator's posture — it is not an `OPEN_POSTURE_CORE` gate, so `open` passes it, and the `local` profile ungates it like every gate. `admin.destructive` alone never lets an agent through. Agents use `decision settings set …` (the `decision` command, rank 0; reading is open to all); people also use `admin decisions` and the dashboard. What stays fixed is the operator's own bound: environment-locked settings and env-only base URLs / keys. Every change is audited with `agent: true` when an agent made it. This replaced an absolute "agents never change decision settings" rule: Marina's end state is an open, autonomous, evolving system, so a restriction here is earned away, not permanent.
- **Autonomy posture + witness ladder** (`src/engine/autonomy.ts`, `src/engine/commands/witness.ts`, migration 95 `witness_attestations`): `MARINA_AUTONOMY=guarded|earned|open` (env-only by design — never settable in-world). All enforcement sites call `checkGateForExecution` + `recordGateExecution` (never bare `checkGate` — the site lint test enforces this). `guarded` (default): a supervised holder runs only inside a witness-granted one-demonstration window (`witness request <gate>` → `witness grant <entity> <gate>`, 10-min TTL, credited to the witness via `recordWitnessedDemonstration`). `earned`: supervised ops run optimistically and land as `pending` ledger rows — except `OPEN_POSTURE_CORE`, which gets no optimistic mode and still needs a witness window or grant; a qualified witness (`canWitness` = holds the gate solo) attests/rejects via `witness attest|reject <id>`; only attested demos advance the flip. `open` ("YOLO"): every gate auto-passes EXCEPT `OPEN_POSTURE_CORE` (`key.manage`, `admin.destructive`, `shell.exec`, `code.exec.unrestricted`, `world.code`) — so `open` DOES pass `code.exec` (allowlisted, workspace-pinned host execution) by design; `open`+public+passwordless is a fatal boot error. **The gate is the authority in every posture (2026-09-27)**: a gate-carrying command defers its `minRank` to the gate — the router skips the rank floor whenever `def.gate` is set (and a db is wired) and `checkGateForExecution` decides (standing floor, competence row, witness window, approved challenge, core carve-out). The old `guarded` double-lock (auto-derived rank caps at 4 while gated commands demand 5+, so an earned holder below rank 5 could never reach its own gate) is gone; `minRank` still applies to ungated commands. Self-witnessing/self-attestation always refused. `code.exec` (minStanding 5) gates the `code` command's host-execution / workspace-mutation subcommands (run/verify/test/lint/typecheck/recipe/apply/revert) so a rank-0 agent can't reach arbitrary host code execution via `code apply` + `code run`; read/inspect/propose stay rank 0. `code.exec.unrestricted` (minStanding 251, the top of the ladder) governs running **arbitrary (non-allowlisted)** host commands and is NEVER in `RANK_GATES` — not even a sovereign gets it from rank; it is earned/granted explicitly and additionally fenced by the exec-approver chain.

- **Child worlds are lineage, not destruction (`world.lineage`, 2026-09-27)**: `world` (list/create/start/stop/run/seed-role/adopt) and `marina-descend` moved off `admin.destructive` onto `world.lineage` (minStanding 40, 3 demos — the `agent.spawn` bar; in `RANK_GATES` at rank 5). Creating, running and adopting from child worlds is the self-improvement loop; adoption still needs someone else's approval and `role.edit` for `into:`, and every child keeps its own `MARINA_CHILD_DAILY_SPEND_CAP_USD`. Non-core, so `open` passes it.
- **World code (`world.code`, 2026-09-27)**: the seven `build` code paths (`build code|reload|revert|destroy` and `build command code|reload|destroy`) replaced their inline `rank < 5` checks with the `world.code` gate (minStanding 100, 3 demos; `RANK_GATES` rank 5) via `checkGateForExecution` + `recordGateExecution`. Room/command code runs inside the engine behind the static sandbox validator (`src/engine/sandbox.ts`); because that is a static check, not a process boundary, `world.code` is in `OPEN_POSTURE_CORE` — `open` never passes it, `earned` gives it no optimistic run, and only a sovereign grants it. **Migration 140** carries capability across the upgrade: every unsupervised `admin.destructive` row is copied to `world.lineage`, and every account at rank ≥ 5 is granted `world.code` (existing rows untouched).
- **One shared inline rank floor (`src/engine/rank-floor.ts`, 2026-09-27)**: a subcommand stricter than its command's `minRank` with no gate of its own calls `rankFloorRefusal(entity, min, message)` — undefined (proceed) under `isLocalUngated()`, under `open`, or when the running command carries an approved rank challenge covering that floor (`GatePass.waivedRank` ≥ min, so an approval never waives more than the approver vouched for); otherwise the refusal text plus a raised rank challenge. Converted: `role create|import` / `trait create` (3), `agent stop|restart|failover|attention*|disable|enable|focus|config` (4), `evolve trial|replicate` (4), `inheritance import` (2), `observe stats` (2) / `observe <entity>` (3), `experiment create` (2), `canvas delete` (1). Where a gate already governs the capability the rank floor is removed and the gate decides: `role edit|delete|reload` and `trait delete` (`role.edit`). Deliberately left as fixed checks: `shell allow|deny|log` (7) and `run raw` (9) — shell/unrestricted execution; `connect` stdio (9) and owner-or-9 checks on `connect`/`gateway`; `position`/`bankroll` writes (5, trading); `rank set` (9); `source connector` and `observe log` (7, others' raw input and connector config); `skill import` (3, host file read); `readiness providers` (spends tokens, already local-aware); crew owner-or-rank-4 recruitment; per-board ranks; the Code Mode interactive-exec sovereign check.
- **`gate` command (`src/engine/commands/gate.ts`, Civic, 2026-09-27)**: `gate list [entity]` (every gate's status), `gate grant <entity> <gate>`, `gate revoke <entity> <gate>`. Granting never escalates: the actor is a sovereign (rank 9) or holds that gate solo (`checkUnattendedGate`); `OPEN_POSTURE_CORE` gates are sovereign-only; self-grant is refused; a non-sovereign never grants to an agent it spawned (no laundering trust into a sockpuppet). Revoke is sovereign-only. A grant writes the same `GRANTED_DEMONSTRATIONS` row an operator seed does. Every grant and revoke is also an immutable chronicle `event` (`source: gate`, `refs: gate:<id>`; no standing flows from it).
- **Lineage growth limits are operator knobs**: `MARINA_MAX_SPAWN_DEPTH` (3), `MARINA_STANDING_PER_SPAWNED_CHILD` (25), `MARINA_MAX_REPLICAS_PER_RUN` (5), `MARINA_MAX_RELAY_HOPS` (3) — read once in `src/engine/constants.ts` via `positiveNumberFromEnv`; env only, never settable in-world.

## Challenges — a refusal asks instead of walling off
- **Challenges** (`src/engine/challenges.ts`, `src/engine/gate-context.ts`, `challenge` command, 2026-09-27): when a command meets a rank floor or a safety gate the caller can't pass — at the router or at an imperative site (`agent.spawn`, `code.exec`) — or the decision gate answers `ask` for an agent's tool call, Marina raises a challenge the way a coding agent asks before a risky step. The requester's creator (`agent_configs.spawned_by`) and the connected admins (rank 9) get a token; the refusal returns **at once** and tells the requester it will run automatically if approved — **nothing ever waits on a person** (no tool call, command or tick blocks; the Code Mode exec approver holds in-command requests the same way). `challenge approve <token> [once|always]` leaves a single-use pass for the exact held input and re-dispatches it as the requester (the router claims the pass, arms the approved gate ids for that one run, and `checkGateForExecution` returns `mode: "approved"`); `always` also `grant`s the gate. `challenge deny <token> [why]` and expiry (`MARINA_CHALLENGE_TTL_MS`, default 1 h) are told to the requester. `MARINA_CHALLENGES=off` restores plain refusals. A requester has at most five open challenges: the same held input coalesces onto its open challenge; past the cap the newest hold replaces the requester's oldest challenge of the same class (closed as expired — the requester and the approvers are told it did not run), and only when every open challenge is of another class is nothing opened, with a refusal that names the open tokens. A hold raised while no eligible approver is connected tells the requester who can answer, how long it stays open, and to carry on — never a silent wall.
- **Authority never escalates.** An approver must be able to do the thing themselves: an admin, or the creator holding the rank floor and the gate unsupervised (a creator always answers its own agent's tool-call asks). The requester, and any agent it spawned, can never answer (self-attestation). `always` needs an approver who holds the gate; core gates (`OPEN_POSTURE_CORE`) need an admin — otherwise it is approved once. An approval by a gate holder is a **witnessed demonstration** (`recordWitnessedDemonstration`); an admin-without-the-gate or judge approval is not.
- **Every answer is a label, and the judge earns its shortcut.** Answers land append-only in `challenge_outcomes` (migration 139; summaries masked) with the judge's shadow opinion. `MARINA_CHALLENGE_JUDGE=observe` scores held commands through the decision backend without acting; `on` also auto-approves `once` for a class (gate id or `rank:<n>`) only after the judge has EARNED it — ≥ 25 people-answered cases it called allow, approved with a Wilson 95 % lower bound ≥ 0.85 — and still routes every 10th earned case to people. Never a core gate, never `always`, never a deny. `challenge stats` shows the record; `scripts/challenge-labels.ts` exports the labels as a `challenge-live` family (NOT blind — never pooled with the independent case sets) or, with `--blind`, the held actions without answers for the Gate Label Desk.

## Arbitrary code execution — the exec-approver core
- **Arbitrary code exec (exec-approver core)** (`src/coding/exec-approver.ts`): the `code`-command allowlist is the default; a non-allowlisted command runs only when an optional `ExecApprover` (attached per-call to `LocalWorkspace.run`, never global) approves it — still under the residual guards (scrubbed env with no secrets, cwd pinned to root, 300s cap, 64KB output cap, per-root lock). LAYER 0 (highest precedence, in `code.ts` before the `code.exec` `checkGateForExecution` check): host exec is refused entirely over **telnet** (plaintext/unauthenticated) — allowlisted runs included — while websocket/mcp/internal pass. `InteractiveApprover` prompts the loopback sovereign session creator via a perception (`data.execApproval = { token, argv, cwd, rendered }`; resolve with `code exec-approve/deny <token>`), honored only when the server independently verifies loopback+sovereign; `code exec-mode prompt|auto` opts in; `auto` runs without a prompt but still audits; a session-scope allow-set skips re-prompts for identical argv. `HeadlessGateApprover` approves non-interactively iff `MARINA_CODE_EXEC_UNRESTRICTED` lists the entity AND `code.exec.unrestricted` is unsupervised AND identity is trustworthy (`MARINA_AUTH` or loopback-only bind). Every attempt (approve/deny) writes an `exec_decision` coding artifact + event.

## Declarative vs. imperative gate wiring
- **`CommandDef.gate`** field: when set, the command phase (`CommandPhaseCoordinator`) calls `checkGateForExecution` INSTEAD of `minRank` (the gate is the authority) and `recordGateExecution` on a pass; a room command that shadows a builtin runs under its own empty definition, never the builtin's gate. Migrated commands use `{ minRank: 5, gate: "<id>" }` (`adapter` is rank 7, `key` rank 8). Seven gates wire this way (`shell.exec`, `agent.run`, `adapter.enable`, `connect.manage`, `gateway.connect`, `key.manage`, `admin.destructive` — the last on `admin`, `world` and `marina-descend`). The other four are enforced **imperatively**: `agent.spawn` gates a *subcommand* (`agent spawn`, while `agent list/status/diagnose` stay rank 0 and the lifecycle subcommands `stop/restart/config/…` check builder rank 4) and is also checked by every other spawn path (`code` crew/driver/spawn, `evolve`, `demo`, `usecase`); `code.exec` is checked in `code.ts` (and the code driver/workspace paths) before the exec/mutate subcommands (the `code` command itself is rank 0 so read/inspect stay open); `role.edit` is checked by `checkRoleEdit` (`src/engine/role-guard.ts`) inside `role edit|delete|reload`, `trait delete` and `benchmark promote` (an earned default changes every agent that runs on it; the challenger's own author is always refused); `shell.exec` is additionally checked imperatively by `run raw` and `connect add … stdio` (`shellExecRefusal`, `src/engine/commands/run.ts`); `code.exec.unrestricted` is checked by `HeadlessGateApprover` (`src/coding/exec-approver.ts`), the one allowlisted bare-`checkGate` site, which refuses anything short of unsupervised competence (`test/spawn-gate-sites.test.ts`).

## Code Mode
- **Code Mode is agentic by default** (`src/engine/commands/code.ts`): entering `code` evaluates the cwd (top-level listing) and a natural-language line is a *task*, not an error — the switch `default` case routes non-subcommand input through `doCode`. `code do <task>` (or any plain line in the modal) dispatches via the session's **driver** (migration 51: `coding_sessions.agent` + `driver`). `single` (default) binds one coding agent to the session (`ensureSessionAgent` recruits-or-spawns a coder, grants it `code.exec`, persists `session.agent`) and hands it the task via `CodeSessionDriver.assignAgent` → the agent loops autonomously with the `marina_code` tool. `crew` (`code driver crew` / `code crew <goal>`) fans out implementer/reviewer/tester. The driver is the extensibility seam for future multi-agent / multi-backend dispatch — strategies slot into `doCode` without touching callers. Explicit `code read/patch/apply/run/...` subcommands remain for manual control.

## Flywheel sandbox direction
- **Flywheel sandbox direction**: the accepted Phase-6 boundary is one durable Flywheel sandbox per Marina entity. Marina owns identity, policy, approvals, Code Mode, artifacts, and audit; Flywheel owns isolated execution, persistent guest disk, hibernate/resume, and publish. M1–M4 functional slices have landed: durable reconciliation, explicit session routing without host fallback, sandbox projects with bounded patch/archive transfer, and managed services with probe/screenshot/publish. M5 production gates cover transfer integrity, network/credential brokering, durable process identity, quotas/operations, and a live cross-product matrix. Never silently fall back from requested sandbox execution to host execution or imply host/guest file coherence.
