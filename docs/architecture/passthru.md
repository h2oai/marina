# Drop-in Compatibility (Passthru) — OpenAI, Anthropic, Ollama, ACP Surfaces

**When to read this:** you are changing how external clients call *into* Marina — compat profiles and model-id aliases, the OpenAI-compatible `/v1/*` surface, the Anthropic upstream proxy (text blocks, system messages, tool calling, error codes, caching), the Ollama surface, or the ACP editor bridge. `CLAUDE.md` → "Drop-in Compatibility (Passthru)" states the invariants; this page is the full reference including the failures each rule was learned from. Memory injection into these surfaces is covered in `docs/architecture/memory.md` → "Reputation, retrieval quality, and the gateway".

## Roles and compat profiles
- **Three roles**: Marina relates to agents as (1) **participant** — agents inside worlds; (2) **consumer** — Marina calling out to upstream LLMs via the `model` channel; (3) **passthru** — external clients (editors, OpenAI SDKs) calling into Marina. This section is about role #3.
- **Compat profiles** (`src/net/adapters/compat-profiles.ts`) — registry of extra model-id aliases for OpenAI-compatible clients. Each profile declares aliases that resolve to the default `model` channel; `/v1/models` lists them (ships with one neutral `openai` profile exposing the `assistant` alias). Adding an alias is a one-line change in this file. All profiles enabled by default; override with `MARINA_COMPAT=name1,name2` or `none`.
- **Compat profiles** are self-contained — they only register passthru model-id aliases on `/v1/models` and work regardless of which world is loaded. (The `hermes`/`openclaw` migration worlds and their third-party aliases were removed in v0.4.2.)

## Source layout (2026-09-23)

`src/net/model/model-api.ts` is the entry point and the only import path other modules use — it owns authentication, per-IP rate limiting, the path dispatch table (including the `/v1/messages` glue that hands `anthropic-inbound.ts` the `runOpenaiChat` callback) and a stable re-export block, so importers never see the layout. The surfaces live in `src/net/model-api/` behind a strict import DAG rooted at `shared.ts` (headers/CORS, `authenticate`, `json`/`errorJson`, `requestTrace`, model-id ↔ channel mapping, `HttpError`, OpenAI/Ollama wire-format helpers). Above it: `models.ts` (`/v1/models` listing), `anthropic-bridge.ts` (outbound `proxyToAnthropic`, system-prompt join, auto-cache switch, stream-usage sidecar), `openai-responses-bridge.ts` (outbound OpenAI reasoning transport and encrypted tool-loop replay), `upstream.ts` (`proxyToUpstream`, provider table + fallback order, `prepareUpstreamBody`/`stripCacheControl`/`prepareLlamaBody`, `normalizeToolCallSSE`, lifecycle tracing + cost/cache metrics, the provider probe), `responses-sse.ts` (`ResponseRecord`, `formatResponseRecord`, the incremental `ResponsesSseEmitter` and the two stream adapters), `passthru.ts` (`preparePassthru`, trace/upstream hints, response-cache hooks, transcript capture), `routing.ts` (agents-mode channel routing: load balancing, conversation channels, reminders, single/open/panel/streaming routes, `rejectUnsupportedForAgents`), `verify.ts` and `ensemble.ts` (the two passthru formations; `ensemble.ts` reuses `verify.ts`'s rendering, checker resolution and repair helpers and sits above it), and the three handler modules `chat-completions.ts`, `responses.ts` (owner-scoped response index — one instance) and `ollama.ts` (`isModelApiPath`, `OLLAMA_API_PATHS`). `routing.ts` sits above `responses-sse.ts` because the streaming route writes into the emitter, while `responses.ts` sits above `routing.ts`; `upstream.ts` imports the outbound bridges (never the reverse), so `isMarinaModel` lives in `shared.ts`. No module under `model-api/` imports `model-api.ts`; the pre-existing type-only edge `passthru-context.ts → model-api.ts` (`PassthruAuthResult`) is erased at runtime and stays on the entry.

## OpenAI and Anthropic surfaces
- **Pinned defaults:** once the configured default provider is selected, its rejection or outage is returned to the caller; it never silently becomes another provider's default model. A forced passthru model with missing credentials returns `503`. The agents-mode `fallback` setting controls channel-to-upstream fallback, not substitution of a pinned upstream model.
- **Non-default model ids (2026-10-01, tightened 2026-10-05)** — `proxyToUpstream` sends an id with a configured provider's prefix (`openrouter/z-ai/…`, `openai/gpt-…`, `anthropic/claude-…`) to THAT provider ONLY, with the prefix stripped. Before this, a classifier engine on `openrouter/…` reached Anthropic first and returned its 404 on every call. Unprefixed ids and ids whose prefix is not a Marina provider (`vendor/model`) take the first-party-preferred loop with the id as sent; there an Anthropic `404` is a routing miss: the loop tries the next keyed provider and returns the 404 only when none serves the id. The routed target is always the provider that answered.
  - **The named provider's answer is final.** Success, a rejection (`400`/`413`/`415`/`422`, e.g. `logprobs` on a reasoning model), a `404`, a `429`, a `5xx` or a transport failure (`502`, or `504` on timeout) is returned to the caller with the provider's own status and body; it never falls back to another provider. The prefix is that provider's namespace: before this, an OpenRouter `429`/`5xx` on `openrouter/qwen/…` was retried on Hugging Face with the full `openrouter/…` id, which 400'd and hid OpenRouter's reason.
  - **Prefixes that cannot be another provider's id.** An aggregator prefix (`openrouter/…`, `huggingface/…`) or a local-runtime prefix with that provider unconfigured is `503` *not configured*, never sent elsewhere. A first-party vendor prefix with no key for that vendor (`openai/gpt-…` without `OPENAI_API_KEY`) is that vendor's id in an aggregator's namespace, so the loop asks only aggregators (`openrouter`, `huggingface`), never a first-party API. Default (`marina/default`) requests with no pinned `default_model` are the one class that falls back across providers, and each attempt is mapped to that provider's own default model (`getDefaultUpstreamModel`), so no provider is handed an id it does not carry.

  Tests: `test/upstream-explicit-provider.test.ts`.
- **`marina/verify:<proposer>[+<checker>]` (2026-10-03)** — the verification formation as a model id (`src/net/model-api/verify.ts`, reached from `runOpenaiChat` before any routing).
  - **Flow:** proposer draft (tools allowed) → checker review of the draft against the rules, requests and tool results (JSON verdict) → at most `MARINA_VERIFY_ROUNDS` (default 1) proposer revisions with the reviewer's note in the trailing note (after the lessons), so a revision reads the proposer's cached prefix.
  - **Plumbing:** every call goes through `proxyToUpstream`, so spend, the daily cap and lifecycle traces apply. The id travels as `body.model` (never `forceModel`), so each call takes the explicit-provider path: the named provider's answer (rejection, outage or transport failure) is final. A proposer or checker is never answered by another vendor's default model. The caller's distinct passthru identity (bound key / name-map) is stamped on the inner calls' lifecycle events.
  - **Operator pin:** in `passthru` endpoint mode with a configured `passthruModel`, `default` names the pin and any other proposer or checker id is refused with `403 model_not_allowed`; `MARINA_REPAIR_MODEL` is used only when it is the pin.
  - **Response:** sums `usage` and `x-marina-cost-usd`, and sets `x-marina-verify`.
  - **Fails open** to the draft.
  - **Write-action guard** (`guardRevision`): a revision may change text and read-only calls freely, but a state-changing tool call stays as drafted unless the verdict carries a `conflict` (`kind`, verbatim `quote`, `call`, `field`).
    - The quote must be found in the conversation.
    - Only the cited call may be added or dropped, and only the cited argument of a modified call may change.
    - No id may appear that is absent from the conversation and its tool results.
    - A guarded revision is discarded and the response says `x-marina-verify: held-write`.
  - **Output repair** (`src/repair/tool-call-repair.ts`, `MARINA_OUTPUT_REPAIR`). The final message is repaired when tools were sent and the message carries its call as fenced or bare JSON for a declared tool, or has malformed arguments. `<tool_call>` tags are already normalized upstream.
    - The repair is mechanical first, then one re-encoding shot (`MARINA_REPAIR_MODEL`, else the proposer). The shot's values must appear verbatim in the message, and a write call may use only argument names the message wrote.
    - The response says `x-marina-repair: repaired:parse|repaired:shot`.
    - Read-only: the shared tool classifier in its `guard` role (see "Read or write" under the obligations ledger).
  - **Refusals:** `stream` and `n > 1` get `unsupported_parameter`; non-upstream ids get `model_not_found`.
  - **Checker:** the default is `MARINA_VERIFY_CHECKER_MODEL`, else the proposer. Under the instrument stack the checker also sees the caller's memory context beside the lessons (`VerifyExtras.context`, 2026-10-12), so it reviews the draft against what the proposer saw — only for a distinct identity that opted into context, never for a shared or anonymous caller.
  - **Checker effort (2026-10-04):** the checker call carries the caller's effort fields (`reasoning_effort`, `reasoning`, `thinking`, top level first, then a literal `extra_body`), so a caller asking for `high` gets a `high` review. `MARINA_VERIFY_CHECKER_EFFORT=low|medium|high` sends that `reasoning_effort` instead; `off` sends none (the model's default). Provider translation (Anthropic thinking / Claude 5 adaptive effort, `omitsSamplingParams`) happens in the upstream layer, as for any passthru body; the checker never sends sampling parameters.
  - **Checker prompt caching (2026-10-04):** `checkerMessages` lays the request out append-only so its prefix is byte-identical turn over turn: the constant `CHECKER_SYSTEM`; one user message whose parts are the head (rules + tool catalogue), then one text part per conversation message (each clamped independently), then the most recent images (with their note), then the tail (lessons + the draft). For a Claude checker with `MARINA_ANTHROPIC_AUTO_CACHE` on, it marks three breakpoints itself (system, head, last conversation part), so the next turn reads the whole earlier conversation from cache; any other checker gets the same text as one string, which keeps OpenAI-style automatic prefix caching. Trade-off: lessons sit in the uncached tail (they follow the latest user message), and images sit after the cached prefix (the "most recent four" window moves).
  - **Which drafts are reviewed (2026-10-12, `MARINA_VERIFY_REVIEW`):** `consequential` (default) skips the checker for a draft whose tool calls are all read-only lookups (the shared classifier's `guard` role; an unplaced tool is a write) and labels it `x-marina-verify: skipped-read-only`; final replies and any state-changing call are reviewed. `all` reviews every draft. A lookup changes nothing and its result is in front of the proposer next turn, while each review is a full-transcript call.
  - **Checker caching caveat:** the append-only layout below keeps Anthropic breakpoints useful, but an OpenAI checker's prompt ends with the draft, so the next turn's checker prompt never contains the previous one whole and OpenAI's cache (whole earlier prompts only) does not hit across turns.
  - **Tests:** `test/model-api-verify.test.ts`. Guide: [τ²-bench](../guides/tau2.md).
- **Instrument stack (2026-10-11)** — one parsed feature set per request (`src/net/model-api/stack.ts`) instead of a prefix or header per instrument. Members: `lessons`, `obligations`, `argcheck`, `verify`, `context`, `learn`.
  - **Default (`MARINA_PASSTHRU_STACK`, default `identified`):** an identified caller — a key bound to an entity, an authorized name-map (the same distinct-identity test as context injection), or any non-internal caller under the local trust profile — gets `lessons`, `obligations` (`on`), `argcheck` (`on`, at `MARINA_ARGCHECK_TRIGGER`, default `flagged`) and `learn` without asking. Anonymous and shared callers (a plain key; the open-API sentinel outside the local profile) get nothing and are byte-identical, headers included. `all` gives every non-internal caller the default; `off` gives no one. Marina's own agents (internal token) never get the passthru stack — their loops carry the instruments through `MARINA_OBLIGATIONS` / `MARINA_ARGCHECK` / `MARINA_LESSONS_*`. A default stack does not apply on a request that routes to Marina's agents.
  - **Explicit:** `x-marina-stack: full|none|<comma list>` or the model prefix `marina/full:<model>` (combinable with the other prefixes). A list is exact for the four default members; `context` listed turns `X-Marina-Context` on, `none` turns it off, other lists leave the caller's context settings alone. A listed member the request cannot take is refused with `400 unsupported_parameter` (`context`/`learn` without an identity, `learn` with `MARINA_LESSONS_FROM_WORK=off`, `verify` on a stream, `n > 1` or a non-upstream id). `full` runs every member it can and reports the rest. An explicit stack that asks for more than `lessons` on a request routed to Marina's agents is refused.
  - **Opt-outs:** a per-instrument header wins for its instrument — `x-marina-lessons: off`, `x-marina-obligations: off`, `x-marina-argcheck: off`, `x-marina-learn: off`.
  - **Recorded:** the response's `x-marina-stack` header lists the members that ran, the source (`header`, `prefix`, `default`) and `skipped=` members of `full` with the reason. Each instrument keeps its own header (`x-marina-lessons`, `x-marina-obligations`, …).
  - **Why `argcheck` is `on` at `flagged`:** the judge sees only a call whose mechanical pass found a value nobody stated first-hand, and a nudge is one retry per call signature that never rewrites arguments; the 13–25 % false-alarm rate measured for `all-writes` is why that trigger stays opt-in.
  - **Cost:** without `tools` the ledger and the check make no call; with tools, one extraction call per new request batch, a judge call per flagged write, at most one nudge retry each. The response cache is skipped only for an instrumented request with tools.
  - Tests: `test/obligations.test.ts` ("the instrument stack").
- **`marina/verify:` composes with the stack (2026-10-11)** — the formation runs with the caller's memory context and the open obligations in the proposer's trailing note (after the lessons), the caller's own lessons with the shared pool, and the transcript capture; the ledger reads the request before the proposer, and its final-answer check and the argument check read the VERIFIED reply — a nudge re-runs the formation with the note. Before, verify plus the ledger or the check was refused.
- **Ensemble on tool-calling turns (2026-10-12)** — `src/net/model-api/ensemble.ts`. The `ensemble` stack member (`x-marina-stack: ensemble`, the request's model × `MARINA_ENSEMBLE_SIZE`, default 3) or the innermost prefix `marina/ensemble:<a>,<b>[,…]` (a 2–5 model panel) replaces the turn's single upstream call: every proposer drafts the next message against the same request and trailing note (tools included, un-streamed); identical drafts skip the checker (`unanimous`); otherwise the checker — the verify checker resolution (`MARINA_VERIFY_CHECKER_MODEL`, the earned `verify:checker` slot, else the first proposer; the pin under a passthru pin) — sees the conversation as `verify` renders it plus the numbered drafts and a note naming any strict-majority group that shares its state-changing calls, and replies `{"pick":n,"reason":…}`. ONE whole draft is returned, never a combination, so the tool loop stays the client's. A checker outage or unreadable pick fails open to the first draft of that majority group, else the first valid draft (`checker-unavailable`). Output repair runs on the picked draft as in `verify`; the obligations ledger and the argument check wrap the ensemble like a single call (a nudge re-runs it). Usage and `x-marina-cost-usd` are summed across drafts, checker and repair (each inner call records its own spend through `proxyToUpstream`); the pick verdict is a `model_request_lifecycle` event whose `routeReason` carries numbers only (`ensemble:picked:2/3:drafts=3`), and the response header `x-marina-ensemble: picked=<k>/<n>; drafts=<valid>/<n>; <label>`. A streaming request gets the picked reply re-emitted as SSE (content, then tool calls, then the finish reason). Refused with 400: `n > 1`, a panel outside 2–5 ids or with an id that is not an explicit upstream id, and a prefix on a request routed to Marina's agents. Opt-in only: never in the identified-caller default nor in `full`. `/v1/responses` takes it through `runOpenaiChat`; the Ollama routes refuse the prefix (`CHAT_ONLY_MODEL_PREFIXES`). Tests: `test/model-api-ensemble.test.ts`.
- **Ensemble with verify (2026-10-12)** — the two formations compose (`x-marina-stack: ensemble,verify`, `marina/ensemble:<a>,<b>` with the `verify` member, or `marina/verify:<p>[+<c>]` with the `ensemble` member; `runVerifyStack` in `chat-completions.ts`, `VerifyExtras.draft` in `verify.ts`). The order is fixed: (1) the ensemble drafts and its checker picks ONE whole draft (same rules and `checker-unavailable` fail-open as alone; proposers are the listed panel, else verify's resolved proposer × `MARINA_ENSEMBLE_SIZE`; the picker is verify's resolved checker); (2) verify reviews that pick exactly as it reviews a single proposer's draft; (3) a flagged pick is revised by ONE call to the proposer whose draft was picked — the ensemble is not re-run, so a bounce never pays for N more drafts and a second pick; (4) output repair runs ONCE, on verify's final message (the ensemble skips its own repair here); (5) the obligations ledger and the argument check wrap the whole formation as they wrap verify alone, and their nudge re-runs all of it. A listed panel keeps its pin and reachability rules. The response carries both `x-marina-ensemble` and `x-marina-verify`, `x-marina-stack` reports `verify,ensemble` (plus whatever else ran), the reported `model` is the listed panel id when one was given, else the `marina/verify:` id, and each formation emits its own numbers-only `model_request_lifecycle` verdict. Usage and `x-marina-cost-usd` sum every inner call once (verify adds the ensemble's summed header to its own); spend is recorded only where each upstream call leaves Marina (`proxyToUpstream`), never from the summed headers. Streaming follows verify: a listed `ensemble,verify` or an explicit `marina/verify:` with `stream: true` stays a 400 (verify reviews a complete draft); under `full` verify is reported skipped (`skipped=verify(streaming …)`) and the ensemble's pick is re-emitted as SSE. `/v1/responses` asks instrumented turns un-streamed, so both run there and the record is re-emitted as SSE if asked. Tests: `test/model-api-ensemble.test.ts` ("the ensemble with verify").
- **`/v1/responses` runs the stack (2026-10-12)** — a passthru Responses turn that carries any instrument (a `marina/…:` prefix, an instrument header, `x-marina-stack`, or the identified-caller default; `responsesInstruments` in `responses.ts`) is answered by `runOpenaiChat` with the turn's translated chat body, so every member behaves exactly as on chat completions; the completion becomes the Responses record (`previous_response_id` threading, stored tool calls) and the instruments' response headers (`x-marina-stack`, `x-marina-lessons`, `x-marina-verify`, …) ride through. The instrumented turn is asked of the upstream un-streamed so the ledger, the argument check and verify read a complete reply; a client that asked for `stream: true` receives the finished record as Responses SSE (one delta). A turn with no instrument takes the plain path, byte-identical (incremental streaming included). `responses.ts → chat-completions.ts` is the one edge between the two handler modules (`chat-completions.ts` never imports `responses.ts`). Tests: `test/obligations.test.ts` ("the instrument stack").
- **Opt-ins never drop silently (2026-10-08)** — the `marina/lessons:` / `marina/obligations:` / `marina/argcheck:` / `marina/verify:` / `marina/full:` prefixes are honored by `runOpenaiChat` (`/v1/chat/completions`, `/v1/messages`, and passthru `/v1/responses` through it). On the Ollama routes, and on a `/v1/responses` request routed to Marina's agents, they are refused with `400 unsupported_parameter` (`rejectChatOnlyPrefix`, `CHAT_ONLY_MODEL_PREFIXES` in `shared.ts`, pinned by a test), and so are the `x-marina-stack`, `x-marina-lessons`, `x-marina-obligations`, `x-marina-argcheck`, `x-marina-review` and `x-marina-learn` headers unless they say `off`/`none` (`rejectStackHeaders`, 2026-10-11 — before, those routes ignored the headers silently). The Ollama routes keep refusing: their wire formats (`/api/chat` ndjson, `/api/generate`'s single prompt) carry no tool calls for the ledger or the check to read, and an Ollama client has no way to read the `x-marina-*` result headers it would need. The ledger or argument check on a request that routes to Marina's agents (a `marina*` id outside passthru mode) is refused; lessons need no refusal there (the agent route recalls them already).
- **Obligations ledger (2026-10-05)** — `marina/obligations:<model>` (or `x-marina-obligations: on|observe` with an unchanged id; combinable with `marina/lessons:` in either order) keeps track of what a multi-step tool conversation still owes (`src/obligations/`, surface `src/net/model-api/obligations.ts`, reached from the passthru branch of `runOpenaiChat`; `/v1/messages` included). Without the opt-in (or the instrument stack, see above) nothing runs and the request is byte-identical.
  - **Extract:** each new user message is read once into explicit obligations (what, target, constraints, candidate tools from the request's own write tools) by one cheap call on `MARINA_OBLIGATIONS_MODEL`, else the request's own model (the operator's passthru pin wins). A request without `tools` is skipped (`skipped=no-tools`).
  - **Conversation key (2026-10-06):** `x-marina-session` when the client sends one — exact keying, and the recommended way: send a unique id per conversation. Without it the key is derived (`conversationKeys`), scoped by the caller (a bound name, a name-mapped agent, or a hash of the matched key — never the key): a hash of the system/developer text, the declared tool schemas and the first user message, deepened at message-count checkpoints (every non-system message up to 8, then 12, 16, 24, … 128) by a running hash over the history. `LedgerStore.resolve` carries a conversation's state from its deepest known ancestor key to its current key as a COPY, so two conversations with an identical opening share a ledger only while their histories are byte-identical and part at the first checkpoint after they diverge (the previous opening-only hash let two banking simulations share one ledger). A history the client edits or rewrites starts a fresh ledger. Ledgers live in process memory (LRU, 6 h idle TTL, at most 16,000 keys); nothing is written to the world database, and a lost ledger is rebuilt from the resent history on the next request. The argument check keys its per-conversation memo the same way.
  - **Track:** a successful state-changing call (by the classifier below in its `track` role; a generic dispatcher call by the tool it runs, see below; an error-shaped result never counts) settles an obligation when it is one of its candidate tools and its arguments share an id-like token with the target (or neither side has one); a transfer/escalation tool settles all open ones as handled. Equally plausible candidates are ambiguous and go to a judge (the decision layer's `choice` when `MARINA_DECISIONS` / `MARINA_DECISION_ENGINE` is configured, else the ledger's chat model), at most three per request.
  - **Remind (`on`):** open obligations ride as a trailing note AFTER the cache breakpoints (`proxyToUpstream` hint `trailingNote`): appended to the final user turn (a tool-result turn on Anthropic; a new user message after a `tool` message on OpenAI-compatible routes), never a mid-conversation system message, so the cached prefix and the rolling breakpoint are the same with or without it. The note is labelled a bookkeeping note and says it changes no rule (confirmations still apply).
  - **Check before the final answer (`on`, non-streaming):** a reply with no tool call while an obligation is open (and never nudged) is classified per obligation — `owed`, `waiting` (asks the user first), `declined` (refused because a rule or the requester does not allow it, an attempted action failed, or transferred: handled; a reply that calls the work impossible or unsafe on its own judgement without trying anything, when nothing shown prevents it, stays `owed`), `done`. Only `owed` ones trigger ONE retry whose trailing note quotes the draft and lists them; the model's second reply is returned as it wrote it (it may send the draft again). Each obligation is nudged at most once. A judge or retry failure returns the draft. Streams get the reminder only.
  - **Consent (2026-10-08, `MARINA_OBLIGATIONS_CONSENT=observe|on`, default `observe`):** the extractor's existing call also returns `consent` — open obligations the new request explicitly approves as the assistant last described them — recorded as `consentTurn` (no extra call). A final reply judged `waiting` on an approved obligation is a **re-ask**. `observe` only counts (`consented=` / `reasks=` in the header and log line, check `reask`); the model sees nothing new. `on` shows "approved in request N" on listed obligations and treats a re-ask as owed, so the one-time nudge names it with `CONSENT_NOTE` (act now unless something material changed; if a required detail is missing, ask only for that). The agent-loop ledger (`src/obligations/agent.ts`) marks approvals the same way in its section and end-of-run follow-up. Motivation: a requester who approves and ends in one message loses the action when the assistant asks again.
  - **Pre-write review (2026-10-08, `MARINA_OBLIGATIONS_REVIEW=off|observe|auto|on`, default `auto` since 2026-10-11; `src/obligations/review.ts`):** a non-streaming reply that carries a state-changing call (the `guard` classification) gets ONE judge call with the yes/no questions that apply — **order** (≥ 2 open obligations: would doing this now prevent another open request or change its terms?), **evidence** (does the call rely on a condition no recent tool result shows?), **requested** (only when the conversation holds requests, so never for a self-directed agent: is it an action nobody asked for, approved, or that the rules require?) and **permitted** (only when rule passages naming the call exist, `MARINA_OBLIGATIONS_REVIEW_RULE_BYTES`, default 3000: do those rules forbid it or require a step first?). At most 4 reviews per conversation, each kind named at most once. **`auto` (Phase 4, per-task selection):** at the first write it would review, the task is selected once — no requests and no rule text → out (no call); else one decision question (`SELECT_QUESTION`: costly or hard-to-undo action on someone's behalf, constrained by rules or several requests?) → `engaged` acts as `on`, `out`/`unjudged` skips the review entirely (`review-not-selected`, `review_sel=engaged|out`). The env value is a ceiling: `x-marina-review` on a request, or the agent's loop preference `review`, may only lower it (`capReviewMode`). `observe` counts (`reviews=`/`review_flags=`, labels `review-clear|review-<kinds joined by +>|review-unjudged`); `on` (ledger also `on`) retries once with a note that names each concern and invites the same call again (`reviewed-kept|reviewed-changed`). The agent-loop ledger runs the same review as a one-time refusal after the argument check (`AgentObligations.reviewWrite`). With the review off (`MARINA_OBLIGATIONS_REVIEW=off`) every path and label is unchanged.
  - **Learn:** a nudge that led to a tool call becomes one `tools` outcome (`obligations:passthru`, general wording, the obligation text only as the leak check's `privateContext`).
  - **Spend:** every ledger call goes through `proxyToUpstream` (or the metered decision provider), so it is recorded and refused at the daily cap; a refused call degrades the ledger to off for that step. `x-marina-obligations` reports counters (`on;open=1;satisfied=2;declined=0;nudges=1;extract=ok;check=nudged-acted`), `x-marina-obligations-cost-usd` the ledger's own spend on the request including a discarded draft; one `model-api` log line per request carries the same counters, never content.
  - **Agent loops: `observe` is free (2026-10-13, `MARINA_OBLIGATIONS_OBSERVE_SAMPLE`, default 0):** the agent-loop ledger (`AgentObligations`, `MARINA_OBLIGATIONS`, `observe` by default outside Code Mode) shows nothing to the model in `observe`, so by default it makes no model call there: requests are queued (their text, clamped, still reaches the argument check's judge as stated lines), tool calls are counted, and extraction, ambiguous-match judging and the pre-write review are skipped (`unsampled=` in the summary). A fraction above 0 samples refreshes and reviews that then run exactly as in `on` without showing anything — for measuring what `on` would do. `on` is unchanged; the passthru's `x-marina-obligations: observe` is an explicit opt-in and still extracts.

- **Argument check before writes (2026-10-06)** — `marina/argcheck:<model>` (or `x-marina-argcheck: on|observe` with an unchanged id; combinable with `marina/obligations:` and `marina/lessons:` in any order) checks each state-changing call in a reply against what the conversation established (`src/obligations/argcheck.ts`, surface `src/net/model-api/argcheck.ts`, run after the obligations step). Without the opt-in (or the instrument stack) nothing runs and the request is byte-identical.
  - **Read or write (2026-10-06, `src/obligations/tool-effect.ts`, one classifier for the ledger, the check and the verifier's write-action guard):** a declared MCP hint wins (`readOnlyHint: true` read; `readOnlyHint: false` or `destructiveHint: true` write). A generic HTTP request tool — a declared method parameter beside a url/path parameter — is placed by its methods, not its name: it is a write unless every declared method is `GET`/`HEAD`/`OPTIONS`, and each call is placed by the method it actually uses (`readOnlyCall`), so a `POST` through a tool named `api_fetch` is checked as a write and a `GET` through `http_request` is a read (2026-10-11). Otherwise a write verb leading the name or the description (`update_`, `cancel_`, "Change the email…") is a write; a read verb leading the name (`get_`, `list_`, `search_`, `find_`, `lookup_`, `read_`, `check_`, `view_`, `describe_`, …, after up to two namespace words such as `KB_search_bm25`, or camelCase) is a read; a read verb leading the description ("Search the knowledge base…", "Returns the…") is a read when no write word appears in it. An ambiguous verb (`unlock`, `give`, `grant`, `open`, `run`, `execute`, `call`, …) is a read only when the description says the tool gives access to or reveals something and names no write word and no user-owned state (`user`, `customer`, `account`, `card`, `order`, …): "unlock a tool you have access to" is a read, "unlock the user's card" a write. Anything else is a write. The **`guard`** role (argument check, write-action guard) stops there — missing a write would skip its check, while a lookup counted as a write costs only a free mechanical pass. The **`track`** role (obligations ledger) also takes weaker read evidence — the description's read words (`search`, `explore`, `look up`, …) outnumber its write words, or the only parameter is a free-text search (`query`, `q`, `question`, …; limits like `k` aside) — because there a lookup counted as a write is the costly error: the extractor offers it as a way to carry a request out and its calls settle obligations they never fulfilled. A lone `command`/`script`/`sql` parameter is read evidence in neither role: only the description can say a shell explores. No product-specific tool names.
  - **Which calls:** the classifier above in its `guard` role; at most four write calls per reply.
  - **Dispatcher calls (2026-10-06, `src/obligations/tool-call.ts`, shared by the ledger and the check on both surfaces):** a call whose arguments are exactly a name key (`tool`, `tool_name`, `*_tool_name`, `action`, `name`, `function`, `method`, `operation`, …) holding an identifier and an arguments key (`arguments`, `args`, `params`, `parameters`, `input`, `kwargs`, `payload`) holding an object or a JSON-object string is classified by the INNER tool with the same rule, so a dispatched lookup is not a write. When the tool declares its parameters, both keys must be declared and a name `enum` must contain the inner name. The shape is detected from the arguments and schema, never from a tool's name. Malformed inner arguments, a non-identifier or unknown inner name, or a third key fall back to the outer tool; an outer tool that is already read-only (declared or by name) stays read-only. The check reads the inner arguments (the inner tool's name is not a checked value), and the ledger matches an obligation's candidate tools against the outer and the inner name. Agent loops skip the check for a `mutate`/`consequential` dispatcher call whose inner tool is a lookup. Streams, upstream errors and requests without `tools` pass through with the counters header.
  - **Mechanical pass (free):** every id, amount, date and short option in the arguments is looked up in the conversation. Amounts are compared as numbers (`$1,250.50` = `1250.5`), dates as ISO days (`May 3, 2026` = `2026-05-03`), ids and options as whole tokens. A value in a user message or a tool result is first-hand; one only in the assistant's own text or the system/policy text is `weak`; one nowhere is missing. Tool-call arguments are never evidence. Free text (`reason`, `note`, long strings), a program the model writes itself (`command`, `cmd`, `script`, `sql` — e.g. a `shell` retrieval tool, which the `guard` role keeps as a write), booleans and integers up to 10 are not checked. A URL (`https://…`, e.g. a generic HTTP tool's `url`) is built by the model from API docs, so only the record ids inside it are checked (path segments and query values with a digit; no version marker such as `v2.1`, no range or method syntax such as `A1:C2:clear`) (2026-10-13; before, every such write was flagged on its URL and sent to the judge). A call whose values are all first-hand passes with no model call. A write to the caller's OWN record (2026-10-13, `writesOwnRecord` in `tool-effect.ts`: a record-kind word — memory, note, journal, reflection, skill, … — among the name's first three words, or a declared description saying so; a description naming someone else's state such as `customer`/`account`/`order` never counts) leaves the writer's own descriptors unchecked (`OWN_RECORD_KEYS`: operation/action, tags, labels, importance, priority, tier, category, type/note type, kind, confidence, title, name, its claim, an idempotency key), since they are chosen, never quoted; its ids, spaces and targets are still checked, and with nothing left to check it is not judged under `all-writes` either. Before, a resident's memory write was flagged on its own `tags[0] = task-1` or `importance = medium` and refused once per call.
  - **Judge trigger (`MARINA_ARGCHECK_TRIGGER`, read by both surfaces):** `flagged` (default) asks the judge only about a call the mechanical pass flagged; `all-writes` asks about every write call, with the mechanical findings shown as a free pre-signal. The default comes from offline replays of the judge: in-sample over τ³-Banking write calls `all-writes` caught more wrong-argument calls but judged roughly a quarter of correct writes unsupported; a pre-registered held-out replay (other τ² banking, airline and telecom runs, dispatcher lookups excluded) still put it at about 13 %, above the 10 % at which a nudge on correct writes becomes a risk, while `flagged` stayed near 2–5 %.
  - **Judge:** one `noul` question, "is every argument the value the user meant and the conversation supports?" (`ARGCHECK_QUESTION`, verdict by `decideArgcheck` in `src/decisions/policy.ts`: one cut at 0.5) on the decision layer when configured, else one JSON answer from `MARINA_ARGCHECK_MODEL` (then `MARINA_OBLIGATIONS_MODEL`, then the request's model). Its state (`judgeState`) aims at "a real value, but not the one the user meant": each checked value with where it appears (user / tool / assistant only / instructions only / not found) and up to eight OTHER values of its kind the user or a tool gave (the same argument name in a tool result, the same id shape, the user's amounts and dates — e.g. every account id a lookup returned); the first and the latest six user messages; optionally **rule passages** (`rulePassages`, opt-in with `MARINA_ARGCHECK_RULE_BYTES`, default 0; the held-out replay used 3,000): up to that many UTF-8 bytes of the system text and tool results (the documents the assistant read), split into markdown sections or paragraphs, prose only (a record listing is not a rule), each naming the tool's exact name (for a dispatcher, the inner tool) or one of its action words, ranked by exact name, then idf-weighted action words, then argument names, a document read twice counted once, in conversation order, and framed as untrusted reference data (`formatUntrustedContext`), never instructions, with one added system sentence (a passage that does not clearly govern the call is no reason to doubt it) — off by default because in a pre-registered held-out replay they did not raise recall net of false alarms; passages that mention the arguments' names or values (tool results, user messages, instructions; rarer words weigh more, 3,000 characters; a paragraph already among the rule passages is not repeated); the latest four tool results; and, when the obligations ledger runs too, its stated requests and their constraints. It answers unsupported only for a specific conflict (a value the user or a tool points away from, a rule shown that gives another value, a value found nowhere); a value it cannot verify either way counts as supported. The chat judge may name the argument it doubts; the name is kept only if it is one of the call's argument names, and only the name reaches the nudge.
  - **Nudge (`on`):** an unsupported call gets ONE retry whose trailing note names the flagged values and why (not found / only in the assistant's or the instructions' text), or, for a call with no flagged value (`all-writes`), the doubted argument's name, and asks the model to check them against the request; the note never proposes a value and never lists the alternatives. It addresses "the requester", never "the user" (2026-10-13): an autonomous resident's request may come from another agent, a task or its own goal. The second reply is returned as the model wrote it. Each call signature (tool name + canonical arguments) is nudged at most once per conversation, so the same call issued again passes (`check=repeat`). With the obligations ledger on, its reminder stays in the retry's trailing note.
  - **Failure:** a judge outage or unparseable answer lets the call through (`check=unjudged`); a failed retry returns the draft. `observe` judges and logs but never retries.

## Internal agents always passthru (2026-09-22)

Marina's own runtime agents (room / crew / coding agents on `marina/default`) call the self-proxy `/v1/chat/completions` with the internal model token (`auth.internal === true`) and `tools`. They are **consumers** of the upstream, never participants of the agents/open/panel routes — so `isInternalCaller(auth)` in `model-api.ts` sends them down the passthru branch in EVERY endpoint mode (`runOpenaiChat`, `handleResponsesCreate`, the Ollama handlers; `/v1/messages` reaches `runOpenaiChat` and is covered). Found on a fresh install: the default mode is `agents`, so an internal agent's first turn hit `rejectUnsupportedForAgents` → `400 unsupported_parameter: tools` until an operator switched the endpoint to passthru (before the tool-calling review, agents mode silently dropped the tools instead — equally broken, and the request would have been routed to another agent on the `model` channel). Routing decision, auth × mode → route:

| caller (auth) | `passthru` | `agents` / `open` / `panel` |
|---|---|---|
| internal model token | upstream proxy (`routeKind: passthru`) | **upstream proxy** (`routeKind: passthru`, `routeReason: "internal"`) |
| bound / plain / multi-tenant key, open dev mode | upstream proxy (`routeKind: passthru`) | in-world agents; `tools`/`n`/`response_format` → `400 unsupported_parameter`; 503 + `fallback` → upstream (`routeKind: fallback`) |

Internal callers still pass through `preparePassthru`, so identity, injection and receipts apply exactly as for passthru (an internal agent sends no `X-Marina-Agent`/bound key, so it gets a plain proxy). The `passthruModel` pin applies to them the way it applies to the fallback route. Test: `test/internal-agent-routing.test.ts`.

## Cache breakpoints (2026-09-22)

Under `MARINA_ANTHROPIC_AUTO_CACHE`, `placeCacheBreakpoints` (`src/net/adapters/anthropic-tools.ts`) lays out `cache_control: ephemeral` as **last STABLE system block → last system block → last tool**, within Anthropic's four-breakpoint limit (markers the client already set count against it) and never on a block that already has one. The stable block is the one before a volatile last system block when the caller says it has one (`injectedSystemTail` hint from `proxyToUpstream` → `proxyToAnthropic` → `buildAnthropicRequest`), else the last block; the passthru's own injections no longer use it (see below). When the client placed its own markers (pi-ai `cacheControlFormat: "anthropic"`, an Anthropic SDK on `/v1/messages`) every marker is preserved and the proxy adds ONLY the stable-block breakpoint, and only if that block has none — a native body whose last system block is already marked is forwarded untouched. Tests: `test/cache-breakpoints.test.ts`.

**Per-request injections trail the breakpoints (2026-10-06).** Everything the passthru adds per request — the memory addendum (relevance-gated, grows as notes accrue), opt-in `marina/lessons:` lessons, the obligations reminder and the obligations/argcheck nudges, and `marina/verify`'s proposer lessons and reviewer note — is ONE trailing note (`passthruUpstreamHints` → `proxyToUpstream` hint `trailingNote`), appended to the final user turn AFTER the cache breakpoints are placed: a trailing text block of that turn on Anthropic (native `/v1/messages` bodies included), appended to the last user message or sent as a new user message after a `tool`/assistant message on OpenAI-compatible routes, appended to the prompt on `/api/generate`. The caller's system prompt, tools and every earlier message are forwarded byte-identical turn after turn, so the previous turn's rolling breakpoint is read from cache whatever was injected. Before, the addendum was a system block right after the caller's prompt: the stable-block breakpoint kept the system prompt cached, but the whole conversation after it was rewritten whenever the addendum changed — a τ³ run with lessons recalled from each turn's latest user message saw cache-read share fall from 0.96 to 0.89 and cache writes rise about fourfold per call. Lessons are also recalled for the conversation's OPENING user request (`lessonQuery`), so one conversation is served the same set on every turn and it changes only when the lesson pool does; memory stays relevance-gated on the latest turn (it is in the uncached tail, so that costs nothing). The response cache keys on the request with its note (`effectiveBody`), so different memory never shares an entry. A request with nothing opted in (an anonymous or shared caller, or `x-marina-stack: none`) is forwarded byte-identical. Tests: `test/passthru-prefix-stability.test.ts`.

**Sticky trailing notes on OpenAI-compatible upstreams (2026-10-12).** OpenAI's automatic prompt cache reuses a WHOLE earlier prompt: a cache hit is the previous request's full input, never a shorter shared prefix. A trailing note is at the end of turn N's request and absent from the client's history on turn N+1, so turn N's prompt was never a prefix of turn N+1's and every instrumented turn missed the cache (the Anthropic breakpoints above are unaffected: they cache the prefix before the note). `src/net/model-api/sticky-notes.ts` remembers each note sent under a hash chain of the client messages it followed, scoped to the caller (`noteScopeFor`: hashed credential, bound name, `X-Marina-Agent`), and re-inserts it at the same place with the same bytes on every later turn (into the final user message when it was appended there, else as its own user message); this turn's note still goes last. A remembered note is never re-inserted at the final position (a nudge or a retry of the same history replaces it), and a note identical to the latest one already in the history is not repeated. The upstream request of turn N is then an exact prefix of turn N+1's, for chat completions, `/v1/responses` (through the chat core) and the `marina/verify:` / ensemble proposers. Memory is in process, bounded (4096 notes) and expires after two hours; a miss only means no re-insertion. Applied on OpenAI-compatible dispatch (OpenAI, its Responses bridge, OpenRouter, local runtimes); never to Claude models (the Anthropic route, or `anthropic/*` through OpenRouter), which cache at breakpoints placed before the note. `MARINA_PASSTHRU_STICKY_NOTES=off` restores the fresh trailing note. `/v1/responses` forwards the caller's `prompt_cache_key` / `prompt_cache_retention`; side calls (ledger, argument-check judge, verify checker) never carry them. Tests: `test/passthru-stack-cache.test.ts`.

**Rolling conversation breakpoint (2026-10-03).** System and tool breakpoints alone leave the conversation uncached: in a multi-turn tool loop (Code Mode, crews, benchmark harnesses) the history grows every turn and was re-billed at full input price. On the translated path (`buildAnthropicRequest` → `placeCacheBreakpoints({ rollingMessages: true, model })`) auto-cache adds a fourth kind: a breakpoint on the last markable block (`text` with content, `image`, `document`, `tool_use`, `tool_result`; never `thinking`) of the latest message, a string content becoming one text block. Each turn writes only the new tail and reads everything before it (the previous turn's breakpoint is within Anthropic's 20-block lookback unless one turn appends more). It is placed only when the client set no marker anywhere (pi-ai's own rolling marker wins), only within the four-breakpoint limit (stable system + last system + last tool + rolling = 4 at most), and only when the estimated prefix (`estimatePrefixTokens`, serialized length / 4) reaches `minCacheableTokens(model)` — 512 on Opus 5.x/Fable/Mythos, 1024 on Sonnet and Opus 4.0/4.1/4.8 and unknown ids, 2048 on Opus 4.7/Haiku 3.5, 4096 on Opus 4.5/4.6/Haiku 4.5. Native `/v1/messages` bodies keep their messages exactly as sent (system/tool placement is unchanged there). Every write costs 1.25× on the newly written tail, so a one-shot request pays that premium on its messages once — the reason auto-cache stays off by default outside the `local` profile.

**OpenRouter `anthropic/*`.** `prepareUpstreamBody` used to strip `cache_control` for every OpenAI-compatible provider, so Claude via OpenRouter (the route most benchmark runs use) never cached at all — not even a client's own markers. OpenRouter forwards `cache_control` on content parts to Anthropic, so `honorsCacheControl(provider, model)` (OpenRouter + `anthropic/` id) now keeps the client's markers, and under auto-cache with none present `placeOpenAICacheBreakpoints` adds them in the OpenAI shape: the last stable leading system message, the memory addendum (`injectedSystemTail`, passed through `prepareUpstreamBody`'s `cache` argument), and the rolling breakpoint on the latest message's last text part (role `tool` included — OpenRouter honors it there) — at most three. Every other upstream (OpenAI, Gemini or any non-Anthropic id on OpenRouter, local runtimes) is still stripped; OpenAI's automatic prefix caching and Gemini's implicit caching need no markers. A related routing fix: an explicit `anthropic/<id>` request now reaches Anthropic with the bare id (`proxyToUpstream` passes the resolved model into the body), instead of 404ing there and silently falling back to OpenRouter. Tests: `test/rolling-cache-breakpoints.test.ts`.

## Cost and cache headers (2026-09-22)

Every proxied reply (passthru, internal, fallback) carries `x-marina-upstream-model` = the served `provider/model` (the lifecycle `target`; set before the body, so streams have it too). Non-streaming replies add `x-marina-cache-read-tokens`, `x-marina-cache-write-tokens` and `x-marina-cost-usd` (the tokens of a stream ride its final SSE `usage` chunk and the lifecycle event instead). Cost comes from the upstream's own `usage.cost` when it reports one (OpenRouter), else from pi-ai's built-in catalog (`upstreamCostUsd`: `builtinModels().getModel(provider, id)` + `calculateCost` over uncached input / output / cache-read / cache-write; OpenAI-shaped `prompt_tokens` includes the cached share, so it is subtracted first) — undefined, never a fabricated $0, for unlisted or local models. It lands on the lifecycle `completed` event as `costUsd`, so agents on the synthesized `marina/default` model (which has no price of its own) are priced by what actually served them. Usage bodies carry `prompt_tokens_details.cache_creation_tokens` (extension) and, with the same value, `cache_write_tokens` — the name pi-ai's OpenAI-completions client reads — so an agent's `cacheWriteTokens` is no longer always 0. Streamed lifecycle `completed` events are populated from the final SSE usage chunk (`stream_options.include_usage` for OpenAI-shaped upstreams; the Anthropic translator reports `message_start`/`message_delta` usage through an `onUsage` side channel even when the client did not ask for usage in the stream).

## Usage-limited direct routes (2026-10-14)

A first-party key can hit its ACCOUNT's usage limit while the same model is still available elsewhere: Anthropic answers `400 invalid_request_error` "You have reached your specified workspace API usage limits. You will regain access on 2026-11-01 at 00:00 UTC." (or "credit balance is too low"), OpenAI `429 insufficient_quota`, OpenRouter `402`. That is a limit of the ROUTE (provider + key), not of the model and not of Marina's own daily spend cap. `src/net/model/route-health.ts` holds the one shared mechanism, used by the `/v1` proxy and the agent loop:

- **Classification** — `classifyUpstreamRefusal(message, status)` → `usage-limit` (with `resetAt` parsed from the message when it names one), `auth` (the provider-auth park keeps it), `rate-limit` (transient backoff, unchanged) or `other`. Marina's own cap (`spend_cap_reached`, `run_budget_exhausted`) is never a route limit.
- **Route health** — a process-wide registry, persisted in core memory (owner `route:health`, attached at engine boot) so a restart does not hammer the limited route. A limited route is not called until its reset, or — when the provider named none — a re-probe after 15 min doubling to 2 h. When that time is up, the NEXT real call is the re-probe (one caller at a time, `routeChoice` → `probe`; a refused call is not billed); success restores the direct route (`noteRouteOk`).
- **Same-model fallback** — while the direct route is limited, the SAME model is served via OpenRouter when `OPENROUTER_API_KEY` is set (env or stored key) and OpenRouter's live catalog lists the mapped id (`openRouterSameModel` in `src/agent/provider-cost.ts`, the catalog fetch already used for pricing): `anthropic` + `claude-opus-5-5` → `anthropic/claude-opus-5-5`, else `anthropic/claude-opus-5.5` (dash → dot version, the same mapping `defaultModelPrice` uses); vendor namespaces `openai`, `google`, `x-ai`, `mistralai`, `deepseek`. No date or tier is dropped — an unlisted id has no fallback, so a different model is never substituted. `MARINA_PROVIDER_FALLBACK=off` disables it.
- **Labelling** — the routed lifecycle target (and `servedBy`, `x-marina-upstream-model`) is `openrouter/<id>`, never the direct provider; `x-marina-route: via=openrouter; anthropic:direct=usage-limit; until=<iso>` says why; spend is recorded at OpenRouter's price (its `usage.cost`, else the list price). With no same-model route, a request on a route still inside its limit gets `429 route_usage_limit` naming the route and reset ("Anthropic API (direct key) usage limit until 2026-11-01 00:00 UTC — no other route serves anthropic/claude-opus-5-5") instead of another call to the limited key.
- **Readiness** — a `provider-routes` check (degraded) and `readiness providers` list each limited route — `anthropic (direct key): usage limit until 2026-11-01 00:00 UTC; anthropic models served via openrouter` — separately from the daily spend cap. The provider probe always calls the direct route (it is a re-probe) and reports a fallback-served probe as the route limit, not a pass.

Covered: every `proxyToUpstream` path (configured default, explicit `provider/model`, the fallback loop), and the agent loop's own turns plus its compaction summarizer, repair shot and obligations calls. Not covered (they build their own clients): the arena/forecast `modelComplete` helper and benchmark runners — out of scope by design. Tests: `test/route-fallback.test.ts`, `test/agent-route-fallback.test.ts`.

- **Ollama surface** (same file) — `/api/tags`, `/api/chat`, `/api/generate` for Ollama-compatible clients.

## OpenAI reasoning transport

The shared outbound proxy uses `openai-responses-bridge.ts` for GPT-6.1 Sol/GPT-6 Astra and
reasoning tool requests on the other GPT-5/GPT-6 and o-series models. It uses the direct OpenAI
key and retains normal routing, tracing and spend settlement. Non-function tools and unsupported
translations fail before a provider request. Reasoning effort is preserved; incompatible sampling
controls are omitted. Function schemas retain Chat's non-strict default unless explicitly strict.
See [OpenAI's Responses migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses)
and [GPT-6.1 Sol's API contract](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

Upstream requests use `store:false` and preserve encrypted reasoning items. Responses clients
can replay returned `reasoning` items or use the owner-scoped `previous_response_id`. Structured
conversation prefixes retain tool calls, results and reasoning across multiple turns without
copying the whole prefix into every record; the combined request still obeys the body-size limit.
Chat clients must replay the assistant's `marina_reasoning` field or its opaque `reasoning_details`
entries (`format: marina-openai-responses-v1`); Marina's native pi-ai adapter retains the latter.
Encrypted reasoning is never rendered into the conversation's plain-text memory projection.

Streaming translates text and tool deltas incrementally and propagates cancellation. A stream
without a terminal upstream response fails; token-limit termination is reported as `incomplete`.
Provider usage, including cached input, remains available to the accounting path even when the
caller does not request an SSE usage chunk.

## Responses API streaming (2026-09-22)

`/v1/responses` with `stream: true` is incremental on both paths. Passthru consumes the upstream chat-completions SSE (`stream_options.include_usage`) and re-emits `response.created → response.in_progress → output_item.added(message) → content_part.added → output_text.delta… → [per tool call] output_item.added(function_call) → function_call_arguments.delta… → output_text.done / function_call_arguments.done → output_item.done → response.completed` with a running `sequence_number`; agents mode streams `model_response_chunk` events the same way. `formatResponseRecord` is the single source for the `response.completed` payload and `GET /v1/responses/:id`, so streamed and non-streamed bodies are identical. A mid-stream upstream failure emits `response.failed` (`error.code: "upstream_error"`) and stores nothing; the response cache is bypassed for streams.

## Responses API tools (2026-09-22)

`src/net/model/responses-tools.ts` is the single translation point between the Responses shapes and chat-completions on the passthru path — request: flat `tools[{type:"function", name, description, parameters, strict?}]` → `tools[{type:"function", function:{…}}]`, `tool_choice` `auto|none|required|{type:"function", name}` → `auto|none|required|{type:"function", function:{name}}`, `parallel_tool_calls` passthrough; `input` items `function_call` → `assistant.tool_calls` (consecutive calls merge into one assistant message) and `function_call_output` → `role:"tool"` (`responsesInputToMessages`, which also owns the text/`input_text` mapping and the plain-text rendering the conversation channel stores). Reply: chat `tool_calls` → `function_call` output items with `call_id` = the upstream id verbatim (`chatToolCallsToResponses`, consumed by `extractResponseTextAndUsage`); streamed `delta.tool_calls` fragments feed `ResponsesSseEmitter.toolCallDelta` unchanged. `translateResponsesTools` runs in `handleResponsesCreate` before `runResponsesPassthru`, so a hosted tool type (`web_search`, `file_search`, `computer_use_preview`, `code_interpreter`, …) is `400 unsupported_parameter` with `param: "tools[i].type"` before any upstream call — never a silent drop; `ResponsesRequestError` covers malformed values (a nameless function tool, a result without `call_id`). Because `proxyToAnthropic` already translates chat tools to Anthropic `tools`/`tool_use`/`tool_result`, a Responses client with tools works end-to-end against an Anthropic upstream (`test/responses-tools.test.ts`). **Tool loop over server-side state**: a `previous_response_id` continuation replays its owner-scoped structured history, including all prior tool calls/results and encrypted reasoning. History uses immutable linked turns and is bounded by the request-size limit before calling the provider. Older records without structured history retain the `restorePriorToolCalls` compatibility path. Agents mode keeps refusing `tools` via `rejectUnsupportedForAgents` (`param: "tools"`).

## Image content parts (2026-10-03)

Images pass through every passthru translation, and anything that can't be forwarded is refused, never dropped (`test/multimodal-passthru.test.ts`).
- **OpenAI-compatible upstreams** (OpenAI, Google's OpenAI-compatible endpoint, OpenRouter, Groq, local servers) receive chat `image_url` parts unchanged; the OpenAI Responses bridge translates them to `input_image`. `stripCacheControl` keeps image content.
- **Anthropic:** `image_url` and `input_image` parts become image blocks (a `data:` URL becomes base64, http(s) becomes `url`), including images inside `role:"tool"` results, which Anthropic `tool_result` accepts. Any other non-text part, or an image without a URL, is `400 unsupported_parameter`.
- **Responses:** `responsesInputToMessages` turns `input_image` parts (an http(s) or `data:` URL, `detail` kept) into chat `image_url` parts. Text-only content stays a plain string. `input_file`, `input_audio` and images by `file_id` are `400 unsupported_parameter`. The conversation channel's text rendering appends `[N images]`.
- **Inbound `/v1/messages` (2026-10-15):** `translateMessages` (`src/net/adapters/anthropic-inbound.ts`) turns `image` blocks into `image_url` parts (a `base64` source becomes a `data:` URL for png/jpeg/gif/webp, a `url` source passes as is); the user message's content becomes a parts array. An OpenAI `tool` message cannot carry images, so a `tool_result`'s images follow the tool messages in one user message (`Attached image(s) from tool result:` + the parts, then the turn's own content), and the tool text is `(see attached image)` when there was none. `document` blocks, other image source kinds (`file`, …) and other media types are refused with `400 invalid_request_error` naming the block (`messages[i].content[j]`), never dropped. A native Anthropic upstream still receives the original body verbatim.
- **Inbound Ollama (2026-10-15):** `messages[].images` on `/api/chat` and `images` on `/api/generate` (bare base64) are checked by content (PNG/JPEG/GIF/WebP) and against `MARINA_VISION_MAX_BYTES` in `validateOllamaRequest`, then become `image_url` data-URL parts on that message (`ollamaMessageToOpenai`) on the passthru route. Anything else is `400 unsupported_parameter`; a request routed to Marina's agents (which hear text) refuses images the same way. `/api/show` keeps advertising `completion` only.

## Audio endpoints (2026-10-15)

`src/net/api/audio-api.ts`, dispatched from `model-api.ts` before `/v1/media` and authenticated exactly like every other `/v1` route (`MODEL_API_KEYS`, run keys, the internal token; `MARINA_OPEN_API` for development). Both endpoints run Marina's single audio path (`src/engine/media/audio.ts`) as the authenticated caller (`resolveCaller`, the `/v1/media` identity rule: a `secret:entity` key is its entity, a Marina session token its entity, the internal token or a multi-tenant operator key `system`), so per-entity caps (`MAX_TRANSCRIPTION_JOBS_PER_DAY`, `MAX_SPEECH_JOBS_PER_DAY`), the daily spend cap (`429 spend_cap_reached`) and the `media_jobs` row belong to that caller. They are compute endpoints: nothing is stored as an asset. The job id is returned in `x-marina-media-job`, the recorded price in `x-marina-cost-usd`.

- **`POST /v1/audio/transcriptions`** — `multipart/form-data`: `file`, `model`, `language` or `languages[]` (not both), `prompt`, `temperature` (0–1), `response_format` `json` (default; `{ text, languages?: [{code}], usage?: { type: "duration", seconds } }`), `text`, `verbose_json` (`task`, `language`, `duration`, `text`, `segments`), `srt`/`vtt` (built from timed segments; a model that returned none is `400`), `timestamp_granularities[]=segment`. Uploads are held to min(`MARINA_AUDIO_MAX_BYTES`, `MARINA_MAX_UPLOAD_BYTES`) (`413 payload_too_large`). Long audio and video are split and merged exactly as for the `audio` command.
- **`POST /v1/audio/speech`** — JSON: `model`, `input`, `voice` (a name or `{ id }`), `response_format` (`mp3` default, `opus`, `aac`, `flac`, `wav`, `pcm`), `speed` (0.25–4), `instructions`, `stream_format: "audio"`. The reply is the whole audio file with its `Content-Type`.
- **Models.** A bare OpenAI audio id (`gpt-transcribe`, `whisper-1`, `gpt-4o-mini-tts`, `tts-1`, …) is OpenAI's; anything else must name its provider as `<provider>/<model>` with `<PROVIDER>_AUDIO_BASE_URL` configured, else `404 model_not_found`.
- **Never dropped.** Any other field (`include[]`, `chunking_strategy`, `keywords[]`, `known_speaker_*`, `seed`, …), `stream=true`, word timestamps and `stream_format: "sse"` are `400 unsupported_parameter` naming the parameter. A provider refusal is `400 invalid_request_error` with the provider's message; an outage `502 upstream_error`.
- **`/v1/responses` `input_audio`** stays `400 unsupported_parameter` (the chat path has no audio input to route it to); transcribe first.

Tests: `test/media-audio.test.ts` ("/v1/audio endpoints"), `test/media-audio-providers.test.ts`.
