# Drop-in Compatibility (Passthru) — OpenAI, Anthropic, Ollama, ACP Surfaces

**When to read this:** you are changing how external clients call *into* Marina — compat profiles and model-id aliases, the OpenAI-compatible `/v1/*` surface, the Anthropic upstream proxy (text blocks, system messages, tool calling, error codes, caching), the Ollama surface, or the ACP editor bridge. `CLAUDE.md` → "Drop-in Compatibility (Passthru)" states the invariants; this page is the full reference including the failures each rule was learned from. Memory injection into these surfaces is covered in `docs/architecture/memory.md` → "Reputation, retrieval quality, and the gateway".

## Roles and compat profiles
- **Three roles**: Marina relates to agents as (1) **participant** — agents inside worlds; (2) **consumer** — Marina calling out to upstream LLMs via the `model` channel; (3) **passthru** — external clients (editors, OpenAI SDKs) calling into Marina. This section is about role #3.
- **Compat profiles** (`src/net/compat-profiles.ts`) — registry of extra model-id aliases for OpenAI-compatible clients. Each profile declares aliases that resolve to the default `model` channel; `/v1/models` lists them (ships with one neutral `openai` profile exposing the `assistant` alias). Adding an alias is a one-line change in this file. All profiles enabled by default; override with `MARINA_COMPAT=name1,name2` or `none`.
- **Compat profiles** are self-contained — they only register passthru model-id aliases on `/v1/models` and work regardless of which world is loaded. (The `hermes`/`openclaw` migration worlds and their third-party aliases were removed in v0.4.2.)

## Source layout (2026-09-23)

`src/net/model-api.ts` is the entry point and the only import path other modules use — it owns authentication, per-IP rate limiting, the path dispatch table (including the `/v1/messages` glue that hands `anthropic-inbound.ts` the `runOpenaiChat` callback) and a stable re-export block, so importers never see the layout. The surfaces live in `src/net/model-api/` behind a strict import DAG rooted at `shared.ts` (headers/CORS, `authenticate`, `json`/`errorJson`, `requestTrace`, model-id ↔ channel mapping, `HttpError`, OpenAI/Ollama wire-format helpers). Above it: `models.ts` (`/v1/models` listing), `anthropic-bridge.ts` (outbound `proxyToAnthropic`, system-prompt join, auto-cache switch, stream-usage sidecar), `upstream.ts` (`proxyToUpstream`, provider table + fallback order, `prepareUpstreamBody`/`stripCacheControl`/`prepareLlamaBody`, `normalizeToolCallSSE`, lifecycle tracing + cost/cache metrics, the provider probe), `responses-sse.ts` (`ResponseRecord`, `formatResponseRecord`, the incremental `ResponsesSseEmitter` and the two stream adapters), `passthru.ts` (`preparePassthru`, trace/upstream hints, response-cache hooks, transcript capture), `routing.ts` (agents-mode channel routing: load balancing, conversation channels, reminders, single/open/panel/streaming routes, `rejectUnsupportedForAgents`), and the three handler modules `chat-completions.ts`, `responses.ts` (owner-scoped response index — one instance) and `ollama.ts` (`isModelApiPath`, `OLLAMA_API_PATHS`). `routing.ts` sits above `responses-sse.ts` because the streaming route writes into the emitter, while `responses.ts` sits above `routing.ts`; `upstream.ts` imports `anthropic-bridge.ts` (never the reverse), so `isMarinaModel` lives in `shared.ts`. No module under `model-api/` imports `model-api.ts`; the pre-existing type-only edge `passthru-context.ts → model-api.ts` (`PassthruAuthResult`) is erased at runtime and stays on the entry.

## OpenAI and Anthropic surfaces
- **Pinned defaults:** once the configured default provider is selected, its rejection or outage is returned to the caller; it never silently becomes another provider's default model. A forced passthru model with missing credentials returns `503`. The agents-mode `fallback` setting controls channel-to-upstream fallback, not substitution of a pinned upstream model.
- **Non-default model ids (2026-10-01, tightened 2026-10-05)** — `proxyToUpstream` sends an id with a configured provider's prefix (`openrouter/z-ai/…`, `openai/gpt-…`, `anthropic/claude-…`) to THAT provider ONLY, with the prefix stripped. Before this, a classifier engine on `openrouter/…` reached Anthropic first and returned its 404 on every call. Unprefixed ids and ids whose prefix is not a Marina provider (`vendor/model`) take the first-party-preferred loop with the id as sent; there an Anthropic `404` is a routing miss: the loop tries the next keyed provider and returns the 404 only when none serves the id. The routed target is always the provider that answered.
  - **The named provider's answer is final.** Success, a rejection (`400`/`413`/`415`/`422`, e.g. `logprobs` on a reasoning model), a `404`, a `429`, a `5xx` or a transport failure (`502`, or `504` on timeout) is returned to the caller with the provider's own status and body; it never falls back to another provider. The prefix is that provider's namespace: before this, an OpenRouter `429`/`5xx` on `openrouter/qwen/…` was retried on Hugging Face with the full `openrouter/…` id, which 400'd and hid OpenRouter's reason.
  - **Prefixes that cannot be another provider's id.** An aggregator prefix (`openrouter/…`, `huggingface/…`) or a local-runtime prefix with that provider unconfigured is `503` *not configured*, never sent elsewhere. A first-party vendor prefix with no key for that vendor (`openai/gpt-…` without `OPENAI_API_KEY`) is that vendor's id in an aggregator's namespace, so the loop asks only aggregators (`openrouter`, `huggingface`), never a first-party API. Default (`marina/default`) requests with no pinned `default_model` are the one class that falls back across providers, and each attempt is mapped to that provider's own default model (`getDefaultUpstreamModel`), so no provider is handed an id it does not carry.

  Tests: `test/upstream-explicit-provider.test.ts`.
- **`marina/verify:<proposer>[+<checker>]` (2026-10-03)** — the verification formation as a model id (`src/net/model-api/verify.ts`, reached from `runOpenaiChat` before any routing).
  - **Flow:** proposer draft (tools allowed) → checker review of the draft against the rules, requests and tool results (JSON verdict) → at most `MARINA_VERIFY_ROUNDS` (default 1) proposer revisions with the reviewer's note in the trailing note (after the lessons), so a revision reads the proposer's cached prefix.
  - **Plumbing:** every call goes through `proxyToUpstream`, so spend, the daily cap and lifecycle traces apply. The id travels as `body.model` (never `forceModel`), so each call takes the explicit-provider path: the named provider's answer (rejection, outage or transport failure) is final. A proposer or checker is never answered by another vendor's default model. The caller's distinct passthru identity (bound key / name-map) is stamped on the inner calls' lifecycle events.
  - **Operator pin:** in `passthru` endpoint mode with a configured `passthruModel`, `default` names the pin and any other proposer or checker id is refused with `403 model_not_allowed`; `MARINA_REPAIR_MODEL` is used only when it is the pin.
  - **Response:** sums `usage` and `x-marina-cost-usd`, and sets `x-marina-verify`.
  - **Fails open** to the draft.
  - **Write-action guard** (`guardRevision`): a revision may change text and read-only calls freely, but a state-changing tool call stays as drafted unless the verdict carries a `conflict` (`kind`, verbatim `quote`, `call`, `field`).
    - The quote must be found in the conversation.
    - Only the cited call may be added or dropped, and only the cited argument of a modified call may change.
    - No id may appear that is absent from the conversation and its tool results.
    - A guarded revision is discarded and the response says `x-marina-verify: held-write`.
  - **Output repair** (`src/repair/tool-call-repair.ts`, `MARINA_OUTPUT_REPAIR`). The final message is repaired when tools were sent and the message carries its call as fenced or bare JSON for a declared tool, or has malformed arguments. `<tool_call>` tags are already normalized upstream.
    - The repair is mechanical first, then one re-encoding shot (`MARINA_REPAIR_MODEL`, else the proposer). The shot's values must appear verbatim in the message, and a write call may use only argument names the message wrote.
    - The response says `x-marina-repair: repaired:parse|repaired:shot`.
    - Read-only: the shared tool classifier in its `guard` role (see "Read or write" under the obligations ledger).
  - **Refusals:** `stream` and `n > 1` get `unsupported_parameter`; non-upstream ids get `model_not_found`.
  - **Checker:** the default is `MARINA_VERIFY_CHECKER_MODEL`, else the proposer.
  - **Checker effort (2026-10-04):** the checker call carries the caller's effort fields (`reasoning_effort`, `reasoning`, `thinking`, top level first, then a literal `extra_body`), so a caller asking for `high` gets a `high` review. `MARINA_VERIFY_CHECKER_EFFORT=low|medium|high` sends that `reasoning_effort` instead; `off` sends none (the model's default). Provider translation (Anthropic thinking / Claude 5 adaptive effort, `omitsSamplingParams`) happens in the upstream layer, as for any passthru body; the checker never sends sampling parameters.
  - **Checker prompt caching (2026-10-04):** `checkerMessages` lays the request out append-only so its prefix is byte-identical turn over turn: the constant `CHECKER_SYSTEM`; one user message whose parts are the head (rules + tool catalogue), then one text part per conversation message (each clamped independently), then the most recent images (with their note), then the tail (lessons + the draft). For a Claude checker with `MARINA_ANTHROPIC_AUTO_CACHE` on, it marks three breakpoints itself (system, head, last conversation part), so the next turn reads the whole earlier conversation from cache; any other checker gets the same text as one string, which keeps OpenAI-style automatic prefix caching. Trade-off: lessons sit in the uncached tail (they follow the latest user message), and images sit after the cached prefix (the "most recent four" window moves).
  - **Tests:** `test/model-api-verify.test.ts`. Guide: [τ²-bench](../guides/tau2.md).
- **Obligations ledger (2026-10-05)** — `marina/obligations:<model>` (or `x-marina-obligations: on|observe` with an unchanged id; combinable with `marina/lessons:` in either order) keeps track of what a multi-step tool conversation still owes (`src/obligations/`, surface `src/net/model-api/obligations.ts`, reached from the passthru branch of `runOpenaiChat`; `/v1/messages` included). Without the opt-in nothing runs and the request is byte-identical.
  - **Extract:** each new user message is read once into explicit obligations (what, target, constraints, candidate tools from the request's own write tools) by one cheap call on `MARINA_OBLIGATIONS_MODEL`, else the request's own model (the operator's passthru pin wins). A request without `tools` is skipped (`skipped=no-tools`).
  - **Conversation key (2026-10-06):** `x-marina-session` when the client sends one — exact keying, and the recommended way: send a unique id per conversation. Without it the key is derived (`conversationKeys`), scoped by the caller (a bound name, a name-mapped agent, or a hash of the matched key — never the key): a hash of the system/developer text, the declared tool schemas and the first user message, deepened at message-count checkpoints (every non-system message up to 8, then 12, 16, 24, … 128) by a running hash over the history. `LedgerStore.resolve` carries a conversation's state from its deepest known ancestor key to its current key as a COPY, so two conversations with an identical opening share a ledger only while their histories are byte-identical and part at the first checkpoint after they diverge (the previous opening-only hash let two banking simulations share one ledger). A history the client edits or rewrites starts a fresh ledger. Ledgers live in process memory (LRU, 6 h idle TTL, at most 16,000 keys); nothing is written to the world database, and a lost ledger is rebuilt from the resent history on the next request. The argument check keys its per-conversation memo the same way.
  - **Track:** a successful state-changing call (by the classifier below in its `track` role; a generic dispatcher call by the tool it runs, see below; an error-shaped result never counts) settles an obligation when it is one of its candidate tools and its arguments share an id-like token with the target (or neither side has one); a transfer/escalation tool settles all open ones as handled. Equally plausible candidates are ambiguous and go to a judge (the decision layer's `choice` when `MARINA_DECISIONS` / `MARINA_DECISION_ENGINE` is configured, else the ledger's chat model), at most three per request.
  - **Remind (`on`):** open obligations ride as a trailing note AFTER the cache breakpoints (`proxyToUpstream` hint `trailingNote`): appended to the final user turn (a tool-result turn on Anthropic; a new user message after a `tool` message on OpenAI-compatible routes), never a mid-conversation system message, so the cached prefix and the rolling breakpoint are the same with or without it. The note is labelled a bookkeeping note and says it changes no rule (confirmations still apply).
  - **Check before the final answer (`on`, non-streaming):** a reply with no tool call while an obligation is open (and never nudged) is classified per obligation — `owed`, `waiting` (asks the user first), `declined` (refused, impossible or transferred: handled), `done`. Only `owed` ones trigger ONE retry whose trailing note quotes the draft and lists them; the model's second reply is returned as it wrote it (it may send the draft again). Each obligation is nudged at most once. A judge or retry failure returns the draft. Streams get the reminder only.
  - **Consent (2026-10-08, `MARINA_OBLIGATIONS_CONSENT=observe|on`, default `observe`):** the extractor's existing call also returns `consent` — open obligations the new request explicitly approves as the assistant last described them — recorded as `consentTurn` (no extra call). A final reply judged `waiting` on an approved obligation is a **re-ask**. `observe` only counts (`consented=` / `reasks=` in the header and log line, check `reask`); the model sees nothing new. `on` shows "approved in request N" on listed obligations and treats a re-ask as owed, so the one-time nudge names it with `CONSENT_NOTE` (act now unless something material changed; if a required detail is missing, ask only for that). The agent-loop ledger (`src/obligations/agent.ts`) marks approvals the same way in its section and end-of-run follow-up. Motivation: a requester who approves and ends in one message loses the action when the assistant asks again.
  - **Pre-write review (2026-10-08, `MARINA_OBLIGATIONS_REVIEW=off|observe|on`, default `off`; `src/obligations/review.ts`):** a non-streaming reply that carries a state-changing call (the `guard` classification) gets ONE judge call with up to two yes/no questions — **order** (only with ≥ 2 open obligations: would doing this now prevent another open request or change its terms?) and **evidence** (does the call rely on a condition no recent tool result shows?). At most 4 reviews per conversation, each kind named at most once. `observe` counts (`reviews=`/`review_flags=`, labels `review-clear|review-order|review-evidence|review-order+evidence|review-unjudged`); `on` (ledger also `on`) retries once with a note that names the concern and invites the same call again (`reviewed-kept|reviewed-changed`). The agent-loop ledger runs the same review as a one-time refusal after the argument check (`AgentObligations.reviewWrite`). With the review off every path and label is unchanged.
  - **Learn:** a nudge that led to a tool call becomes one `tools` outcome (`obligations:passthru`, general wording, the obligation text only as the leak check's `privateContext`).
  - **Spend:** every ledger call goes through `proxyToUpstream` (or the metered decision provider), so it is recorded and refused at the daily cap; a refused call degrades the ledger to off for that step. `x-marina-obligations` reports counters (`on;open=1;satisfied=2;declined=0;nudges=1;extract=ok;check=nudged-acted`), `x-marina-obligations-cost-usd` the ledger's own spend on the request including a discarded draft; one `model-api` log line per request carries the same counters, never content.
  - **Tests:** `test/obligations.test.ts`.
- **Argument check before writes (2026-10-06)** — `marina/argcheck:<model>` (or `x-marina-argcheck: on|observe` with an unchanged id; combinable with `marina/obligations:` and `marina/lessons:` in any order) checks each state-changing call in a reply against what the conversation established (`src/obligations/argcheck.ts`, surface `src/net/model-api/argcheck.ts`, run after the obligations step). Without the opt-in nothing runs and the request is byte-identical.
  - **Read or write (2026-10-06, `src/obligations/tool-effect.ts`, one classifier for the ledger, the check and the verifier's write-action guard):** a declared MCP hint wins (`readOnlyHint: true` read; `readOnlyHint: false` or `destructiveHint: true` write). Otherwise a write verb leading the name or the description (`update_`, `cancel_`, "Change the email…") is a write; a read verb leading the name (`get_`, `list_`, `search_`, `find_`, `lookup_`, `read_`, `check_`, `view_`, `describe_`, …, after up to two namespace words such as `KB_search_bm25`, or camelCase) is a read; a read verb leading the description ("Search the knowledge base…", "Returns the…") is a read when no write word appears in it. An ambiguous verb (`unlock`, `give`, `grant`, `open`, `run`, `execute`, `call`, …) is a read only when the description says the tool gives access to or reveals something and names no write word and no user-owned state (`user`, `customer`, `account`, `card`, `order`, …): "unlock a tool you have access to" is a read, "unlock the user's card" a write. Anything else is a write. The **`guard`** role (argument check, write-action guard) stops there — missing a write would skip its check, while a lookup counted as a write costs only a free mechanical pass. The **`track`** role (obligations ledger) also takes weaker read evidence — the description's read words (`search`, `explore`, `look up`, …) outnumber its write words, or the only parameter is a free-text search (`query`, `q`, `question`, …; limits like `k` aside) — because there a lookup counted as a write is the costly error: the extractor offers it as a way to carry a request out and its calls settle obligations they never fulfilled. A lone `command`/`script`/`sql` parameter is read evidence in neither role: only the description can say a shell explores. No product-specific tool names.
  - **Which calls:** the classifier above in its `guard` role; at most four write calls per reply.
  - **Dispatcher calls (2026-10-06, `src/obligations/tool-call.ts`, shared by the ledger and the check on both surfaces):** a call whose arguments are exactly a name key (`tool`, `tool_name`, `*_tool_name`, `action`, `name`, `function`, `method`, `operation`, …) holding an identifier and an arguments key (`arguments`, `args`, `params`, `parameters`, `input`, `kwargs`, `payload`) holding an object or a JSON-object string is classified by the INNER tool with the same rule, so a dispatched lookup is not a write. When the tool declares its parameters, both keys must be declared and a name `enum` must contain the inner name. The shape is detected from the arguments and schema, never from a tool's name. Malformed inner arguments, a non-identifier or unknown inner name, or a third key fall back to the outer tool; an outer tool that is already read-only (declared or by name) stays read-only. The check reads the inner arguments (the inner tool's name is not a checked value), and the ledger matches an obligation's candidate tools against the outer and the inner name. Agent loops skip the check for a `mutate`/`consequential` dispatcher call whose inner tool is a lookup. Streams, upstream errors and requests without `tools` pass through with the counters header.
  - **Mechanical pass (free):** every id, amount, date and short option in the arguments is looked up in the conversation. Amounts are compared as numbers (`$1,250.50` = `1250.5`), dates as ISO days (`May 3, 2026` = `2026-05-03`), ids and options as whole tokens. A value in a user message or a tool result is first-hand; one only in the assistant's own text or the system/policy text is `weak`; one nowhere is missing. Tool-call arguments are never evidence. Free text (`reason`, `note`, long strings), a program the model writes itself (`command`, `cmd`, `script`, `sql` — e.g. a `shell` retrieval tool, which the `guard` role keeps as a write), booleans and integers up to 10 are not checked. A call whose values are all first-hand passes with no model call.
  - **Judge trigger (`MARINA_ARGCHECK_TRIGGER`, read by both surfaces):** `flagged` (default) asks the judge only about a call the mechanical pass flagged; `all-writes` asks about every write call, with the mechanical findings shown as a free pre-signal. The default comes from offline replays of the judge: in-sample over τ³-Banking write calls `all-writes` caught more wrong-argument calls but judged roughly a quarter of correct writes unsupported; a pre-registered held-out replay (other τ² banking, airline and telecom runs, dispatcher lookups excluded) still put it at about 13 %, above the 10 % at which a nudge on correct writes becomes a risk, while `flagged` stayed near 2–5 %.
  - **Judge:** one `noul` question, "is every argument the value the user meant and the conversation supports?" (`ARGCHECK_QUESTION`, verdict by `decideArgcheck` in `src/decisions/policy.ts`: one cut at 0.5) on the decision layer when configured, else one JSON answer from `MARINA_ARGCHECK_MODEL` (then `MARINA_OBLIGATIONS_MODEL`, then the request's model). Its state (`judgeState`) aims at "a real value, but not the one the user meant": each checked value with where it appears (user / tool / assistant only / instructions only / not found) and up to eight OTHER values of its kind the user or a tool gave (the same argument name in a tool result, the same id shape, the user's amounts and dates — e.g. every account id a lookup returned); the first and the latest six user messages; optionally **rule passages** (`rulePassages`, opt-in with `MARINA_ARGCHECK_RULE_BYTES`, default 0; the held-out replay used 3,000): up to that many UTF-8 bytes of the system text and tool results (the documents the assistant read), split into markdown sections or paragraphs, prose only (a record listing is not a rule), each naming the tool's exact name (for a dispatcher, the inner tool) or one of its action words, ranked by exact name, then idf-weighted action words, then argument names, a document read twice counted once, in conversation order, and framed as untrusted reference data (`formatUntrustedContext`), never instructions, with one added system sentence (a passage that does not clearly govern the call is no reason to doubt it) — off by default because in a pre-registered held-out replay they did not raise recall net of false alarms; passages that mention the arguments' names or values (tool results, user messages, instructions; rarer words weigh more, 3,000 characters; a paragraph already among the rule passages is not repeated); the latest four tool results; and, when the obligations ledger runs too, its stated requests and their constraints. It answers unsupported only for a specific conflict (a value the user or a tool points away from, a rule shown that gives another value, a value found nowhere); a value it cannot verify either way counts as supported. The chat judge may name the argument it doubts; the name is kept only if it is one of the call's argument names, and only the name reaches the nudge.
  - **Nudge (`on`):** an unsupported call gets ONE retry whose trailing note names the flagged values and why (not found / only in the assistant's or the instructions' text), or, for a call with no flagged value (`all-writes`), the doubted argument's name, and asks the model to check them against the user's request; the note never proposes a value and never lists the alternatives. The second reply is returned as the model wrote it. Each call signature (tool name + canonical arguments) is nudged at most once per conversation, so the same call issued again passes (`check=repeat`). With the obligations ledger on, its reminder stays in the retry's trailing note.
  - **Failure:** a judge outage or unparseable answer lets the call through (`check=unjudged`); a failed retry returns the draft. `observe` judges and logs but never retries.
  - **Spend and telemetry:** the chat judge goes through `proxyToUpstream` (`routeReason: argcheck`; the retry `argcheck:nudge`), the decision provider meters itself; both count against the daily cap. `x-marina-argcheck` reports counters (`on;writes=1;checked=3;flagged=1;judged=1;nudges=1;check=nudged-changed`), `x-marina-argcheck-cost-usd` the check's spend including a discarded draft; one `model-api` log line per request carries counters only.
  - **Tests:** `test/argcheck.test.ts`, `test/argcheck-dispatch-rules.test.ts`. The τ² kit's opt-in arms `argcheck` and `obligations+argcheck` measure it.
- **OpenAI surface** (`src/net/model-api.ts`) — `/v1/chat/completions`, `/v1/responses`, `/v1/models`, `/v1/health`. The Responses API has server-side state: each response_id maps to a conversation channel (`model-conv-{id}`); `previous_response_id` threads continuations onto the same channel. In-memory id index, 24h retention, channel lazily garbage-collected on DELETE when no responses reference it.
- **Explicit orchestrations route to their agents in every mode (2026-09-26)** — `liveOrchestrationChannel` (`model-api/shared.ts`): a `marina:<name>` / `marina/<name>` id naming a `model-<name>` channel with an ONLINE member goes to those agents even in `passthru` endpoint mode and from an internal caller (previously both proxied it upstream, which can only 404 — so in-world `benchmark run --model marina:<crew>` / `sweep` / `evolve trial` never reached agents in a default world). `marina`, `marina/default` (the internal agents' proxy model), conversation channels and ids with no live channel keep their route; a caller that is itself a member of the channel (`X-Marina-Agent`) is never routed back into it.
- **Explicit upstream ids route upstream in every mode (2026-10-01)**: this is the mirror rule.
  - **The rule.** `explicitUpstreamModel` (`model-api/upstream.ts`) covers a `<provider>/<id>` naming an upstream this instance can reach, meaning a `PROVIDER_UPSTREAM` provider with a key, or an opted-in local runtime. Such an id takes the passthru branch in the `agents` / `open` / `panel` modes too, on chat completions, responses and both Ollama handlers.
  - **The bug it fixes.** Before this, an external caller in the default `agents` mode got `404 model_not_found` without any upstream call: the id was looked up as a `model-<id>` channel that cannot exist. A benchmark judge could therefore not use, through Marina, a model Marina serves to its own agents.
  - **Forced models.** In those modes `passthruForceModel` never lets the configured fallback model answer an explicit id. In `passthru` mode the operator's pinned model still wins.
  - **Unchanged ids.** `marina` / `marina/default`, unprefixed ids and ids naming an unreachable provider keep their route.
  - **Long requests.** Model-API POSTs lift the listener's 255 s idle cap per request to `MODEL_REQUEST_TIMEOUT_MS` + 30 s (`server.timeout`, `modelRequestIdleSeconds`). A crew answering after more than four minutes is therefore still delivered.
  - **Tests:** `test/model-api-explicit-upstream.test.ts`.
- **Anthropic upstream (Claude 5 family)** — `proxyToAnthropic` joins EVERY `text` block of a Messages response via `anthropicTextContent` (Claude 5 models emit a `thinking` block first; reading `content[0].text` returned an empty answer with non-zero completion tokens — found 2026-09-14 when Sonnet 5 scored 6 % on gsm8k through passthru). It also forwards EVERY `system` message, concatenated in order (`anthropicSystemPrompt`; string or OpenAI content-part arrays) — previously only the first was sent, so memory injected as a second system message (the harness, and any OpenAI-style client) was silently dropped for Anthropic upstreams while OpenAI upstreams received it. Upstream 4xx bodies are surfaced in the error message (`anthropicErrorMessage`): Claude 5 rejects `top_p` and any `temperature` other than 1 ("deprecated for this model"); OpenAI clients send both routinely, so the translated path drops them for the Claude 5 family (`omitsSamplingParams`, 2026-09-25 — found when every in-world `benchmark run` 400'd on `temperature: 0`). A native Anthropic body is forwarded as sent. Regression test: `test/anthropic-text-content.test.ts`. **Provider conformance probe** (`probeConfiguredProviders` in model-api.ts; `readiness providers [name]`, rank ≥ 4 unless `isLocalUngated()`): one tiny request per configured provider through the SAME `proxyToUpstream` path passthru uses — two system messages, a check word in the SECOND one — passes only if non-empty text comes back AND the check word is present AND the routed lifecycle target is the probed provider (`servedBy`) — `proxyToUpstream` falls back to the next configured provider when the forced one fails, so a fallback-served reply must not credit a provider whose key is dead (this is how the expired OpenRouter key in the dev `.env` was found). Exactly the two silent failures above; run it after adding a provider or a model generation. `getLastProviderProbe()` keeps the last result in memory. Tests: `test/provider-probe.test.ts` (mocked fetch).
- **Anthropic tool calling + error codes (2026-09-22)** — `src/net/anthropic-tools.ts` translates OpenAI ⇄ Anthropic both ways: `tools/functions` → `tools[{name,description,input_schema}]`, `tool_choice` → `{type: auto|none|any|tool}`, `parallel_tool_calls:false` → `disable_parallel_tool_use`, `stop` → `stop_sequences`, `response_format json_schema` → `output_config.format`; assistant `tool_calls` → `tool_use`, consecutive `role:tool` → ONE user message of `tool_result` blocks; responses map `tool_use` → `tool_calls` + `finish_reason:"tool_calls"` (streaming emits `delta.tool_calls` fragments). `json_object`, `n>1`, non-function tools → `400 unsupported_parameter` (never a silent drop or provider fallback); agents mode refuses `tools`/`n`/`response_format` the same way and omits `usage` when unknown (`usageFromTrace` sums `agent_turn_end` spans). `src/net/openai-errors.ts` gives every error a string `code` (`invalid_api_key`, `model_not_found`, `context_length_exceeded`, `rate_limit_exceeded`, `unsupported_parameter`, `upstream_error`, …). `/v1/responses stream:true` is buffered SSE. Ollama: `/api/version`, `/api/show`, `/api/ps`, richer `/api/tags`; `/v1/embeddings`, `/v1/completions`, `/api/embed(dings)` → 404 `not_found`; `isModelApiPath()` is the dispatcher predicate. Caching: incoming `cache_control` on `/v1/messages` is forwarded verbatim; OpenAI-completions `cache_control` parts map onto Anthropic system/tool blocks; `MARINA_ANTHROPIC_AUTO_CACHE` (default on under `local`) places breakpoints per "Cache breakpoints" below; `cache_read_input_tokens`/`cache_creation_input_tokens` surface as `prompt_tokens_details.{cached_tokens, cache_creation_tokens, cache_write_tokens}`, on the lifecycle event and in the `x-marina-cache-*` headers. `readiness providers` now also runs a tool-call probe (`toolCallOk`) for Anthropic/OpenAI.

## Internal agents always passthru (2026-09-22)

Marina's own runtime agents (room / crew / coding agents on `marina/default`) call the self-proxy `/v1/chat/completions` with the internal model token (`auth.internal === true`) and `tools`. They are **consumers** of the upstream, never participants of the agents/open/panel routes — so `isInternalCaller(auth)` in `model-api.ts` sends them down the passthru branch in EVERY endpoint mode (`runOpenaiChat`, `handleResponsesCreate`, the Ollama handlers; `/v1/messages` reaches `runOpenaiChat` and is covered). Found on a fresh install: the default mode is `agents`, so an internal agent's first turn hit `rejectUnsupportedForAgents` → `400 unsupported_parameter: tools` until an operator switched the endpoint to passthru (before the tool-calling review, agents mode silently dropped the tools instead — equally broken, and the request would have been routed to another agent on the `model` channel). Routing decision, auth × mode → route:

| caller (auth) | `passthru` | `agents` / `open` / `panel` |
|---|---|---|
| internal model token | upstream proxy (`routeKind: passthru`) | **upstream proxy** (`routeKind: passthru`, `routeReason: "internal"`) |
| bound / plain / multi-tenant key, open dev mode | upstream proxy (`routeKind: passthru`) | in-world agents; `tools`/`n`/`response_format` → `400 unsupported_parameter`; 503 + `fallback` → upstream (`routeKind: fallback`) |

Internal callers still pass through `preparePassthru`, so identity, injection and receipts apply exactly as for passthru (an internal agent sends no `X-Marina-Agent`/bound key, so it gets a plain proxy). The `passthruModel` pin applies to them the way it applies to the fallback route. Test: `test/internal-agent-routing.test.ts`.

## Cache breakpoints (2026-09-22)

Under `MARINA_ANTHROPIC_AUTO_CACHE`, `placeCacheBreakpoints` (`src/net/anthropic-tools.ts`) lays out `cache_control: ephemeral` as **last STABLE system block → last system block → last tool**, within Anthropic's four-breakpoint limit (markers the client already set count against it) and never on a block that already has one. The stable block is the one before a volatile last system block when the caller says it has one (`injectedSystemTail` hint from `proxyToUpstream` → `proxyToAnthropic` → `buildAnthropicRequest`), else the last block; the passthru's own injections no longer use it (see below). When the client placed its own markers (pi-ai `cacheControlFormat: "anthropic"`, an Anthropic SDK on `/v1/messages`) every marker is preserved and the proxy adds ONLY the stable-block breakpoint, and only if that block has none — a native body whose last system block is already marked is forwarded untouched. Tests: `test/cache-breakpoints.test.ts`.

**Per-request injections trail the breakpoints (2026-10-06).** Everything the passthru adds per request — the memory addendum (relevance-gated, grows as notes accrue), opt-in `marina/lessons:` lessons, the obligations reminder and the obligations/argcheck nudges, and `marina/verify`'s proposer lessons and reviewer note — is ONE trailing note (`passthruUpstreamHints` → `proxyToUpstream` hint `trailingNote`), appended to the final user turn AFTER the cache breakpoints are placed: a trailing text block of that turn on Anthropic (native `/v1/messages` bodies included), appended to the last user message or sent as a new user message after a `tool`/assistant message on OpenAI-compatible routes, appended to the prompt on `/api/generate`. The caller's system prompt, tools and every earlier message are forwarded byte-identical turn after turn, so the previous turn's rolling breakpoint is read from cache whatever was injected. Before, the addendum was a system block right after the caller's prompt: the stable-block breakpoint kept the system prompt cached, but the whole conversation after it was rewritten whenever the addendum changed — a τ³ run with lessons recalled from each turn's latest user message saw cache-read share fall from 0.96 to 0.89 and cache writes rise about fourfold per call. Lessons are also recalled for the conversation's OPENING user request (`lessonQuery`), so one conversation is served the same set on every turn and it changes only when the lesson pool does; memory stays relevance-gated on the latest turn (it is in the uncached tail, so that costs nothing). The response cache keys on the request with its note (`effectiveBody`), so different memory never shares an entry. A request with nothing opted in is forwarded byte-identical. Tests: `test/passthru-prefix-stability.test.ts`.

**Rolling conversation breakpoint (2026-10-03).** System and tool breakpoints alone leave the conversation uncached: in a multi-turn tool loop (Code Mode, crews, benchmark harnesses) the history grows every turn and was re-billed at full input price. On the translated path (`buildAnthropicRequest` → `placeCacheBreakpoints({ rollingMessages: true, model })`) auto-cache adds a fourth kind: a breakpoint on the last markable block (`text` with content, `image`, `document`, `tool_use`, `tool_result`; never `thinking`) of the latest message, a string content becoming one text block. Each turn writes only the new tail and reads everything before it (the previous turn's breakpoint is within Anthropic's 20-block lookback unless one turn appends more). It is placed only when the client set no marker anywhere (pi-ai's own rolling marker wins), only within the four-breakpoint limit (stable system + last system + last tool + rolling = 4 at most), and only when the estimated prefix (`estimatePrefixTokens`, serialized length / 4) reaches `minCacheableTokens(model)` — 512 on Opus 5.x/Fable/Mythos, 1024 on Sonnet and Opus 4.0/4.1/4.8 and unknown ids, 2048 on Opus 4.7/Haiku 3.5, 4096 on Opus 4.5/4.6/Haiku 4.5. Native `/v1/messages` bodies keep their messages exactly as sent (system/tool placement is unchanged there). Every write costs 1.25× on the newly written tail, so a one-shot request pays that premium on its messages once — the reason auto-cache stays off by default outside the `local` profile.

**OpenRouter `anthropic/*`.** `prepareUpstreamBody` used to strip `cache_control` for every OpenAI-compatible provider, so Claude via OpenRouter (the route most benchmark runs use) never cached at all — not even a client's own markers. OpenRouter forwards `cache_control` on content parts to Anthropic, so `honorsCacheControl(provider, model)` (OpenRouter + `anthropic/` id) now keeps the client's markers, and under auto-cache with none present `placeOpenAICacheBreakpoints` adds them in the OpenAI shape: the last stable leading system message, the memory addendum (`injectedSystemTail`, passed through `prepareUpstreamBody`'s `cache` argument), and the rolling breakpoint on the latest message's last text part (role `tool` included — OpenRouter honors it there) — at most three. Every other upstream (OpenAI, Gemini or any non-Anthropic id on OpenRouter, local runtimes) is still stripped; OpenAI's automatic prefix caching and Gemini's implicit caching need no markers. A related routing fix: an explicit `anthropic/<id>` request now reaches Anthropic with the bare id (`proxyToUpstream` passes the resolved model into the body), instead of 404ing there and silently falling back to OpenRouter. Tests: `test/rolling-cache-breakpoints.test.ts`.

## Cost and cache headers (2026-09-22)

Every proxied reply (passthru, internal, fallback) carries `x-marina-upstream-model` = the served `provider/model` (the lifecycle `target`; set before the body, so streams have it too). Non-streaming replies add `x-marina-cache-read-tokens`, `x-marina-cache-write-tokens` and `x-marina-cost-usd` (the tokens of a stream ride its final SSE `usage` chunk and the lifecycle event instead). Cost comes from the upstream's own `usage.cost` when it reports one (OpenRouter), else from pi-ai's built-in catalog (`upstreamCostUsd`: `builtinModels().getModel(provider, id)` + `calculateCost` over uncached input / output / cache-read / cache-write; OpenAI-shaped `prompt_tokens` includes the cached share, so it is subtracted first) — undefined, never a fabricated $0, for unlisted or local models. It lands on the lifecycle `completed` event as `costUsd`, so agents on the synthesized `marina/default` model (which has no price of its own) are priced by what actually served them. Usage bodies carry `prompt_tokens_details.cache_creation_tokens` (extension) and, with the same value, `cache_write_tokens` — the name pi-ai's OpenAI-completions client reads — so an agent's `cacheWriteTokens` is no longer always 0. Streamed lifecycle `completed` events are populated from the final SSE usage chunk (`stream_options.include_usage` for OpenAI-shaped upstreams; the Anthropic translator reports `message_start`/`message_delta` usage through an `onUsage` side channel even when the client did not ask for usage in the stream).

## Responses API streaming (2026-09-22)

`/v1/responses` with `stream: true` is incremental on both paths. Passthru consumes the upstream chat-completions SSE (`stream_options.include_usage`) and re-emits `response.created → response.in_progress → output_item.added(message) → content_part.added → output_text.delta… → [per tool call] output_item.added(function_call) → function_call_arguments.delta… → output_text.done / function_call_arguments.done → output_item.done → response.completed` with a running `sequence_number`; agents mode streams `model_response_chunk` events the same way. `formatResponseRecord` is the single source for the `response.completed` payload and `GET /v1/responses/:id`, so streamed and non-streamed bodies are identical. A mid-stream upstream failure emits `response.failed` (`error.code: "upstream_error"`) and stores nothing; the response cache is bypassed for streams.

## Responses API tools (2026-09-22)

`src/net/responses-tools.ts` is the single translation point between the Responses shapes and chat-completions on the passthru path — request: flat `tools[{type:"function", name, description, parameters, strict?}]` → `tools[{type:"function", function:{…}}]`, `tool_choice` `auto|none|required|{type:"function", name}` → `auto|none|required|{type:"function", function:{name}}`, `parallel_tool_calls` passthrough; `input` items `function_call` → `assistant.tool_calls` (consecutive calls merge into one assistant message) and `function_call_output` → `role:"tool"` (`responsesInputToMessages`, which also owns the text/`input_text` mapping and the plain-text rendering the conversation channel stores). Reply: chat `tool_calls` → `function_call` output items with `call_id` = the upstream id verbatim (`chatToolCallsToResponses`, consumed by `extractResponseTextAndUsage`); streamed `delta.tool_calls` fragments feed `ResponsesSseEmitter.toolCallDelta` unchanged. `translateResponsesTools` runs in `handleResponsesCreate` before `runResponsesPassthru`, so a hosted tool type (`web_search`, `file_search`, `computer_use_preview`, `code_interpreter`, …) is `400 unsupported_parameter` with `param: "tools[i].type"` before any upstream call — never a silent drop; `ResponsesRequestError` covers malformed values (a nameless function tool, a result without `call_id`). Because `proxyToAnthropic` already translates chat tools to Anthropic `tools`/`tool_use`/`tool_result`, a Responses client with tools works end-to-end against an Anthropic upstream (`test/responses-tools.test.ts`). **Tool loop over server-side state**: a `previous_response_id` continuation that sends only `function_call_output` items gets the stored prior record's `toolCalls` re-attached as `assistant.tool_calls` on the trailing history turn (`restorePriorToolCalls`) so every `role:"tool"` message is paired. Agents mode keeps refusing `tools` via `rejectUnsupportedForAgents` (`param: "tools"`).

## Image content parts (2026-10-03)

Images pass through every passthru translation, and anything that can't be forwarded is refused, never dropped (`test/multimodal-passthru.test.ts`).
- **OpenAI-compatible upstreams** (OpenAI, Google's OpenAI-compatible endpoint, OpenRouter, Groq, local servers) receive chat `image_url` parts unchanged. `stripCacheControl` keeps them.
- **Anthropic:** `image_url` and `input_image` parts become image blocks (a `data:` URL becomes base64, http(s) becomes `url`), including images inside `role:"tool"` results, which Anthropic `tool_result` accepts. Any other non-text part, or an image without a URL, is `400 unsupported_parameter`.
- **Responses:** `responsesInputToMessages` turns `input_image` parts (an http(s) or `data:` URL, `detail` kept) into chat `image_url` parts. Text-only content stays a plain string. `input_file`, `input_audio` and images by `file_id` are `400 unsupported_parameter`. The conversation channel's text rendering appends `[N images]`.
