# Security & API — Authentication, Rate Limits, HTTP Hardening, Gateway

**When to read this:** you are adding an HTTP route, an upload or asset path, an MCP transport change, a login path, rate limiting, external auth, SSRF-sensitive fetches, or federation. `CLAUDE.md` → "Security & API" states the invariants; this page is the complete reference, including HTTP hardening.

## Authentication and rate limiting
- **API authentication**: HTTP endpoints require `MODEL_API_KEYS` / `MEM_API_KEYS` or explicit `MARINA_OPEN_API=true` for dev mode. The dashboard/asset/canvas API auth gate (`authenticateRequest` in `src/net/auth-middleware.ts`) also honors `MARINA_OPEN_API=true`: a missing/invalid token is allowed through as the `OPEN_API_ENTITY_ID` sentinel (valid tokens still resolve to their real entity). Dev-only — never enable in production.
- **Rate limiting**: all endpoints rate-limited (token buckets built in `src/main.ts`) — WebSocket, telnet and MCP commands share one limiter keyed per entity (50/sec refill, burst 200), Model API 20/sec per IP (burst 100), Memory API 10/sec per agent (burst 20); the HTTP route limiters are listed under HTTP hardening below. The `local` trust profile sets `RateLimiter.bypass` except for buckets marked `ignoreBypass` (account-link codes).
- **Login limits**: `MARINA_MAX_LOGINS` caps concurrent entity-bound connections instance-wide (0 = unlimited); `MARINA_LOGIN_ATTEMPTS_PER_MIN` throttles login/reconnect attempts per IP (default 10, 0 = off). Enforced centrally in `engine.login()`/`reconnect()`; internal room/crew agents authenticate via the internal token (`internalToken` on the login/auth WS message) and are exempt from both
- **Account-link codes** (`src/engine/commands/link.ts`): `link` issues a 6-symbol CSPRNG code (5-minute expiry) that Telegram/Discord redeem via `redeemLinkCode` — a binding only; the login that follows still goes through `engine.login()`. Guessing is limited per external account (5 code-shaped attempts, +1 per 2 min) and globally on failures (30, +1 per 10 s); both buckets set `ignoreBypass`, so the `local` profile's `RateLimiter.bypass` never relaxes them. A limited attempt is not checked and falls through like ordinary text, so name login is never blocked.
- **Optional external auth (better-auth)**: OFF by default. `MARINA_AUTH=better-auth` enables email/password + social OAuth sign-in on the web surfaces and gates passwordless name-login (`engine.config.authRequired`). A verified identity is bridged to a *named* entity (the artilect stays the in-world identity); agents keep token auth. Admins by verified email (`MARINA_AUTH_ADMIN_EMAILS`), not name. Lazy-loaded provider in `src/auth/better-auth-provider.ts`, bridge in `src/net/api/auth-api.ts` (`/api/auth-status`, `/api/auth/*`, `POST /api/auth-session`), dashboard gate in `dashboard/src/components/AuthGate.tsx`. When off: no import, no routes, no schema effect. Setup: [docs/authentication.md](../authentication.md)

## HTTP hardening
- **HTTP hardening** (`src/net/http-utils.ts`): `clientIp(req, peer)` uses the socket peer unless `MARINA_TRUST_PROXY=true` and feeds EVERY per-IP limiter; named limiters `HTTP_RATE_LIMITS` (`dashboard` 60/10 s per principal, `mutation` 30/10 s for canvas/asset writes, `publicRead` 30/10 s for `/api/entity/*`, `mcpSession` 10/min per IP for MCP session/login/auth). `refuseOpenApiWrite()` — the `OPEN_API_ENTITY_ID` sentinel is read-only on asset and canvas routes too (403), except under the `local` trust profile (`isLocalUngated()`): with `MARINA_OPEN_API=true` on a loopback bind and no auth, the browser IS the single operator, so the Canvas dev write flow stays open. The Playwright canvas suite (`dashboard/e2e/canvas-server.ts`, which boots with `MARINA_OPEN_API=true`) exercises exactly this path; shared/public keep the sentinel read-only. Assets: MIME allowlist + magic-byte check (`normalizeAssetMime`), off-list → `application/octet-stream`; every asset response carries `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (PDF: no `sandbox`, stays inline for the iframe viewers), `Content-Disposition: attachment` for anything not raster image/audio/video/PDF. HTML surfaces get `nosniff`, `Referrer-Policy`, `X-Frame-Options: SAMEORIGIN`, `frame-ancestors 'self'` (no script-src CSP — the built dashboard needs inline styles/blob URLs). `Bun.serve` has an `error()` handler and `maxRequestBodySize` = max(`MARINA_MAX_REQUEST_BODY_BYTES` 8 MiB, `MARINA_MAX_UPLOAD_BYTES` 50 MiB). MCP transport: bearer required when `MODEL_API_KEYS`/`MARINA_AUTH` is set or the bind is non-loopback; `enableDnsRebindingProtection` always on + `MARINA_MCP_ALLOWED_HOSTS` (unset on a public bind ⇒ fail-closed derived list, `mcpAllowedHosts`); `MARINA_LOCAL_API_KEY` is a bearer only under the `local` profile (`localModelApiKey`; `main.ts` drops it elsewhere); `quoteArg` REJECTS whitespace/control chars in interpolated params (the command tokenizer has no quote grammar); the `flywheel` tool routes through `runCmd` (`code sandbox …`) so gates apply. Internal model token is 32 random bytes. `maskKey` shows last-4 only.
- **Host header validation** (`src/net/host-allowlist.ts`, shared by every listener): the main listener (all HTTP routes and the `/ws`, `/dashboard-ws`, `/canvas-ws` upgrades) answers only to loopback names (`localhost`, `127.x`, `[::1]`, any port), the `BETTER_AUTH_URL` host and `MARINA_ALLOWED_HOSTS` (`name` on any port, `name:port` exactly) when it binds loopback, runs the `local` trust profile, or the allowlist is set; anything else gets `421` naming the variable, and upgrades are refused. A public bind with no allowlist does not validate `Host` (set it to opt in). The standalone memory service (`serveMemory`) and the log viewer (`LogServer`, whose unauthenticated `/ws` feed also refuses a foreign browser `Origin`) apply the same rule through `refuseDisallowedHost`. A DNS name is never loopback, even when it resolves to 127.0.0.1. `isTrustedBrowserOrigin` (`src/net/cors.ts`) counts `Origin` == `Host` as same-origin only when that `Host` passed the listener's policy; `/mcp` uses `mcpAllowedHosts` (`MARINA_MCP_ALLOWED_HOSTS`) from the same module, and its own validation is unchanged. Bind resolution (`resolveBindHostname`, `loopbackBindFromEnv`) and the `/mcp` bearer rule (`transportAuthRequired`) live there too, so the ops posture report and the listeners read one definition.

## SSRF, gateway, dashboard scoping, adapters
- **SSRF protection**: `src/net/url-guard.ts` blocks private IPs, IPv6 loopback, link-local, cloud metadata, IPv4-mapped IPv6
- **Gateway auth**: optional `GATEWAY_SECRET` env var authenticates the gateway *handshake* (who may present as a `Gateway_`-named peer). It does **not** by itself fence bridged-channel participation or cross-instance tells — those are rank-0 commands open to any logged-in entity, so with passwordless name-login (default) a remote peer can still act as an ordinary local entity. For a hard federation boundary, also enable `MARINA_AUTH=better-auth` and don't expose open login.
- **Gateway protocol**: structured JSON fields with version number, regex fallback for backward compatibility
- **Terminal controls never travel**:
  - **Command input.** Every command is cleaned once, at the command phase (`CommandPhaseCoordinator.execute` → `stripControlSequences` in `src/net/ansi.ts`). This covers every transport and internal callers alike. Escape sequences (OSC titles, OSC 52 clipboard writes, OSC 8 links, cursor moves, screen clears), other C0/C1 control bytes and bidi overrides are removed whole; newline, tab and CRLF survive. So a `say`, a tell, a note or a post cannot carry instructions to another participant's terminal.
  - **Telnet output.** Output keeps only the server's own SGR colour (`keepSgr`), which also covers text that entered some other way.
  - **The `marina connect` CLI.** It applies its own client-side filter, `scripts/term-sanitize.ts`, for SGR only.
- **Untrusted framing in agent prompts**: peer- and memory-authored text cannot impersonate harness lines (one-line perceptions, escaped reserved markers, defused `<example>` closers — `src/agent/peer-text.ts`); external tool results are fenced as untrusted data and trust-tagged by effective command verb (`toolResultTrust`), so the reference monitor sees a `web fetch` run through `marina_command`; the continuity journal is never served as `[evidence]` and `x-marina-eval` turns are never journaled; `[trusted]` requires independent verification; `[crew-task]` is honoured only on the flagged dispatch path. See agent-cognition.md and memory.md.
- **Dashboard scoping**: broadcasts filter sensitive data (connectionId, raw command input stripped)
- **Asset ownership and write policy**: an upload is owned by the authenticated writer, the name `DELETE /api/assets/:id` authorizes by. A legacy `entity` form field or `?entity=` that names anyone else is a 403 `asset_owner_mismatch`, unless the writer is an operator (desktop token, rank-9 person, or the local-profile dev sentinel). The MIME policy (`src/storage/asset-mime.ts`: allowlist, magic bytes, `normalizeAssetMime`) applies on EVERY asset write path — `POST /api/assets`, `canvas asset upload` (scratch file or URL), `exec publish`, generated media and the desktop upload. Extension-only paths hint through `mimeFromExtension`, so `.html` is stored as `application/octet-stream`; a genuine raster image with the wrong label gets its sniffed type.
- **Media API identity** (`src/net/api/media-api.ts`): `POST /v1/media` runs as the authenticated model-API caller. A `secret:entity` key or run key is its bound entity, a session bearer is its entity, and anything else (a shared unbound key, dev-open mode) is the anonymous `system` caller. Only a trusted caller (the internal token, a multi-tenant `secret:*` key, an operator session) may name another entity with `entityId`/`entityName`; anyone else who names another entity gets a 403. That identity drives quotas, spend and job/asset ownership. `GET /v1/media/:id` returns a job only to its owner or a trusted caller (to anyone when ownership is not enforced: local-ungated or `open`); everyone else gets the same 404 as a missing id.
- **Private canvas reads** (`src/engine/canvas-access.ts`): one check decides whether principal P may read canvas C, node N or asset A, and every read path uses it. These paths are: the canvas WebSocket subscription (`authorizeCanvasSubscription`), the canvas HTTP API (`buildCanvasPrincipal`), `/api/assets` and `/assets/<key>`, every `canvas` subcommand that takes a canvas name or node or asset id, `image describe` / `video describe`, the `marina_see` agent tool and the MCP `canvas` tool (both run `canvas look`), the media `canvas:` target and journey `canvas_node` results.
  - **Who may read.** Canvases other than `entity` scope are public. An `entity` canvas is readable by its owner (`scope_id`) and by operators: rank 9, or `admin.destructive` held unsupervised (`canvasReaderFor`).
  - **In-world lifts.** These apply to commands, agent tools and MCP (`canvasReaderFor(…, { inWorld: true })`), not to the HTTP and WebSocket surfaces, which keep their rule from before this change.
    - The entity that spawned an agent (`agent_configs.spawned_by`, the creator relation challenges use) may read that agent's canvases. It never gets write access to them.
    - Under `isLocalUngated()`, the entity-canvas restriction is lifted for reads and writes, as it was before this change.
  - **Writes.** Writes through the `canvas` command (post, publish, connect, intents) need canvas-level write access: the owner, operators, or local-ungated. `layout`, `delete` and `disconnect` keep their ownership check.
  - **HTTP writes** (`src/net/canvas/canvas-api.ts`) follow the same ownership rule (`src/engine/canvas-ownership.ts`, `httpOwnershipRefusal`). `DELETE /api/canvases/:id` needs the canvas owner. `DELETE`/`PATCH` of a node and `DELETE` of a relationship need its author or the canvas owner. An admin (rank 9), the desktop operator credential or an `admin.destructive` holder may act on anything; under local-ungated or `open` anyone authenticated may. A refusal is 403 `not_owner` with the in-world explanation, and deleting a canvas or a relationship raises the same challenge as `canvas delete` / `canvas disconnect`. Creating nodes and relationships and the intent lifecycle endpoints stay open to any authenticated writer, and writes are attributed to the authenticated caller, never to a name in the body.
  - **Read budget.** Canvas and asset `GET`s are rate-limited: anonymous readers per client IP (`publicRead`, `clientIp`), principals per principal (a `dashboard`-sized budget kept apart from the dashboard REST bucket).
  - **Request inboxes.** A request inbox (`inbox:<owner>` with `entity` scope, from #281) holds other callers' private uploads, so neither lift applies to it in any profile. It is readable only by its owner, operators and grant holders, and the same holds for request-image assets.
  - **Grants.** Anyone else may read a single node only under an explicit `CanvasReadGrants` entry (`engine.canvasGrants`) naming that node and that principal, with an expiry. A grant covers reading only (`canvas look`, `GET /api/canvases/:id/nodes/:node`, the node's asset), never writes or the canvas listing. Grants are held in memory, because a grant outlives only its request and a restart ends the request.
  - **Request images.** Agents-mode `/v1/chat/completions` and `/v1/responses` grant a request's staged images (`stageRequestImages`) to the principals that serve it (`requestImageGrant`). These are every member of the endpoint's `model-<name>` channel plus the serving crew's members, for `MODEL_REQUEST_TIMEOUT_MS` plus 60 s. Knowing the node id is no longer enough. A consultant outside the channel and crew gets no grant.
  - **Assets.** An asset is private when it is a request image (`metadata.origin = "request"`, readable by its `owner`) or when every node that shows it is on a private canvas. A private asset is hidden from listings and is "not found" by id. Attaching it to another node, including over `POST /api/canvases/:id/nodes`, needs the same read access. Request-image bytes at `/assets/<key>` follow the check with the caller's bearer, desktop or loopback identity; a call with no identity is refused. Other assets' bytes stay capability URLs, so that `<img>` tags, which cannot send a bearer, keep rendering. The storage key is disclosed only through the gated reads.
  - **Signed asset URLs** (`src/net/api/asset-signing.ts`). `<img>`, `<video>`, `<audio>`, `<iframe>` and download links cannot send a bearer, so a remote dashboard viewer would be refused a request image it may read. `POST /api/assets/sign` (bearer required, `dashboard` rate limit, at most 100 paths) returns, for each `/assets/<key>` path the caller may read, either the plain URL (`expiresAt: null` — anyone may read it, or the caller is a sentinel that reads without a header) or `/assets/<key>?p=<entity id>&exp=<unix s>&sig=<HMAC-SHA256>` valid for 10 minutes; paths it may not read are omitted. The HMAC binds (asset id, principal, expiry) under a random per-process secret, so every signed URL dies on restart (the dashboard re-signs on demand). The signature is identity, never access: `/assets/<key>` runs the same read check as the signed principal, compares in constant time, and treats an expired, tampered, re-addressed or sentinel-naming signature as absent (an anonymous read). Signatures name real entities only — never the loopback, dev-open or desktop-operator sentinels. Gated responses carry `Cache-Control: private` (`max-age` up to the signature's expiry; `no-store` for header reads) instead of the public immutable caching of open assets. Request URLs (and so signatures) are not logged; assets are served with `Referrer-Policy: no-referrer`. The dashboard's `useAssetUrl` (`dashboard/src/lib/asset-url.ts`) batches signing, re-signs a minute before expiry and leaves loopback, sessionless pages and other origins untouched (the desktop shell reads bytes through its native adapter into `blob:` URLs instead of signing); pdf.js sends the bearer directly (`assetAuthHeaders`, this server's assets only) so a long document never outlives its URL.
  - **Derivatives** (thumbnails, posters, previews — `assets.derived_from`, migration 168) are exactly as readable as the asset they were made from: `mayReadAsset` follows `derived_from` to the parent, an orphan is refused, and `isGatedAssetBytes` gates a request image's thumbnails' bytes like the image itself. The library view (`GET /api/assets?view=library`, `src/net/api/asset-library-view.ts`) runs the read check per row for the viewer, counts facets over the viewer's visible set only, and signs private URLs with the same rule as `POST /api/assets/sign`. `PATCH /api/assets/:id` answers 404 to a writer who cannot read the asset and 403 to one who can but is neither the owner (or its agent's creator) nor an operator. `asset_*` events carry ids, owner and MIME only and go to the writer, the owner and operators.
  - **Refusals.** A refused read answers exactly like a missing one ("not found", HTTP 404), so it never confirms that a private node exists. Every refusal, grant and grant expiry is logged in the `canvas` Logger category.
- **Adapter persistence**: Discord/Telegram user mappings persisted to DB, auto-reconnect on restart

## Container workspaces (Code Mode)

`src/coding/container-workspace.ts`, configured per session by `code workspace runner …` (`src/engine/commands/code/runner.ts`) or for every local session by `MARINA_CODE_CONTAINER_IMAGE`. Files stay on the host; finite commands run inside an image.

- **Same gates, one spawn step swapped.** `ContainerWorkspace` extends `LocalWorkspace` and overrides only `spawnNormalized`. The allowlist (`normalizeAllowedCodeCommand`), the per-call `ExecApprover` and its `exec_decision` artifacts, the telnet chokepoint (`HostExecForbiddenError`) and the per-root lock run first, unchanged. Configuring a runner is in `CODE_EXEC_SUBCOMMANDS` (the `code.exec` gate, LAYER-0 telnet refusal, no-code-root refusal).
- **No host fallback.** A configured runner that cannot resolve (no podman/docker, an invalid image reference) becomes `UnavailableContainerWorkspace`: file operations work, every command fails with the reason. Host-side candidate dependency installation is refused too.
- **Containment flags** (`containerRunArgv`, unit-tested): `--rm`, `--network none` unless the runner opts in, `--cap-drop=ALL`, `--security-opt no-new-privileges`, `--pids-limit`, `--cpus`, `--memory`, a private `/tmp` tmpfs, and a timeout that also removes the container by name.
- **Mount sync**: the worktree is the only host path mounted (read-write at the workdir) on a `--read-only` root; the process runs as the host user (`--userns=keep-id` on Podman, `--user uid:gid` on Docker). Its git metadata is bound **read-only** on top (`gitMetadataPaths`: `.git`, and a worktree's `gitdir`/`commondir` when they live inside the worktree), so code run in the container cannot plant `core.fsmonitor`, hooks, `diff.external` or filter drivers that host git would later execute. A root without its own `.git`, or with a symlinked one, is refused: the container could otherwise create or redirect it. Git commands that write the repository therefore fail inside a mount-sync container.
- **Patch sync**: nothing from the host is mounted. The pending diff (`git diff HEAD --binary` plus untracked files, capped at 20 MB, refused rather than truncated) is fed on stdin and applied inside the throwaway container.
- **The command stays an argv.** The only shell text is the fixed patch step and the operator's `init` preamble (`MARINA_CODE_CONTAINER_INIT`); the validated command follows as `"$@"`. In-world `code workspace runner … -- <init>` is refused, and an `init` in a stored session setting is dropped on use, because a preamble runs outside the allowlist, the approver and the `exec_decision` audit.
- **Operator policy wins** (`operatorContainerPolicy` / `effectiveRunner` in `code/runner.ts`, applied on every use, so a setting stored earlier never outranks it). Containers are required when `MARINA_CODE_CONTAINER_REQUIRED=true`, or when it is unset and `MARINA_CODE_CONTAINER_IMAGE` is set. While required, `code workspace runner local` is refused and the image, runtime, sync, workdir, shell, network and init are the operator's; a session tunes only cpus, memory and timeout. Only `MARINA_CODE_CONTAINER_REQUIRED=false` (env) lets a session leave an operator image for the host. Without an operator image, a session-chosen image or `network:on` passes `checkGateForExecution` / `recordGateExecution` for `code.exec.unrestricted` (a refusal raises a challenge); network access survives on use only when the stored setting records that pass.
- **Host git is hardened** (`src/coding/host-git.ts`, the one helper every host git spawn in Code Mode goes through: `runCapture`, `runWorkspaceCommand`, candidate capture). Every call gets `-c core.fsmonitor=false -c core.hooksPath=/dev/null` (plus `core.sshCommand`, `credential.helper`, `gc.auto`/`maintenance.auto` overrides), `diff` gets `--no-ext-diff --no-textconv`, and the environment is minimal: `PATH`, a scratch `HOME`, `LANG=C`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` — no server secrets and no inherited `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`. This is the second layer behind the read-only mount, and it also covers host test runners that can write the repository.
- **Two environments, kept apart.**
  - **The runtime CLI** (podman/docker) runs with the operator's container configuration and storage. `HOME`, `XDG_*`, `CONTAINER_*`/`CONTAINERS_*` and `DOCKER_*` are captured from the server's own environment at startup (`captureRuntimeEnv`), not the scratch `HOME` that host Code Mode commands get. A fresh rootless store under that scratch HOME would re-pull every image, possibly onto a tmpfs `/tmp`.
  - **The process inside the container** sees none of it: only the fixed `-e` values (`CI`, `TERM`, `HOME=/tmp`), never `--env-host`.
  - **Overrides:** `MARINA_CODE_CONTAINER_STORAGE` / `_RUNROOT` (absolute paths, Podman only) become `--root` / `--runroot`.
  - **Warning:** `code doctor` shows the image store and warns loudly when it sits on tmpfs/ramfs or under the temp directory.

## Test-runner allowlist shapes

`code test` / `code verify` follow the detected project runner (`src/coding/project-detection.ts`). Like `bun run test`, a project's test suite executes repository code, so the non-JavaScript runners join the allowlist only in fixed shapes: `python -m pytest` with relative selectors or node ids and `-q -x -v -rA --no-header --tb=short|line`; `python manage.py test` and `python <path>/runtests.py` with dotted labels and `--verbosity=N` / `--parallel=N`; `cargo test [--quiet] [filter]`; `go test` with relative package patterns and `-count=N -short -v`; `python -m unittest` with `discover [-s dir] [-p pattern] [-t dir]` or dotted test names and `-q -v -f -b`; and an existing workspace test script (`python tests/….py`, `test_*.py`, `*_test.py`). Selectors are confined to the workspace like `bun test` paths; `python -c`, other modules, other scripts, absolute paths and bare `pytest` stay off the list (an exec approver can still approve them per call). When the detected pytest is not importable (the fixed `python -m pytest --version` probe), `code test` / `code verify` switch to the project's test script or `python -m unittest`; that command is one of the shapes above and runs through the same allowlist, approver and gates — the switch adds no exec path. Verification adds, in the same fixed style: `npm|pnpm|yarn run <script>` for the `bun run` script names, `<manager> run test [--] <relative paths>`, `python -m mypy` / `pyright` with relative paths, `npx --no-install tsc --noEmit [-p <relative tsconfig>]`, `uv run --frozen --no-sync <allowed python command>`, `mvn -B -q test [-Dtest=Class,…]` and `gradle test -q [--tests Class]`.

**Verification preparation** (`src/coding/verification-plan.ts`) is not a `code run` path. `runPreparationStep` accepts only exact argvs from a closed table: environment probes (`python -m pytest --version`, `python -c "import django"`, `test -d node_modules`, `go version`, `cargo --version`, `mvn -v`, `gradle --version`) and lockfile-frozen installs without lifecycle scripts (`npm ci --ignore-scripts`, `pnpm`/`yarn`/`bun install --frozen-lockfile --ignore-scripts`, `uv sync --frozen`). An install runs only where `installsPermitted()` is true: a container runner with mount sync (so the install persists) and network the operator enabled (`MARINA_CODE_CONTAINER_NETWORK`, or — without an operator image — a session `network:on` that passed the `code.exec.unrestricted` gate; see "Operator policy wins"). Otherwise the install step comes back `not_run` with its reason and never moves to the host. Host workspaces refuse installs; the only host install remains the hardened Bun candidate path (`candidate-dependencies.ts`). A requested manager for another language never runs. Pre-spawn authority refusals still abort the run (`VerificationStopped`), never recorded as a check outcome.

See also: `docs/authentication.md`, `docs/guides/identity.md`, `docs/guides/deployment.md`, `SECURITY.md`; `docs/architecture/civic-substrate.md` (gates, trust profile, exec approval).

## Dashboard Content-Security-Policy

Every HTML route (`/dashboard`, `/canvas`, `/who*`, `/chat`, `/ask`, the not-built placeholder) carries `HTML_CSP` from `http-utils.ts`: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; img-src 'self' data: blob:; media-src 'self' blob: data:; font-src 'self' data: https://fonts.gstatic.com; connect-src 'self' ws: wss:; worker-src 'self' blob:; frame-src 'self' https:; frame-ancestors 'self'; object-src 'none'; base-uri 'self'; form-action 'self'`. Grants beyond `'self'` exist for: Google Fonts (`index.html`, `unified-canvas.css`) and operator-supplied `embed` iframes (`CanvasNodeEmbed.tsx`, `components/media/MediaViewer.tsx`, sandboxed). `/chat` and `/ask` have inline scripts and get per-file `'sha256-…'` hashes appended — never `'unsafe-inline'` for scripts. `MARINA_DASHBOARD_CSP=off` drops the header; any other value is sent verbatim. Verified: 0 CSP console violations on all seven routes under Playwright. The pdf.js worker is bundled with the dashboard (`PdfNode.tsx` and the media viewer's lazily loaded `PdfPages.tsx` import `pdf.worker.min.mjs?url`), so it loads same-origin under `script-src 'self'` / `worker-src 'self'` and works offline.

## Daily spend cap and budget scopes

`src/engine/spend-ledger.ts` records every upstream dollar once, where it leaves Marina, and refuses spend at `MARINA_DAILY_SPEND_CAP_USD` (UTC day; default $50; `0`/`off` uncapped; junk keeps the default).

- **Pricing an agent turn.** An agent turn on a model pi-ai cannot price uses the Marina default-model list price (`src/agent/provider-cost.ts`), else the provider's reported `usage.cost`. Priced media jobs record under source `media` (migration 142).

- **One ledger per world database.** The engine attaches a sink over `spend_daily` (migration 131). Every command-line entry point that spends attaches the same `DB_PATH` ledger: `attachCliSpendLedger` in `src/engine/cli-spend-ledger.ts`, or `attachWorldSpend` for the forecasting adapters. Those entry points are `futurex`, `forecast`, `arena` (spending subcommands), `arena:portfolio`, `metaculus`, `forecastbench` and `qualify-decisions`. The cap is checked against the persisted day total, re-read on every check, so a timer that starts a new process each hour or a backtest in another process cannot get a fresh budget. The in-process view is the larger of the last persisted read and the process's own spend since, so a failed write or a closed database never lowers it.
- **Atomic across processes.** `addDailySpend` writes the global row and the scope row in one `BEGIN IMMEDIATE` transaction of upserts (`cost_usd = cost_usd + excluded.cost_usd`) on the WAL database with a 5 s busy timeout. Concurrent writers serialize, and no increment is lost (`test/spend-ledger-processes.test.ts` runs two writer processes). The check and the spend are not one transaction, so concurrent processes can overshoot the cap by the calls already in flight.
- **Shared ledger across processes** (`MARINA_SPEND_LEDGER=<path>`, `src/engine/shared-spend-ledger.ts`). A host that embeds Marina may run one process per world, each on its own world database, which would give each world its own cap. Every process that names the same file records into it and checks the global and scope caps against its one UTC-day total. The file is its own small SQLite database (WAL, 5 s busy timeout, mode 0600), not a world migration. It has the same `(day, source)` and `(day, scope, source)` keys, and each record is one `BEGIN IMMEDIATE` transaction of upserts. Spend is still written to the world database too, so per-world history and per-session cost readers keep working, but caps, `readiness` and Ops `spend.daily` read the shared total. Opening it is fail-closed: an unusable path throws instead of falling back to a per-world cap. A World Collective child inherits the file and the parent's global cap, and its own budget becomes scope `child:<name>` capped at min(`MARINA_CHILD_DAILY_SPEND_CAP_USD`, parent cap). If the parent runs under a scope, the child inherits that scope with its cap lowered to the same minimum (`childSpendEnv`).
- **Budget scopes** (migration 156, `spend_scope_daily`). With `MARINA_SPEND_SCOPE=<name>`, a process also records its dollars under that scope, capped by `MARINA_SPEND_SCOPE_CAP_USD` (default $50; `0`/`off` = no scope cap). The process is refused when EITHER cap is reached, so a scope only narrows the world budget and never widens it. An invalid scope name refuses all spend rather than dropping the scope cap. Callers that reserve ahead of spending (`dailyBudget`) use whichever cap has less headroom. Without a scope, the server's behaviour is unchanged.
- **Purposes** (`src/model/purpose.ts`). Every in-process library model call (`src/model`) names what it was for: forecast, arena, research, lessons, outcomes, swarm, judge, benchmark, agent or other. The dollar is recorded once under the purpose's source (forecast/arena/research → `forecast`; judge → `decision`; agent → `agent`; the rest → `model_api`) and, in the same transaction, under a `purpose:<name>` row in `spend_scope_daily`. Purpose rows are a breakdown, not a budget: `scopeSpendToday` skips them, `purposeSpendToday` reads them, they go to the world database only (never the shared ledger file), and `MARINA_SPEND_SCOPE` may not take the `purpose:` prefix. A loopback `marina/*` call is not recorded by the caller: the `/v1` passthru that serves it records it as `model_api`.
- **One stop for batch work** (`src/engine/spend-guard.ts`, `SpendGuard`).
  - `stopReason()` stops starting items while every item in flight can still finish. It holds a reserve against the job's own budget and against the daily caps.
  - `share(slots)` gives each concurrent unit an even share of what is left as a hard cap, so the shares never add up past the budget.
  - Its users are the FutureX clean backtest, the forecasting selection, the Metaculus bot and `swebench run --max-usd`.
  - It is not the per-call stop: BrowseComp-Plus checks `CallSpendGuard` (`benchmarks/call-spend-guard.ts`) before every model call and treats a tripped item as not run. The reproduction kit splits `--budget-usd` with `budgetShare` and `capEnvValue`, which rounds down and never writes `0`/`off`.
- **Recorded once:** the lesson judge's cost is recorded by the judge itself (`metered()` or `/v1`), never again by the learning service. The spawn-time tool probe is refused at the cap, and an inconclusive probe waits `INCONCLUSIVE_PROBE_RETRY_MS` before a spawn pays for another one. The Metaculus bot records a paid forecast it did not file as a `metaculus-attempt` row: the row counts against its daily budget, and the question is not forecast again that day.
- **Without a database** a command-line process counts in memory and prints one warning that the cap is per process.
- **Visibility:** `readiness` adds a `spend-scopes` check (this process's scope against its cap, plus every scope's spend today). Privileged Ops overviews carry `spend.daily` (world total, cap, per-scope totals), which the header spend chip shows in its tooltip. Both tables are `ledger`-class rows in `RETENTION_POLICIES`.

## Ops API

`GET /api/ops/overview` and `POST /api/ops/agents/:name/stop` live in `src/net/api/ops-api.ts` (contract `src/net/ops-types.ts`, re-exported type-only by `dashboard/src/lib/ops-types.ts` with a contract test). Scoped like the memory observability API: privileged principals see every agent; a resident sees its own transitive spawn lineage. The stop route is privileged (`authorizePrivileged(…, "agent.spawn")`) and cascades children-first, emitting one `agent_stop` event per agent. `mcpAuthRequired` and `loopbackBind` are computed by local mirrors of the mcp-server / websocket-server predicates (to avoid an import cycle) — change both together.
