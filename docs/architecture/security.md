# Security & API — Authentication, Rate Limits, HTTP Hardening, Gateway

**When to read this:** you are adding an HTTP route, an upload or asset path, an MCP transport change, a login path, rate limiting, external auth, SSRF-sensitive fetches, or federation. `CLAUDE.md` → "Security & API" states the invariants; this page is the complete reference, including HTTP hardening.

## Authentication and rate limiting
- **API authentication**: HTTP endpoints require `MODEL_API_KEYS` / `MEM_API_KEYS` or explicit `MARINA_OPEN_API=true` for dev mode. The dashboard/asset/canvas API auth gate (`authenticateRequest` in `src/net/auth-middleware.ts`) also honors `MARINA_OPEN_API=true`: a missing/invalid token is allowed through as the `OPEN_API_ENTITY_ID` sentinel (valid tokens still resolve to their real entity). Dev-only — never enable in production.
- **Rate limiting**: all endpoints rate-limited (token buckets built in `src/main.ts`) — WebSocket, telnet and MCP commands share one limiter keyed per entity (50/sec refill, burst 200), Model API 20/sec per IP (burst 100), Memory API 10/sec per agent (burst 20); the HTTP route limiters are listed under HTTP hardening below. The `local` trust profile sets `RateLimiter.bypass` except for buckets marked `ignoreBypass` (account-link codes).
- **Login limits**: `MARINA_MAX_LOGINS` caps concurrent entity-bound connections instance-wide (0 = unlimited); `MARINA_LOGIN_ATTEMPTS_PER_MIN` throttles login/reconnect attempts per IP (default 10, 0 = off). Enforced centrally in `engine.login()`/`reconnect()`; internal room/crew agents authenticate via the internal token (`internalToken` on the login/auth WS message) and are exempt from both. A refused reconnect says which it is (`reconnectRefusal`, `SessionManager.inspect`): a token this server never issued or has revoked, or a session that expired (idle, or the lifetime cap) and how long ago — plus how long the server has been up, so a client can tell a restart from a stale token; the content is never more than that
- **Account-link codes** (`src/engine/commands/link.ts`): `link` issues a 6-symbol CSPRNG code (5-minute expiry) that Telegram/Discord redeem via `redeemLinkCode` — a binding only; the login that follows still goes through `engine.login()`. Guessing is limited per external account (5 code-shaped attempts, +1 per 2 min) and globally on failures (30, +1 per 10 s); both buckets set `ignoreBypass`, so the `local` profile's `RateLimiter.bypass` never relaxes them. A limited attempt is not checked and falls through like ordinary text, so name login is never blocked.
- **Optional external auth (better-auth)**: OFF by default. `MARINA_AUTH=better-auth` enables email/password + social OAuth sign-in on the web surfaces and gates passwordless name-login (`engine.config.authRequired`). A verified identity is bridged to a *named* entity (the artilect stays the in-world identity); agents keep token auth. Admins by verified email (`MARINA_AUTH_ADMIN_EMAILS`), not name. Lazy-loaded provider in `src/auth/better-auth-provider.ts`, bridge in `src/net/api/auth-api.ts` (`/api/auth-status`, `/api/auth/*`, `POST /api/auth-session`), dashboard gate in `dashboard/src/components/AuthGate.tsx`. When off: no import, no routes, no schema effect. Setup: [docs/authentication.md](../authentication.md)

## HTTP hardening
- **HTTP hardening** (`src/net/http-utils.ts`): `clientIp(req, peer)` uses the socket peer unless `MARINA_TRUST_PROXY=true` and feeds EVERY per-IP limiter; named limiters `HTTP_RATE_LIMITS` (`dashboard` 60/10 s per principal, `mutation` 30/10 s for canvas/asset writes, `publicRead` 30/10 s for `/api/entity/*`, `mcpSession` 10/min per IP for MCP session/login/auth, `setupStatus` 20/min per IP for the pre-auth `/api/setup-status`, `authFailure` 20/min per IP consumed only by a rejected credential on `/v1`, the Ollama routes and `/mem` — `ignoreBypass`, so the `local` profile keeps it — `modelRead` 120/min per IP for `/v1/models`, `/api/tags` and health, `assetRead` 300/min per IP for `GET /assets/*`). `refuseOpenApiWrite()` (`src/net/auth-middleware.ts`) — the `OPEN_API_ENTITY_ID` sentinel is read-only on asset and canvas routes too (403), except under the `local` trust profile (`isLocalUngated()`): with `MARINA_OPEN_API=true` on a loopback bind and no auth, the browser IS the single operator, so the Canvas dev write flow stays open. The Playwright canvas suite (`dashboard/e2e/canvas-server.ts`, which boots with `MARINA_OPEN_API=true`) exercises exactly this path; shared/public keep the sentinel read-only. Assets: MIME allowlist + magic-byte check (`normalizeAssetMime`), off-list → `application/octet-stream`; every asset response carries `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (PDF: no `sandbox`, stays inline for the iframe viewers), `Content-Disposition: attachment` for anything not raster image/audio/video/PDF. HTML surfaces get `nosniff`, `Referrer-Policy`, `X-Frame-Options: SAMEORIGIN`, `frame-ancestors 'self'` (no script-src CSP — the built dashboard needs inline styles/blob URLs). `Bun.serve` has an `error()` handler and `maxRequestBodySize` = max(`MARINA_MAX_REQUEST_BODY_BYTES` 8 MiB, `MARINA_MAX_UPLOAD_BYTES` 50 MiB). MCP transport: bearer required when `MODEL_API_KEYS`/`MARINA_AUTH` is set or the bind is non-loopback; `enableDnsRebindingProtection` always on + `MARINA_MCP_ALLOWED_HOSTS` (unset on a public bind ⇒ fail-closed derived list, `mcpAllowedHosts` in `src/net/mcp/mcp-server.ts`); `MARINA_LOCAL_API_KEY` is a bearer only under the `local` profile (`localModelApiKey`; `main.ts` drops it elsewhere); `quoteArg` REJECTS whitespace/control chars in interpolated params (the command tokenizer has no quote grammar); the `flywheel` tool routes through `runCmd` (`code sandbox …`) so gates apply. Internal model token is 32 random bytes. `maskKey` shows last-4 only.
- **Host header validation** (`src/net/host-allowlist.ts`, shared by every listener): the main listener (all HTTP routes and the `/ws`, `/dashboard-ws`, `/canvas-ws` upgrades) answers only to loopback names (`localhost`, `127.x`, `[::1]`, any port), the `BETTER_AUTH_URL` host and `MARINA_ALLOWED_HOSTS` (`name` on any port, `name:port` exactly) when it binds loopback, runs the `local` trust profile, or the allowlist is set; anything else gets `421` naming the variable, and upgrades are refused. A public bind with no allowlist does not validate `Host` (set it to opt in). The standalone memory service (`serveMemory`) and the log viewer (`LogServer`, whose unauthenticated `/ws` feed also refuses a foreign browser `Origin`) apply the same rule through `refuseDisallowedHost`. A DNS name is never loopback, even when it resolves to 127.0.0.1. `isTrustedBrowserOrigin` (`src/net/cors.ts`) counts `Origin` == `Host` as same-origin only when that `Host` passed the listener's policy; `/mcp` keeps its own validation, `mcpAllowedHosts` (`MARINA_MCP_ALLOWED_HOSTS`) in `src/net/mcp/mcp-server.ts`. Bind resolution (`resolveBindHostname`, `loopbackBindFromEnv`) and the `/mcp` bearer rule (`transportAuthRequired`) live there too, so the ops posture report and the listeners read one definition.

## SSRF, gateway, dashboard scoping, adapters
- **Boot exposure checks** (called from `src/main.ts`): a non-loopback exposure with passwordless login, `MARINA_OPEN_API=true` or `open` posture (`bindSafetyRefusal` in `src/net/bind-safety.ts`), or a non-loopback bind with the `local` profile or `sovereign` (`assertTrustProfileSafe` in `src/engine/trust-profile.ts`), is fatal unless `MARINA_ALLOW_INSECURE_PUBLIC=true`. Exposure is the real bind, except that inside a container (`/.dockerenv` or `/run/.containerenv`) a wildcard bind whose `MARINA_PUBLISHED_HOST` is loopback counts as loopback (`publishedLoopback` in `src/net/loopback.ts`); `docker-compose.yml` passes `MARINA_PUBLISHED_HOST=${MARINA_BIND_IP:-127.0.0.1}` and no longer sets the insecure ack, so a routable `MARINA_BIND_IP` trips the refusal. The trust profile is still derived from the real bind.
- **Local agent host-command hold**: under the implicit `local` profile an agent's `shell.exec` and `code.exec.unrestricted` are held for a person (see `docs/architecture/civic-substrate.md`); `MARINA_AUTONOMY=sovereign` lifts it.
- **SSRF protection**: `src/net/url-guard.ts` blocks private IPs, IPv6 loopback, link-local, cloud metadata, IPv4-mapped IPv6
- **Gateway auth**: `GATEWAY_SECRET` authenticates the gateway *handshake* (who may present as a `Gateway_`-named peer). On the `shared`/`public` profiles it is required for inbound federation: without it every `gateway_auth` frame and `Gateway_` login is refused with the remediation (`gatewayIngressRefusal` in `src/engine/gateway-runtime.ts`, checked in `websocket-server.ts`; boot log line; readiness `federation-inbound`). Only the `local` profile accepts peers without a secret. It does **not** by itself fence bridged-channel participation or cross-instance tells — those are rank-0 commands open to any logged-in entity, so with passwordless name-login (default) a remote peer can still act as an ordinary local entity. For a hard federation boundary, also enable `MARINA_AUTH=better-auth` and don't expose open login.
- **Gateway protocol**: structured JSON fields with version number, regex fallback for backward compatibility
- **Terminal controls never travel**:
  - **Command input.** Every command is cleaned once, at the command phase (`CommandPhaseCoordinator.execute` → `stripControlSequences` in `src/net/ansi.ts`). This covers every transport and internal callers alike. Escape sequences (OSC titles, OSC 52 clipboard writes, OSC 8 links, cursor moves, screen clears), other C0/C1 control bytes and bidi overrides are removed whole; newline, tab and CRLF survive. So a `say`, a tell, a note or a post cannot carry instructions to another participant's terminal.
  - **Telnet output.** Output keeps only the server's own SGR colour (`keepSgr`), which also covers text that entered some other way.
  - **The `marina connect` CLI.** It applies its own client-side filter, `scripts/term-sanitize.ts`, for SGR only.
- **Untrusted framing in agent prompts**: peer- and memory-authored text cannot impersonate harness lines (one-line perceptions, escaped reserved markers, defused `<example>` closers — `src/agent/peer-text.ts`); external tool results are fenced as untrusted data and trust-tagged by effective command verb (`toolResultTrust`), so the reference monitor sees a `web fetch` run through `marina_command`; the continuity journal is never served as `[evidence]` and `x-marina-eval` turns are never journaled; `[trusted]` requires independent verification; `[crew-task]` is honoured only on the flagged dispatch path. See agent-cognition.md and memory.md.
- **Dashboard scoping**: broadcasts filter sensitive data (connectionId, raw command input stripped); an entity's raw command input, full properties and core memory are served only to the entity itself, the person who owns it (the first person up its spawn chain — never an agent, so a sibling or child agent gains nothing), and privileged readers (`src/net/entity-visibility.ts`, shared by the snapshot, `GET /api/entities/:name` — which gives everyone else a public view — and the name-scoped memory routes, which refuse everyone else via `authorizeEntityRead`); individual notes keep the memory system's own owner/pool ACL
- **Asset ownership and write policy**: an upload is owned by the authenticated writer, the name `DELETE /api/assets/:id` authorizes by. A legacy `entity` form field or `?entity=` that names anyone else is a 403 `asset_owner_mismatch`, unless the writer is an operator (desktop token, rank-9 person, or the local-profile dev sentinel). The MIME policy (`src/storage/asset-mime.ts`: allowlist, magic bytes, `normalizeAssetMime`) applies on EVERY asset write path — `POST /api/assets`, `canvas asset upload` (scratch file or URL), `exec publish`, generated media and the desktop upload. Extension-only paths hint through `mimeFromExtension`, so `.html` is stored as `application/octet-stream`; a genuine raster image with the wrong label gets its sniffed type.
- **Media API identity** (`src/net/api/media-api.ts`): `POST /v1/media` runs as the authenticated model-API caller. A `secret:entity` key or run key is its bound entity, a session bearer is its entity, and anything else (a shared unbound key, dev-open mode) is the anonymous `system` caller. Only a trusted caller (the internal token, a multi-tenant `secret:*` key, an operator session) may name another entity with `entityId`/`entityName`; anyone else who names another entity gets a 403. That identity drives quotas, spend and job/asset ownership. `GET /v1/media/:id` returns a job only to its owner or a trusted caller (to anyone when ownership is not enforced: local-ungated or `open`); everyone else gets the same 404 as a missing id.
- **Private canvas reads** (`src/engine/canvas-access.ts`): one check decides whether principal P may read canvas C, node N or asset A, and every read path uses it. These paths are: the canvas WebSocket subscription (`authorizeCanvasSubscription`), the canvas HTTP API (`buildCanvasPrincipal`), `/api/assets` and `/assets/<key>`, every `canvas` subcommand that takes a canvas name or node or asset id, `image describe` / `video describe`, the `marina_see` agent tool and the MCP `canvas` tool (both run `canvas look`), the media `canvas:` target and journey `canvas_node` results.
  - **Who may read.** Canvases other than `entity` scope are public. An `entity` canvas is readable by its owner (`scope_id`) and by operators: rank 9, or `admin.destructive` held unsupervised (`canvasReaderFor`).
  - **In-world lifts.** These apply to commands, agent tools and MCP (`canvasReaderFor(…, { inWorld: true })`), not to the HTTP and WebSocket surfaces, which keep their rule from before this change.
    - The entity that spawned an agent (`agent_configs.spawned_by`, the creator relation challenges use) may read that agent's canvases. It never gets write access to them.
    - Under `isLocalUngated()`, the entity-canvas restriction is lifted for reads and writes, as it was before this change.
  - **Writes.** Writes through the `canvas` command (post, publish, connect, intents) need canvas-level write access: the owner, operators, or local-ungated. `layout`, `delete` and `disconnect` keep their ownership check.
  - **HTTP writes** (`src/net/canvas/canvas-api.ts`) follow the same ownership rule (owners from `src/engine/canvas-ownership.ts`, the refusal from `httpOwnershipRefusal` in `src/net/owner-authorization.ts`). `DELETE /api/canvases/:id` needs the canvas owner. `DELETE`/`PATCH` of a node and `DELETE` of a relationship need its author or the canvas owner. An admin (rank 9), the desktop operator credential or an `admin.destructive` holder may act on anything; under local-ungated or `open` anyone authenticated may. A refusal is 403 `not_owner` with the in-world explanation, and deleting a canvas or a relationship raises the same challenge as `canvas delete` / `canvas disconnect`. Creating nodes and relationships and the intent lifecycle endpoints stay open to any authenticated writer, and writes are attributed to the authenticated caller, never to a name in the body.
  - **Read budget.** Canvas and asset `GET`s are rate-limited: anonymous readers per client IP (`publicRead`, `clientIp`), principals per principal (a `dashboard`-sized budget kept apart from the dashboard REST bucket).
  - **Request inboxes.** A request inbox (`inbox:<owner>` with `entity` scope, from #281) holds other callers' private uploads, so neither lift applies to it in any profile. It is readable only by its owner, operators and grant holders, and the same holds for request-image assets.
  - **Grants.** Anyone else may read a single node only under an explicit `CanvasReadGrants` entry (`engine.canvasGrants`) naming that node and that principal, with an expiry. A grant covers reading only (`canvas look`, `GET /api/canvases/:id/nodes/:node`, the node's asset), never writes or the canvas listing. Grants are held in memory, because a grant outlives only its request and a restart ends the request.
  - **Request images.** Agents-mode `/v1/chat/completions` and `/v1/responses` grant a request's staged images (`stageRequestImages`) to the principals that serve it (`requestImageGrant`). These are every member of the endpoint's `model-<name>` channel plus the serving crew's members, for `MODEL_REQUEST_TIMEOUT_MS` plus 60 s. Knowing the node id is no longer enough. A consultant outside the channel and crew gets no grant.
  - **Assets.** An asset is private when it is a request image (`metadata.origin = "request"`, readable by its `owner`) or when every node that shows it is on a private canvas. A private asset is hidden from listings and is "not found" by id. Attaching it to another node, including over `POST /api/canvases/:id/nodes`, needs the same read access. Request-image bytes at `/assets/<key>` follow the check with the caller's bearer, desktop or loopback identity; a call with no identity is refused. Other assets' bytes stay capability URLs, so that `<img>` tags, which cannot send a bearer, keep rendering. The storage key is disclosed only through the gated reads.
  - **Signed asset URLs** (`src/net/api/asset-signing.ts`). `<img>`, `<video>`, `<audio>`, `<iframe>` and download links cannot send a bearer, so a remote dashboard viewer would be refused a request image it may read. `POST /api/assets/sign` (bearer required, `dashboard` rate limit, at most 100 paths) returns, for each `/assets/<key>` path the caller may read, either the plain URL (`expiresAt: null` — anyone may read it, or the caller is a sentinel that reads without a header) or `/assets/<key>?p=<entity id>&exp=<unix s>&sig=<HMAC-SHA256>` valid for 10 minutes; paths it may not read are omitted. The HMAC binds (asset id, principal, expiry) under a random per-process secret, so every signed URL dies on restart (the dashboard re-signs on demand). The signature is identity, never access: `/assets/<key>` runs the same read check as the signed principal, compares in constant time, and treats an expired, tampered, re-addressed or sentinel-naming signature as absent (an anonymous read). Signatures name real entities only — never the loopback, dev-open or desktop-operator sentinels. Gated responses carry `Cache-Control: private` (`max-age` up to the signature's expiry; `no-store` for header reads) instead of the public immutable caching of open assets. Request URLs (and so signatures) are not logged; assets are served with `Referrer-Policy: no-referrer`. The dashboard's `useAssetUrl` (`dashboard/src/lib/asset-url.ts`) batches signing, re-signs a minute before expiry and leaves loopback, sessionless pages and other origins untouched (the desktop shell reads bytes through its native adapter into `blob:` URLs instead of signing); pdf.js sends the bearer directly (`assetAuthHeaders`, this server's assets only) so a long document never outlives its URL.
  - **Derivatives** (thumbnails, posters, previews — `assets.derived_from`, migration 168) are exactly as readable as the asset they were made from: `mayReadAsset` follows `derived_from` to the parent, an orphan is refused, and `isGatedAssetBytes` gates a request image's thumbnails' bytes like the image itself. The library view (`GET /api/assets?view=library`, `src/net/api/asset-library-view.ts`) runs the read check per row for the viewer, counts facets over the viewer's visible set only, and signs private URLs with the same rule as `POST /api/assets/sign`. `PATCH /api/assets/:id` answers 404 to a writer who cannot read the asset and 403 to one who can but is neither the owner (or its agent's creator) nor an operator. `asset_*` events carry ids, owner and MIME only and go to the writer, the owner and operators.
  - **Refusals.** A refused read answers exactly like a missing one ("not found", HTTP 404), so it never confirms that a private node exists. Every refusal, grant and grant expiry is logged in the `canvas` Logger category.
- **Adapter persistence**: Discord/Telegram user mappings persisted to DB, auto-reconnect on restart

## Container workspaces (Code Mode)

`src/coding/container-workspace.ts`, configured per session by `code workspace runner …` (`src/engine/commands/code/runner.ts`) or for every local session by `MARINA_CODE_CONTAINER_IMAGE`. Files stay on the host; finite commands run inside an image.

- **Same gates, one spawn step swapped.** `ContainerWorkspace` extends `LocalWorkspace` and overrides only `spawnNormalized`. The allowlist (`normalizeAllowedCodeCommand`), the per-call `ExecApprover` and its `exec_decision` artifacts, the telnet chokepoint (`HostExecForbiddenError`) and the per-root lock run first, unchanged. Configuring a runner is in `CODE_EXEC_SUBCOMMANDS` (the `code.exec` gate, LAYER-0 telnet refusal, no-code-root refusal).
- **No host fallback.** A configured runner that cannot resolve (no podman/docker, an invalid image reference) becomes `UnavailableContainerWorkspace`: file operations work, every command fails with the reason. Host-side candidate dependency installation is refused too.
- **Per-destination egress** (`src/coding/egress-proxy.ts`, podman only): with an operator allowlist (`MARINA_CODE_CONTAINER_EGRESS`) the container runs on `pasta:--splice-only,-T,<port>` — loopback and one forwarded port, no route and no DNS — and that port is an in-process CONNECT/HTTP proxy living for exactly one run. A destination passes only when the allowlist names its host and port AND `resolveGuardedHost` (the SSRF guard) finds every address public; the upstream is pinned to the checked address. Refusals are a readable `403` plus a `[marina egress] blocked …` line in the command's output. A destination refused only for being unlisted (`approvable`) raises a challenge from `code run` (`raiseEgressChallenge`, kind `tool`, tool `egress`): a person's approval records an `egress_grant` session artifact (`grantSessionEgress`) and re-runs the command in the requester's slot. Grants extend an operator allowlist only (`withEgressGrants`) — they never create network where the operator gave none — and an address the SSRF guard refused is never offered.
- **Model access without credentials** (`MARINA_CODE_CONTAINER_MODEL_API`, needs an allowlist): the reserved host `marina.model` exists only inside the proxy. A plain-HTTP request whose WHATWG-normalized path starts with `/v1/` goes to Marina's loopback listener with `Authorization: Bearer <run key>` replacing any caller credential (`marinaModelHead`); `CONNECT`, other paths (`/api`, `/mem`, traversal) and runners without the setting get a non-approvable 403. The run key (`benchmark-run-keys.ts`) is minted per command, bound to the session owner, capped (`MARINA_CODE_CONTAINER_MODEL_CAP_USD`) and revoked when the command ends; the container's environment holds only the placeholder `marina`. HTTPS is filtered by host and port, never decrypted. The list is operator-only (stripped from session settings like `init`); Docker with a list is refused, never left unenforced.
- **Containment flags** (`containerRunArgv`, unit-tested): `--rm`, `--network none` unless the runner opts in, `--cap-drop=ALL`, `--security-opt no-new-privileges`, `--pids-limit`, `--cpus`, `--memory`, a private `/tmp` tmpfs, and a timeout that also removes the container by name.
- **Mount sync**: the worktree is the only host path mounted (read-write at the workdir) on a `--read-only` root; the process runs as the host user (`--userns=keep-id` on Podman, `--user uid:gid` on Docker). Its git metadata is bound **read-only** on top (`gitMetadataPaths`: `.git`, and a worktree's `gitdir`/`commondir` when they live inside the worktree), so code run in the container cannot plant `core.fsmonitor`, hooks, `diff.external` or filter drivers that host git would later execute. A root without its own `.git`, or with a symlinked one, is refused: the container could otherwise create or redirect it. Git commands that write the repository therefore fail inside a mount-sync container.
- **Patch sync**: nothing from the host is mounted. The pending diff (`git diff HEAD --binary` plus untracked files, capped at 20 MB, refused rather than truncated) is fed on stdin and applied inside the throwaway container.
- **The command stays an argv.** The only shell text is the fixed patch step and the operator's `init` preamble (`MARINA_CODE_CONTAINER_INIT`); the validated command follows as `"$@"`. In-world `code workspace runner … -- <init>` is refused, and an `init` in a stored session setting is dropped on use, because a preamble runs outside the allowlist, the approver and the `exec_decision` audit.
- **Operator policy wins** (`operatorContainerPolicy` / `effectiveRunner` in `code/runner.ts`, applied on every use, so a setting stored earlier never outranks it). Containers are required when `MARINA_CODE_CONTAINER_REQUIRED=true`, or when it is unset and `MARINA_CODE_CONTAINER_IMAGE` is set. While required, `code workspace runner local` is refused and the image, runtime, sync, workdir, shell, network and init are the operator's; a session tunes only cpus, memory and timeout. Only `MARINA_CODE_CONTAINER_REQUIRED=false` (env) lets a session leave an operator image for the host. Without an operator image, a session-chosen image or `network:on` passes `checkGateForExecution` / `recordGateExecution` for `code.exec.unrestricted` (a refusal raises a challenge); network access survives on use only when the stored setting records that pass.
- **Host git is hardened** (`src/coding/host-git.ts`, the one helper every host git spawn in Code Mode goes through: `runCapture`, `runWorkspaceCommand`, candidate capture). Every call gets `-c core.fsmonitor=false -c core.hooksPath=/dev/null` (plus `core.sshCommand`, `credential.helper`, `gc.auto`/`maintenance.auto`, `commit.gpgSign`/`tag.gpgSign`/`log.showSignature` overrides), `diff` gets `--no-ext-diff --no-textconv`, every content driver the repository's config names is switched off (`hostGitDriverOverrides`: `filter.<n>.clean|smudge|process` empty with `required=false`, so content is hashed as stored; `diff.<n>.textconv` an absolute `cat`, `diff.<n>.command` and `diff.external` the builtin `true`; `merge.<n>.driver` the builtin `false`, so such a merge reports a conflict; every configured hook `hook.<n>` gets `event=` and `enabled=false`, because `core.hooksPath` does not reach config-defined hooks — driver and hook names are read with `git config --get-regexp`, which runs nothing; a name `-c` cannot carry fails closed), and the environment is minimal: `PATH`, a scratch `HOME`, `LANG=C`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` — no server secrets and no inherited `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`. This is the second layer behind the read-only mount, and it also covers host test runners that can write the repository.
- **Two environments, kept apart.**
  - **The runtime CLI** (podman/docker) runs with the operator's container configuration and storage. `HOME`, `XDG_*`, `CONTAINER_*`/`CONTAINERS_*` and `DOCKER_*` are captured from the server's own environment at startup (`captureRuntimeEnv`), not the scratch `HOME` that host Code Mode commands get. A fresh rootless store under that scratch HOME would re-pull every image, possibly onto a tmpfs `/tmp`.
  - **The process inside the container** sees none of it: only the fixed `-e` values (`CI`, `TERM`, `HOME=/tmp`), never `--env-host`.
  - **Overrides:** `MARINA_CODE_CONTAINER_STORAGE` / `_RUNROOT` (absolute paths, Podman only) become `--root` / `--runroot`.
  - **Warning:** `code doctor` shows the image store and warns loudly when it sits on tmpfs/ramfs or under the temp directory.

## Local sandbox runner (Code Mode)

`src/coding/sandbox-workspace.ts`, selected per session by `code workspace runner sandbox` (`src/engine/commands/code/runner.ts`), for every local session by `MARINA_CODE_SANDBOX=default`, or as the only runner by `MARINA_CODE_SANDBOX=required` (`marina --sandbox`). Files stay on the host; finite commands run inside a bubblewrap (`bwrap`) sandbox, and the sandbox, not the argv shape, is the boundary.

- **Any command, same gates around it.** `SandboxWorkspace` extends `LocalWorkspace`, overrides `run` to skip the allowlist and the exec approver (argv straight through; `sh -c '<line>'` is how shell syntax arrives — `code run` tokenizes with quotes via `parseCommandArgv`, and `SHELL_METACHARACTERS` rejection stays on the host allowlist path only) and overrides `spawnNormalized` to wrap the argv in bwrap. Selecting the runner is in `CODE_EXEC_SUBCOMMANDS` (the `code.exec` gate, LAYER-0 telnet refusal); running needs `code.exec` like any `code run`. The telnet chokepoint (`HostExecForbiddenError`) still refuses before anything spawns. Verification follows the runner: under the sandbox, `runAllowlisted` (background, candidate and delivery checks) and the verification admission accept any command as well, run in the same bwrap and prlimit wrapper with the same pins, in the snapshot directory for a candidate or delivery check; every non-sandbox path keeps the allowlist.
- **Trusted launchers.** `bwrap` is `/usr/bin/bwrap`, else `/bin/bwrap`, else the operator's absolute `MARINA_CODE_SANDBOX_BWRAP`; `prlimit` is `/usr/bin/prlimit` or `/bin/prlimit`. Neither is ever looked up through PATH. Each must be a regular file owned by root or the server user, not group- or world-writable, in a directory that is not world-writable, and outside the workspace and every task root; a present-but-untrusted candidate fails closed rather than falling through to the next. bubblewrap must be 0.10 or newer (`--size`, `--disable-userns`).
- **Isolation flags** (`sandboxArgv`, unit-tested): `--unshare-all --unshare-user` (user, pid, ipc, uts, cgroup and **network** namespaces: only a private loopback), `--disable-userns` (no nested user namespaces inside), `--die-with-parent`, `--new-session` (no `TIOCSTI` into the server's terminal), `--cap-drop ALL`, `--clearenv` then only `TERM`, `LANG`, `CI`, `PATH`, `TMPDIR` and `HOME=/tmp/home`. A fresh `/proc` for the sandbox's own pid namespace (the server's `/proc/<pid>/environ` is not visible), a minimal `/dev` remounted read-only (`/dev/null` works, nothing can be created) with its own `/dev/shm`, a private `/tmp`. Every tmpfs is capped with `--size`: `/tmp` and the masked home by `MARINA_CODE_SANDBOX_TMPFS_MB` (default 1024 each), `/dev/shm` by `MARINA_CODE_SANDBOX_SHM_MB` (default 64). The command runs under `prlimit --nproc --as --fsize --core=0` (`MARINA_CODE_SANDBOX_NPROC` 4096, `_AS_MB` 16384, `_FSIZE_MB` 4096); no prlimit, no run.
- **Filesystem.** The system directories are bound read-only one by one (`/usr`, `/bin`, `/sbin`, `/lib*`, `/etc`, `/opt`, `/nix`; merged-`/usr` symlinks recreated), never `/` wholesale, so `/run` (agent and bus sockets such as ssh-agent, gpg-agent, D-Bus, the podman socket), `/var`, `/home`, `/root`, `/mnt` and `/media` are absent. The user's home is masked with an empty tmpfs; only the Bun executable is bound back read-only (its directory only when it holds nothing but `bun`/`bunx`; never HOME, a directory containing HOME, or a shared bin such as `~/.local/bin`). Mount order: system, tmpfs, Bun, the workspace read-write, read-only task roots, the pins (below), and the git metadata read-only LAST so no later mount shadows it — `.git`, a linked worktree's gitdir, its common dir, `<common>/modules` and object alternates.
- **Pins.** A path inside the work tree that host git will later read or run is held in place for the command: every directory from the root down to it is bound onto itself (a mount point cannot be renamed, moved or replaced — `mv` fails with "Device or resource busy") and the target is bound read-only. Pinned: every submodule's `.git` (gitfile or directory), recursively — a submodule's own index, read with hardened git from `<modules>/<name>` (`-c core.quotePath=false ls-files -s -z`, so quoted or non-ASCII paths are matched), lists the nested ones. An uninitialised submodule's empty directory is bound read-only as a whole, and an absent gitlink directory gets an empty, read-only tmpfs (bubblewrap creates the empty mount-point directory), so no `.git` can appear there during a command. Program-naming git config is scanned key by key — EVERY key of every config file visited (the repository's local, worktree and common config, each submodule's module config, the person's global, XDG and system config, and everything those include), read per file with hardened git (`--no-includes --null --list`); nothing in them is executed. Git runs config commands with the work-tree root as cwd, and every key is treated as one git may run unless it is in the ONE data-only list (`DATA_ONLY_GIT_CONFIG` in `sandbox-workspace.ts`: whole sections such as `user`, `branch`, `init`, `color`, `log`, `format`, `status`, `safe`, `pull`, `push`, `fetch`, plus single keys such as `remote.*.url|fetch|push` and `submodule.*.url`; a plain non-`!` alias is git arguments), so new git features such as `hook.<name>.command` are covered by default. Then: (a) shell expansion (`$`, a backtick) in an executable key, and every content driver — `filter.*.clean|smudge|process`, `diff.*.textconv|command`, `diff.external`, `merge.*.driver` — is **supported and reported**, not pinned: an in-tree path built at run time cannot be pinned, and a driver's program can read work-tree files it does not name (an interpreter's `-m module`, a tool's own config). Each one becomes a `GitExposure` (key and file, never the value) and the literal in-tree programs it names are still pinned where they can be (see "Content drivers and shell expansion" below). git-lfs's own filters (`git-lfs clean -- %f`, `git-lfs smudge -- %f`, `git-lfs filter-process`, the program a bare name or an absolute path outside the tree) are neither reported nor run inside; an lfs program inside the tree is refused; an `ext::` transport URL is refused (it runs a command on the person's fetch or push); (b) every path-like token (contains `/`, or starts with `.` or `~`; URLs and refspecs excepted; `core.hooksPath` even as a bare word) that resolves inside the tree is pinned read-only — so husky- or lefthook-style hook directories such as `.husky/` are **read-only inside the sandbox**. In the other executable keys a path that does not exist yet, a symlink on the way, or other shell syntax around an in-tree path refuses the layout. Refusals name the key and the file only, never the value: a person's global config can hold a credential, and refusals reach the agent. A server `PATH` with a relative or empty entry is refused too, because a bare program name in config would then resolve to a file the sandbox can write. The check reads the SERVER's PATH (the environment Marina and its host git run with), not the person's interactive shell PATH, which Marina cannot see; a person whose own PATH has a relative entry runs that risk with their own git.
- **Content drivers and shell expansion.** The property kept: nothing sandboxed code writes in the work tree runs outside the sandbox through a process Marina starts. (1) Marina's own git work that needs a filter — `SandboxWorkspace.diff`, `changedPaths`, the candidate tree (`captureCandidate`, `stagedEntries("index")`) and the HEAD-based snapshot `code trial` / `code ship` commit (`snapshotTree`) — runs git INSIDE the sandbox (same layout, pins and submodule checks as any command) with `.git` read-only, a private index and object directory in a host scratch directory bound at `/tmp` (`GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, the repository's objects as `GIT_ALTERNATE_OBJECT_DIRECTORIES`), and a generated global config holding only the driver definitions of the person's own config files plus a copy of their global attributes file (their home is hidden there); git-lfs filters, hooks and fsmonitor are off inside. The results come back as files read as data only (`O_NOFOLLOW`, regular file, bounded): `ls-files -s -z` entries (stage 0, known modes, no `..`/`.git`/absolute path) and a `cat-file --batch` stream of the new objects; host git then writes each missing blob itself with `hash-object -w --no-filters` and refuses one whose bytes do not hash to the claimed oid, and builds the tree with `update-index --index-info` / `write-tree` in a fresh index. The candidate keeps raw bytes for its materialized copy and fingerprint; only its tree takes the staged blobs. (2) Host git never runs them: `hostGitDriverOverrides` switches off every driver AND every configured hook (`hook.<name>.event=` and `.enabled=false`: `core.hooksPath=/dev/null` does not reach `hook.<name>.command`, which git 2.5x runs on `update-ref`, `commit` and checkout), `HOST_GIT_CONFIG_ARGS` add `commit.gpgSign=false` / `tag.gpgSign=false` / `log.showSignature=false` (`commit-tree` honours `commit.gpgSign`), and the git that `code trial`, `code ship` and the version stamps (`sourceRevision`, `run-version.ts`) start now uses `hostGitEnv` and the driver overrides instead of the server's environment and the person's global config. `code ship`'s push and `gh` keep the operator's credentials but run with `publishEnv`: the same overrides as `GIT_CONFIG_*` entries, which bind every git `gh` starts (its `git status` would otherwise run the clean filter). (3) The person's own later git does run them, on the host, with the work tree as cwd; no pin can say what such a program reads. That residual is made explicit: `code workspace runner` and the start line name the settings (`gitExposureStartNotice`); when a session ends (`code done`, before its worktree is cleaned up; the end of `marina --sandbox`) and in `code ship`, `gitExposureReport` lists every file under the work tree (ignored files included, `.git` skipped) whose ctime is at or after the session's start — ctime cannot be set back by an unprivileged process — 20 by name with a count of the rest. `code ship` refuses to push for a sandboxed session whose push would run a shell-expanded credential helper, SSH/askpass command, remote pack program or signing setting (`publishExposureRefusal`); the person pushes. Kept refused: `ext::` transports (no way to show what they run) and includes of writable in-tree config (sandboxed code would write config itself).
- **Existing git hooks are reported, not refused.** Executable, non-`.sample` files in the hooks directory (`<common>/hooks`, or any `core.hooksPath`) and `hook.<name>.command` settings are listed at layout. Generated hooks (pre-commit's `$INSTALL_PYTHON -mpre_commit`, husky's scripts) run from the work-tree root and read work-tree code and configuration that the sandbox could change; the hook files themselves are read-only inside the sandbox, but what they run is not. `code start`, `code workspace runner` and every sandboxed command result say plainly that the project has git hooks that run work-tree code and that a person should review the changes before their next commit. The sandbox's guarantee is therefore narrower in such a project: it holds git metadata and every program configuration names, not the code a project's own hooks choose to run.
- **Refused layouts** (`resolveSandboxLayout`, re-checked before every command): a root without its own `.git` or with a symlinked one; a gitdir or common dir inside the work tree anywhere but `<root>/.git` (renaming its parent would swap it); a local, worktree or common git config whose `include.path` / `includeIf.*.path` (followed recursively, read with hardened host git, never executed) resolves inside the work tree or a task root; a workspace that contains HOME, a system directory, or the server's own state (`DB_PATH`, `MARINA_SPEND_LEDGER`, `~/.marina` with the folder instances' `.env` files, the server's working-directory `.env` — so the Marina checkout that holds the live `marina.db` cannot be a sandbox root); writable task roots (not supported yet: a writable root without `.git` could get a planted one); a read-only task root that overlaps the workspace, its git metadata, a system directory, contains HOME, or contains the server's own state (a read root over `~/.marina` would expose instance `.env` files).
- **Submodules.** Before each command every gitlink (recursively; names from the INDEX's `.gitmodules`, never the writable work-tree copy) is pinned as above and its `.git` state recorded. A gitfile that does not point into `<modules>/…`, a `.git` directory at a gitlink path while `<modules>/<name>` exists, or any other `.git` (a symlink) refuses the run. After the command the recorded states are compared again as a backstop: any change fails the command with a security notice, restores nothing, and holds the WORKSPACE ROOT (core-memory owner `sandbox:hold`, keyed by the root's realpath): every command on that tree — any session, a new `code start` included, any runner — fails until a person (never an agent) runs `code workspace runner release`. A hold raises a critical ops-inbox item (`sandbox-hold:<root>`, assigned to the session's owner, visible to operators) and a `sandbox.hold` notice through `MARINA_OPS_NOTIFY`; release resolves the item. The checks exist because a person's own later plain `git status` in such a repository runs whatever a submodule's config names (`core.fsmonitor`); Marina's host git never descends into submodules (`diff.ignoreSubmodules=all`, `submodule.recurse=false`), a person's git does.
- **No host fallback.** A missing or untrusted launcher, a refused layout, or `MARINA_CODE_SANDBOX=off` for a stored sandbox setting yields `UnavailableSandboxWorkspace`: file operations work, every command fails with the reason. A sandbox that fails to start (user namespaces disabled) reports bwrap's own error, labelled as "the command did not run". Host-side candidate dependency preparation is refused; there is no network, so verification installs are `not_run`.
- **Operator policy** (env-only, `@protected`, refused by the dashboard's settings editor). `MARINA_CODE_SANDBOX=off|available|default|required`. Under `required`, `code workspace runner local|container` is refused and a stored `local` or container setting (for example from an earlier launch) makes commands fail instead of running elsewhere. Under `default`, an agent's `code workspace runner local` is refused (`principalOf`); a person may still choose the host. An operator-required container (`MARINA_CODE_CONTAINER_REQUIRED`, or an image while it is unset) wins over every sandbox mode. The runner setting is read with a kind-and-status query (`listCodingArtifacts(session, 1, "workspace_runner", "active")`), so newer artifacts of other kinds can never hide it and drop the session to the host. `code start` names the effective runner.
- **The person's own responsibility.** After review, what the agent wrote is the person's to run or not: scripts, `package.json` scripts, build and test configuration, editor tasks, Makefiles and the like run with the person's full rights when the person (or a host-runner session) later runs them, exactly as with any coding agent. The sandbox contains what runs during the session; it cannot make later use of the agent's output safe.
- **What it does not protect.** The workspace itself is fully readable and writable: a project `.env`, a database or credentials kept inside the workspace are visible to the sandboxed command, and so is `.git/config` (a remote URL with an embedded token). `/etc` and `/opt` stay readable. Output returns to the model, so anything a command can read can leave through the model conversation even with no network. There is no seccomp filter yet and no CPU limit beyond the timeout (bubblewrap has no cgroups; prlimit bounds processes, address space and file size, not total memory across processes). The kernel is shared: a kernel or user-namespace vulnerability escapes the sandbox, which a VM-based provider would contain. Files written in the workspace (scripts, `package.json` scripts, editor tasks, a nested `sub/.git` outside the index's gitlinks) run later on the host if a person or a host-runner session runs them. Other world commands that run on the host (`run raw`, behind `shell.exec`) are not changed by the sandbox setting.

## Test-runner allowlist shapes

`code test` / `code verify` follow the detected project runner (`src/coding/project-detection.ts`). Like `bun run test`, a project's test suite executes repository code, so the non-JavaScript runners join the allowlist only in fixed shapes: `python -m pytest` with relative selectors or node ids and `-q -x -v -rA --no-header --tb=short|line`; `python manage.py test` and `python <path>/runtests.py` with dotted labels and `--verbosity=N` / `--parallel=N`; `cargo test [--quiet] [filter]`; `go test` with relative package patterns and `-count=N -short -v`; `python -m unittest` with `discover [-s dir] [-p pattern] [-t dir]` or dotted test names and `-q -v -f -b`; and an existing workspace test script (`python tests/….py`, `test_*.py`, `*_test.py`). Selectors are confined to the workspace like `bun test` paths; `python -c`, other modules, other scripts, absolute paths and bare `pytest` stay off the list (an exec approver can still approve them per call). When the detected pytest is not importable (the fixed `python -m pytest --version` probe), `code test` / `code verify` switch to the project's test script or `python -m unittest`; that command is one of the shapes above and runs through the same allowlist, approver and gates — the switch adds no exec path. Verification adds, in the same fixed style: `npm|pnpm|yarn run <script>` for the `bun run` script names, `<manager> run test [--] <relative paths>`, `python -m mypy` / `pyright` with relative paths, `npx --no-install tsc --noEmit [-p <relative tsconfig>]`, `uv run --frozen --no-sync <allowed python command>`, `mvn -B -q test [-Dtest=Class,…]` and `gradle test -q [--tests Class]`.

**Verification preparation** (`src/coding/verification-plan.ts`) is not a `code run` path. `runPreparationStep` accepts only exact argvs from a closed table: environment probes (`python -m pytest --version`, `python -c "import django"`, `test -d node_modules`, `go version`, `cargo --version`, `mvn -v`, `gradle --version`) and lockfile-frozen installs without lifecycle scripts (`npm ci --ignore-scripts`, `pnpm`/`yarn`/`bun install --frozen-lockfile --ignore-scripts`, `uv sync --frozen`). An install runs only where `installsPermitted()` is true: a container runner with mount sync (so the install persists) and network the operator enabled (`MARINA_CODE_CONTAINER_NETWORK`, or — without an operator image — a session `network:on` that passed the `code.exec.unrestricted` gate; see "Operator policy wins"). Otherwise the install step comes back `not_run` with its reason and never moves to the host. Host workspaces refuse installs; the only host install remains the hardened Bun candidate path (`candidate-dependencies.ts`). A requested manager for another language never runs. Pre-spawn authority refusals still abort the run (`VerificationStopped`), never recorded as a check outcome.

See also: `docs/authentication.md`, `docs/guides/identity.md`, `docs/guides/deployment.md`, `SECURITY.md`; `docs/architecture/civic-substrate.md` (gates, trust profile, exec approval).

## Daily spend cap and budget scopes

`src/engine/spend-ledger.ts` records every upstream dollar once, where it leaves Marina, and refuses spend at `MARINA_DAILY_SPEND_CAP_USD` (UTC day; default $50; `0`/`off` uncapped; junk keeps the default).

- **Pricing an agent turn.** An agent turn on a model pi-ai cannot price uses the Marina default-model list price (`src/agent/provider-cost.ts`), else the provider's reported `usage.cost`. Priced media jobs record under source `media` (migration 142).

- **One ledger per world database.** The engine attaches a sink over `spend_daily` (migration 131). Every command-line entry point that spends attaches the same `DB_PATH` ledger: `attachCliSpendLedger` in `src/engine/cli-spend-ledger.ts`, or `attachWorldSpend` for the forecasting adapters. Those entry points are `futurex`, `forecast`, `arena` (spending subcommands), `arena:portfolio`, `metaculus`, `forecastbench` and `qualify-decisions`. The cap is checked against the persisted day total, re-read on every check, so a timer that starts a new process each hour or a backtest in another process cannot get a fresh budget. The in-process view is the larger of the last persisted read and the process's own spend since, so a failed write or a closed database never lowers it.
- **Atomic across processes.** `addDailySpend` writes the global row and the scope row in one `BEGIN IMMEDIATE` transaction of upserts (`cost_usd = cost_usd + excluded.cost_usd`) on the WAL database with a 5 s busy timeout. Concurrent writers serialize, and no increment is lost (`test/spend-ledger-processes.test.ts` runs two writer processes). The check and the spend are not one transaction, so concurrent processes can overshoot the cap by the calls already in flight.
- **Shared ledger across processes** (`MARINA_SPEND_LEDGER=<path>`, `src/engine/shared-spend-ledger.ts`). A host that embeds Marina may run one process per world, each on its own world database, which would give each world its own cap. Every process that names the same file records into it and checks the global and scope caps against its one UTC-day total. The file is its own small SQLite database (WAL, 5 s busy timeout, mode 0600), not a world migration. It has the same `(day, source)` and `(day, scope, source)` keys, and each record is one `BEGIN IMMEDIATE` transaction of upserts. Spend is still written to the world database too, so per-world history and per-session cost readers keep working, but caps, `readiness` and Ops `spend.daily` read the shared total. Opening it is fail-closed: an unusable path throws instead of falling back to a per-world cap. A World Collective child inherits the file and the parent's global cap, and its own budget becomes scope `child:<name>` capped at min(`MARINA_CHILD_DAILY_SPEND_CAP_USD`, parent cap). If the parent runs under a scope, the child inherits that scope with its cap lowered to the same minimum (`childSpendEnv`).
- **Budget scopes** (migration 156, `spend_scope_daily`). With `MARINA_SPEND_SCOPE=<name>`, a process also records its dollars under that scope, capped by `MARINA_SPEND_SCOPE_CAP_USD` (default $50; `0`/`off` = no scope cap). The process is refused when EITHER cap is reached, so a scope only narrows the world budget and never widens it. An invalid scope name refuses all spend rather than dropping the scope cap. Callers that reserve ahead of spending (`dailyBudget`) use whichever cap has less headroom. Without a scope, the server's behaviour is unchanged.
- **Purposes** (`src/model/purpose.ts`). Every in-process library model call (`src/model`) names what it was for: forecast, arena, research, lessons, outcomes, swarm, judge, benchmark, agent or other. The dollar is recorded once under the purpose's source (forecast/arena/research → `forecast`; judge → `decision`; agent → `agent`; the rest → `model_api`) and, in the same transaction, under a `purpose:<name>` row in `spend_scope_daily`. Purpose rows are a breakdown, not a budget: `scopeSpendToday` skips them, `purposeSpendToday` reads them, they go to the world database only (never the shared ledger file), and `MARINA_SPEND_SCOPE` may not take the `purpose:` prefix. A loopback `marina/*` call is not recorded by the caller: the `/v1` passthru that serves it records it as `model_api`.
- **One stop for batch work** (`src/engine/spend-guard.ts`, `SpendGuard`).
  - `stopReason()` stops starting items while every item in flight can still finish. It holds a reserve against the job's own budget and against the daily caps.
  - `share(slots)` gives each concurrent unit an even share of what is left as a hard cap, so the shares never add up past the budget.
  - Its users are the FutureX clean backtest, the forecasting selection, the Metaculus bot and `swebench run --max-usd`.
  - It is not the per-call stop: BrowseComp-Plus checks `CallSpendGuard` (`benchmarks/call-spend-guard.ts`) before every model call and treats a tripped item as not run. The reproduction kit splits `--budget-usd` with `budgetShare` and `capEnvValue`, which rounds down and never writes `0`/`off`.
- **Recorded once:** the lesson judge's cost is recorded by the judge itself (`metered()` or `/v1`), never again by the learning service. The spawn-time tool probe is refused at the cap, and an inconclusive probe waits `INCONCLUSIVE_PROBE_RETRY_MS` before a spawn pays for another one. The Metaculus bot records a paid forecast it did not file as a `metaculus-attempt` row: the row counts against its daily budget, and the question is not forecast again that day.
- **Without a database** a command-line process counts in memory and prints one warning that the cap is per process.
- **Visibility:** `readiness` adds a `spend-scopes` check (this process's scope against its cap, plus every scope's spend today). Privileged Ops overviews carry `spend.daily` (world total, cap, per-scope totals), which the header spend chip shows in its tooltip. Both tables are `ledger`-class rows in `RETENTION_POLICIES`.

## Ops API

`GET /api/ops/overview` and `POST /api/ops/agents/:name/stop` live in `src/net/api/ops-api.ts` (contract `src/net/ops-types.ts`, re-exported type-only by `dashboard/src/lib/ops-types.ts` with a contract test). Scoped like the memory observability API: privileged principals see every agent; a resident sees its own transitive spawn lineage. The stop route is privileged (`authorizePrivileged(…, "agent.spawn")`) and cascades children-first, emitting one `agent_stop` event per agent. `mcpAuthRequired` and `loopbackBind` come from `transportAuthRequired` and `loopbackBindFromEnv` in `src/net/host-allowlist.ts`, the same definitions the listeners use.
